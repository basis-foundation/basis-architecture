# Execution-Boundary Discovery Assessment

> **Status: non-normative discovery assessment.** This document inventories the current authorization-to-execution boundary, analyzes unresolved execution requirements and alternatives, and identifies the decisions required before BASIS implements protocol execution. It does not itself authorize execution implementation, does not establish the final execution model, does not create an ADR, does not modify any implementation repository, and does not publish or propose a schema. Where this document reaches a judgment, it is stated as an inference or a recommendation, not as accepted architecture — see §19 for what is and is not decided.

**Scope of this pass:** read-only, evidence-based inspection of the locally checked-out state of `basis-producer`, `basis-gateway`, `basis-adapters`, `basis-core`, `basis-schemas`, and `basis-identity`, plus the historical BASIS proof-of-concept material preserved in `basis-architecture`'s own white paper (the separate `basis-poc` repository was not mounted in the working environment and was not inspected directly). Only `basis-architecture` is modified.

**Companion documents:** [`docs/architecture/operation-producer-and-execution-boundary.md`](operation-producer-and-execution-boundary.md) (the primary architecture document this assessment extends past its own stopping point), [`docs/architecture/operation-producer-discovery-assessment.md`](operation-producer-discovery-assessment.md) (the methodological precedent this assessment follows), [ADR-0007](../adr/0007-adapter-evidence-construction.md), [ADR-0008](../adr/0008-producer-workload-authentication-and-admission.md), [ADR-0009](../adr/0009-trusted-producer-mtls-ingress-and-gateway-certificate-handoff.md), [ADR-0010](../adr/0010-establish-basis-producer-as-operation-producer-runtime.md), [`docs/architecture/adapter-evidence-construction-semantics.md`](adapter-evidence-construction-semantics.md), [`docs/architecture/bounded-operation-producer-reference-implementation-plan.md`](bounded-operation-producer-reference-implementation-plan.md), [`docs/security/threat-model.md`](../security/threat-model.md), [`docs/glossary.md`](../glossary.md), [`ROADMAP.md`](../../ROADMAP.md) (**Next Producer and Execution-Evidence Boundary**).

## 1. Purpose

The bounded operation-producer authorization reference slice is complete. [ADR-0010](../adr/0010-establish-basis-producer-as-operation-producer-runtime.md) (Accepted) established `basis-producer` as the permanent operation-producer-runtime repository, and, per direct inspection of that repository at commit `b8271de` on `main`, all five phases of its bounded implementation are merged: Phase 2A evidence retention (`src/basis_producer/evidence_store.py`), Phase 2B reference lifecycle (`src/basis_producer/evidence_reference_lifecycle.py`, `reference_binding.py`, `reference_id.py`), Phase 3 the authenticated gateway client (`gateway_client.py`, `gateway_client_config.py`, `gateway_client_request.py`, `gateway_client_response.py`, `gateway_client_errors.py`), Phase 4 REST adapter composition (`rest_composition.py`), and Phase 5 cross-repository conformance and demonstration (`demo/bounded-slice/`, `tests/test_bounded_slice_conformance.py`). `basis-gateway`'s Phase 1B (1B.1–1B.3) is merged at `main` `2835c4c`, implementing trusted-ingress mTLS producer authentication and admission (`src/basis_gateway/auth/operation_producer_mtls.py`, `producer_mtls.py`, `producer_mtls_trusted_proxy.py`) alongside the retained legacy bearer-subject allowlist (`auth/operation_producer.py`).

That reference slice proves protocol normalization; deterministic adapter evidence construction; evidence retention; reference lifecycle; producer workload authentication through mTLS; exact producer admission; independent bearer authorization-subject authentication; authenticated producer-to-gateway submission; gateway composition and enforcement; `basis-core` authorization evaluation; deterministic `ALLOW`/`DENY`; conformance; and reproducible demonstration. It also deliberately proves **no execution**: `basis_producer.rest_composition`'s own module docstring states, as a scope boundary rather than an omission, that the module will not "execute any protocol operation under any disposition, including `ALLOW`," and its demonstration (`demo/bounded-slice/run_demo.py`) prints an explicit `executed: no` line on every scenario summary, per the bounded implementation plan's own release-readiness record.

The current path deliberately ends at:

```text
authoritative authorization disposition → STOP
```

This document investigates what must exist beyond that point. It does not implement execution and does not choose the final execution architecture. Its purpose is to establish enough evidence and architectural clarity that a subsequent ADR, and a normative architecture specification if one proves necessary, can make the execution-model decision deliberately rather than by default or by accretion.

Execution was intentionally excluded from the completed producer chapter for a documented reason, not an oversight: `operation-producer-and-execution-boundary.md` §5 already states the invariant that "execution must never occur before the authoritative disposition is received," and [ADR-0010](../adr/0010-establish-basis-producer-as-operation-producer-runtime.md) restates that its own repository-placement decision "does not expand, and does not authorize expanding, the bounded producer slice ADR-0008 already authorized" to include execution "for REST, BACnet, Modbus, OPC UA, MQTT, DNP3, IEC 61850, KNX, or Niagara." Every accepted document this assessment inspected treats the authorization/execution split as a load-bearing architectural boundary, not an artifact of implementation sequencing. This assessment inherits that boundary; it does not reopen whether the split itself is correct.

## 2. Scope

**This assessment covers:** the logical execution responsibilities that appear once an authorized operation may cause a physical or protocol side effect; the authorization-to-execution binding problem; a candidate execution lifecycle and its failure semantics; protocol-family differences relevant to that lifecycle; workload and device trust and credential ownership; replay and freshness; execution evidence and its relationship to authorization evidence; correlation across the existing and future identifier chain; deployment-topology options; and a first-order compromise/bypass analysis of each option.

**This assessment explicitly excludes:** runtime implementation in any repository; schema publication or schema placeholders; creation of `basis-executor` or any other new repository; a final process/deployment topology; full protocol-stack implementation for any of the nine adapter families; `basis-console` design; and deployment tooling. It does not authorize a "Phase 6" of the completed producer implementation plan — that plan's own status record is explicit that "no Phase 6 is defined by this plan: the bounded reference slice stops at the authorization disposition, and extending it into protocol execution is a separate, future architecture decision this plan does not make."

**Governing principle, restated from the task that authorized this assessment and consistent with every accepted document this assessment cites:**

> A logical architectural role does not automatically imply a repository, process, service, package, or deployment unit. In particular, this assessment does not create or recommend `basis-executor` merely because the phrase "protocol executor" is useful.

Nothing below the `STOP` line exists in any inspected repository.

**What the system can prove at this point, restated precisely:** who called the gateway (the mTLS-authenticated producer workload identity, independently of the bearer-authenticated authorization subject); what operation was normalized and by which adapter implementation; what the producer asserted as evidence for that operation, referenced by an RFC-8785-canonical digest; what the kernel decided, deterministically and reproducibly, given that input; and what disposition the gateway enforced at its own HTTP boundary. Each of these facts is recordable and correlatable by the identifiers in §13, but their durability guarantees are not uniform, and this assessment does not claim otherwise: adapter evidence retained under `basis-producer`'s Phase 2A/2B evidence-retention lifecycle is durably retrievable by design, verified at retention time and independently re-derivable from the retained artifact (subject to the caveats §10's digest-verification discussion states); `basis-core` itself remains persistence-independent by design — it performs no external I/O or persistence during evaluation, per the glossary's **Evaluation Layer** entry — and does not itself guarantee that `AuditEvidence` is durably stored anywhere, which is a caller/deployment responsibility rather than a kernel one; and `basis-gateway` records `GatewayAuditEvent` according to its own runtime and deployment configuration, which this assessment did not inspect for durability guarantees beyond confirming the event type exists and its construction-time invariants (§3). A future execution-evidence design should not assume the authorization side's durability is more uniform across components than it actually is.

**What it cannot prove, restated precisely, because no accepted document states this list in one place and it is the single fact this whole assessment exists to make unmissable:** an `ALLOW` disposition does not prove that execution was attempted; that execution occurred; that a device received anything; that the operation succeeded; that resulting device state changed; or that the specific operation dispatched — if any dispatch ever occurs — is the same operation that was authorized rather than one modified after the fact. `basis_core.enforcement.operation_aware.EnforcementDisposition`'s own class docstring already states the narrowest form of this limit for the kernel's own artifact type ("not... proof that any downstream protocol command actually executed"); this assessment generalizes it to the whole chain because no single document currently states the generalization as directly as the completion of the producer slice now makes possible.

## 5. Logical Roles and Ownership Questions

`operation-producer-and-execution-boundary.md` §2 already named two roles this assessment inherits rather than re-derives: the **protocol executor** ("the component that, after the gateway's disposition permits it, actually communicates with the protocol endpoint or platform") and the **execution-evidence producer** ("the component that records what was observed after authorization permitted an attempt"). Neither role has an implementation anywhere in the inspected repositories, and neither role's definition has changed since that document was written — this assessment's contribution is analyzing what sits *inside* those two named roles now that the authorization side of the boundary is a real, working system to reason against, not a hypothetical one.

Decomposing further, direct inspection of the completed producer slice suggests at least four genuinely distinct sub-responsibilities hide inside "protocol executor" and "execution-evidence producer" as currently named:

- **Original-operation preservation and authorized-operation binding** (working, non-normative terminology — this is a corrected reframing of what an earlier draft of this assessment called "execution-request derivation"; see the note below) — retaining the original protocol-shaped `ProtocolOperation` that entered the chain at normalization, and, immediately before dispatch, verifying that the operation about to be dispatched is the same operation whose normalized semantics received the authoritative disposition. The chain already carries a protocol-preserving artifact partway: `NormalizedAuthorizationRequest` includes protocol evidence preserved verbatim from the original `ProtocolOperation` (§4), which is at minimum a *candidate* preservation mechanism. Whether that existing artifact is sufficient on its own to serve as the record of the operation to be dispatched, or whether a distinct dispatch-intent record is needed, is not established by this assessment. This framing does not claim that a security binding between the original `ProtocolOperation` and the final authorization disposition already exists today — it does not (§6) — only that the artifact to be preserved and bound is the original operation, not a reconstruction of one.
- **Protocol dispatch** — opening the protocol session or connection and transmitting the operation. This is the role `operation-producer-and-execution-boundary.md` names "protocol executor" most directly.
- **Execution-result observation** — determining, from whatever the protocol offers (an acknowledgement, a timeout, a subsequent read), what actually happened.
- **Execution-evidence construction and retention** — turning that observation into a recorded, provenance-classified account, analogous to (but never merged with) what `basis-adapters`' `construct_adapter_evidence()` and `basis-producer`'s evidence-retention/reference-lifecycle pair already do on the authorization side.

**Note on this reframing.** An earlier draft of this section analyzed the first sub-responsibility as "execution-request derivation" — an executor turning the gateway's canonical authorization representation back into a dispatchable protocol operation by reversing gateway/kernel authorization semantics. This assessment now rejects that framing as the preferred model, and cautions against designing toward it: the producer path already begins with a real protocol-shaped `ProtocolOperation`, and reconstructing one from normalized/composed authorization output would create a second, redundant protocol-mapping path outside `basis-adapters`, risking normalization/dispatch drift of the same kind ADR-0007 already reasoned about (and rejected a combined role to avoid) on the authorization side. The more precise architectural problem, restated directly, is not how to derive a dispatchable operation from what authorization produced, but how BASIS preserves the original protocol-shaped operation and proves that the exact operation about to be dispatched is the operation whose normalized semantics were authorized.

Whether these four are one component, two, or four is exactly the kind of decision this assessment declines to make on its own authority, consistent with the governing principle in §2. What the evidence supports is that **verifying the binding immediately before dispatch is plausibly inseparable from dispatch itself** — the check is only meaningful as the last gate before the side effect, so co-locating it with dispatch avoids a second, potentially stale copy of "what was authorized" living in a component other than the one doing the dispatching — while **preservation of the original protocol operation is plausibly separable from dispatch**: the chain already begins preserving protocol-native data at normalization (§4), and extending that preservation through the authorization chain is closer in kind to the evidence-retention responsibility `basis-producer` already has (Phase 2A/2B) than to a dispatch-time responsibility. **Execution-result observation and execution-evidence construction/retention are, separately, plausibly separable from dispatch** — the same separation ADR-0007 already made, and justified the same way, on the authorization side ("risks normalization drift" was ADR-0007's stated reason for rejecting a combined evidence-construction-plus-assembly role; an analogous drift risk — misrepresenting what a device did because the same component both dispatched and self-reported — applies here).

### Option A — producer and executor are one process/component

Conceptual form: `basis-producer` → authorization → internal execution role → endpoint.

*Simplicity.* Highest of the three options — no new network trust boundary, no new authenticated handoff contract, no second deployable artifact. `basis-producer`'s existing `RestOperationComposer` pattern (§rest_composition.py) already demonstrates the "compose several already-tested collaborators into one bounded pipeline" style this option would extend one more stage.

*Credential custody.* The same process that holds the producer's mTLS client certificate and (however it obtains one) the authorization-subject credential would also hold whatever protocol/device credential the target endpoint requires. ADR-0010 already establishes that `basis-producer` is "materially different in kind" from every neighboring component specifically because it is the one component permitted to hold a network-facing credential; adding a device credential to that same process is an incremental widening of an already-accepted credential-custody boundary, not the creation of a new one.

*Compromise blast radius.* Highest of the three options for a *single* compromised process: an attacker who compromises this process gains the producer's authenticated identity, the evidence-construction/retention path, and direct device reach, in one step. §12 analyzes this in more detail.

*Operational deployment.* Simplest — one artifact to deploy, version, and monitor per protocol integration.

*Correlation.* Simplest to get right, because no cross-process handoff needs its own binding mechanism (§6) — the process's own in-memory state can serve as the binding between "what was authorized" and "what is about to be dispatched," subject to the crash-consistency caveats in §14.

*Evidence lifecycle.* The same evidence-retention infrastructure `basis-producer` already has (Phase 2A/2B) could plausibly be reused or extended for execution evidence, though §10 argues this reuse should not be assumed without deciding whether authorization and execution evidence should share a retention mechanism at all.

*Testing.* `basis-producer`'s existing layered-error-propagation test discipline (each collaborator's typed errors propagate unwrapped, per `rest_composition.py`'s own "Failure semantics" section) extends naturally to one more collaborator.

*Protocol extensibility.* Adding execution to `basis-producer` for a second protocol would mean adding a second protocol-specific dispatch path inside the same component that already orchestrates that protocol's adapter — no worse, extensibility-wise, than the adapter library's own nine-protocol pattern, but it does mean `basis-producer` would need to become protocol-aware in a way it deliberately is not today (`rest_composition.py` is the *only* protocol-specific module in the current `basis-producer` source tree; every other module is protocol-neutral).

### Option B — producer and executor are separate processes/services

Conceptual form: `basis-producer` → authenticated execution handoff → executor → endpoint.

*Additional trust boundary.* This is the option's defining cost. `operation-producer-and-execution-boundary.md` §9 already names the risk directly: "a compromised or confused executor that accepts commands without checking their disposition binding reintroduces exactly the 'confused deputy' abuse case the interoperability roadmap already names." Any handoff artifact crossing this boundary needs the same rigor ADR-0008/ADR-0009 applied to the producer-to-gateway boundary — which took four ADRs' worth of decision-making (mTLS selection, trusted-ingress topology, certificate-identity-profile precision) to get right for a *single* boundary. This option requires doing that work again for a second boundary.

*Execution handoff authentication.* Genuinely undecided territory (§11): does the executor authenticate the producer, does the producer authenticate the executor, or both mutually? No accepted document answers this because no accepted document has needed to.

*Replay protection.* Materially harder than same-process, because a captured handoff artifact could in principle be replayed against the executor from an entirely different network position than the one that produced it — precisely the residual risk ADR-0008's own "Replayed HTTP requests" security-consequences entry already flags as unresolved for the *existing*, single-hop producer-to-gateway boundary ("full replay protection is an explicitly deferred, ecosystem-wide question"). A second hop does not reduce that residual risk; it plausibly compounds it (§7).

*Credential separation.* This option's strongest argument: the process holding the producer's authorization credentials never needs to hold a device credential at all, and a compromise of one does not automatically compromise the other. This is the same separation-of-custody argument ADR-0010 already accepted for separating `basis-producer` from `basis-gateway` ("the gateway must not hold the producer's client credential").

*Deployment complexity.* Two deployable artifacts, two release cadences, two sets of operational monitoring, per the same kind of cost `basis-producer`'s own establishment already incurred (ADR-0010 "Tradeoffs": "one additional repository and component for the Foundation to maintain").

*Air-gapped operation.* Neutral-to-negative: an air-gapped deployment must now provision and rotate credentials for two authenticated boundaries (producer-to-gateway and producer-to-executor, or gateway-to-executor, depending on where the handoff sits) rather than one. ADR-0008's own "Operational consequences" section already documents certificate-rotation burden as a real, non-minimized cost for a *single* mTLS boundary; a second boundary doubles that class of cost, not merely adds a fixed increment to it.

*Failure modes.* Strictly more numerous than Option A — every failure mode Option A has (§14), plus handoff-transport failure (the executor never receives the dispatch instruction at all) as a new, distinguishable state.

*Additional contracts.* This option is the one most likely to require a new machine-readable contract (§10's "producer admission/capability onboarding contract" gap, generalized to an execution-handoff contract) — though whether that contract needs to be a `basis-schemas` publication or can remain deployment configuration is exactly the kind of question ADR-0008 answered for the producer-to-gateway boundary only after building a reference implementation, not before.

### Option C — shared producer orchestration with protocol-specific conforming executors

This is a placement question layered on top of A or B, not a third structurally distinct option: it asks whether the nine protocol families (§9) justify nine distinct execution implementations under one shared architectural contract, the same way `basis-adapters` already supports nine independent normalization implementations under one shared `normalize()` contract. The evidence in §9 supports this at the level of *interface* — a shared execution-lifecycle vocabulary (§8) that every protocol-specific executor implements — while leaving *process placement* (whether each protocol's executor is a distinct deployable, or nine dispatch branches inside one deployable) as an orthogonal choice between A and B, made independently per protocol if a deployment's risk posture warrants it. Nothing in the inspected repositories argues for or against this at the level of evidence; `operation-producer-and-execution-boundary.md` §11's own "protocol-specific integrations... premature to commit to now, since no reference implementation of even one conforming runtime exists" applies with equal force here, one layer further down the stack.

### Other options considered and set aside

**Embedding execution inside `basis-adapters`.** Rejected on the same grounds `operation-producer-and-execution-boundary.md` §11 already rejected embedding the *producer* role there, restated with sharper evidence now that the library's non-network discipline is proven, not merely asserted: every one of the nine adapters' module docstrings makes an explicit "no live protocol communication" claim (§9 quotes each), and several go further — the DNP3 and IEC 61850 adapters both state, independently and in near-identical language, that they are "stateless" by design and that "stateful control sequencing belongs to a runtime enforcement boundary... not a normalization library." That is the adapters themselves stating, in their own accepted design invariants, that they are not the right home for execution's inherently stateful concerns (select/operate correlation, session state, sequence numbers).

**Embedding execution inside `basis-gateway`.** Rejected for the same reason `operation-producer-and-execution-boundary.md` §11 already rejects it: the gateway's own stated existence rationale is that "`basis-core` is a library, not a network service" requiring authentication, composition, and enforcement — not protocol translation or protocol dispatch. Nothing this assessment found in the gateway's Phase 1B implementation changes that reasoning; if anything, the gateway's own audit-event design (`GatewayAuditEvent` deliberately omitting an `enforcement_status` field, per §10) is direct evidence the gateway's own architects have already reasoned about, and declined, absorbing an execution-result concept.

**Embedding execution inside `basis-core`.** Not seriously entertained by any inspected document, and this assessment finds nothing to reopen that: `basis-core`'s isolation from network, transport, and protocol concerns is the kernel's foundational property (§4 of `basis-ecosystem.md`), and `EnforcementDisposition`'s own two-value, execution-silent design (§4 above) is itself evidence the kernel's authors have already drawn this line precisely where it needs to be.

## 6. Authorization-to-Execution Binding

The threat this section analyzes: `authorized request A` → modification → `executed request B`.

**This section rejects reconstruction-based framings of the binding problem.** An earlier draft of this assessment analyzed part of this problem as "execution-request derivation" — an executor reversing the gateway's canonical authorization representation back into a dispatchable protocol operation. That framing is rejected, or at minimum strongly cautioned against: reconstructing a device command by reversing gateway/kernel authorization semantics would create a second, redundant protocol-mapping path outside `basis-adapters`, and nothing in the evidence gathered here supports building one (§5). The producer path already begins with a real protocol-shaped `ProtocolOperation`; the security question this section analyzes is not how to derive a dispatchable operation from authorization output, but how BASIS preserves that original operation through the authorization chain and proves that the exact operation about to be dispatched is the operation whose normalized semantics were authorized. This reframing does not claim the binding already exists — it does not, per the findings below — only that the artifact to be bound is the preserved original operation.

**How does the preserved original `ProtocolOperation` relate to adapter evidence?** Not directly, and this assessment does not conflate them. Adapter evidence material is constructed from the *normalized* request plus a governed, per-protocol projection of protocol evidence (§9), not from the original `ProtocolOperation` object itself — the evidence material is already one mapping-step removed from the original operation. This matters for the binding question: the adapter evidence digest can attest that specific normalized-plus-projected fields were what the authorization decision was evaluated against, but it does not, by itself, attest that those fields faithfully represent the original `ProtocolOperation`, nor that the operation an executor is about to dispatch is the preserved original rather than some other artifact. Using adapter evidence as a stand-in for "the preserved original operation" without examining whether the normalization mapping it depends on is itself provably faithful would conflate two different artifacts — a caution this assessment states directly rather than resolving.

**What exact data is covered by authorization today.** The kernel evaluates `OperationAwareDecisionRequest`, whose action/resource/context fields are exactly what `basis-gateway`'s `operation_aware_composition.py` composed from the producer's submission. The `AdapterEvidenceReference` the producer submitted is part of that evaluated input (it participates in policy conditions where a bundle's rules reference it), but the reference is a *digest of adapter evidence material*, not a digest of the specific normalized action/resource/context values the gateway went on to compose — those two things are related (the evidence material embeds `protocol`, `action`, `resource_type`, `resource_id` per ADR-0007's `basis-adapter-evidence-v1` profile) but are not cryptographically bound to each other by any mechanism this assessment found. Nothing in the inspected code computes or verifies that the gateway-composed canonical action/resource actually corresponds field-for-field to what the referenced evidence material independently asserts.

**Which normalized fields identify the operation.** `action`, `resource_type`, `resource_id`, and (where present) `operation_intent`, `location`, `device`, `protocol_context`, `safety_context`, `environment_context`, `risk_context` — the same field-ownership table `operation-producer-and-execution-boundary.md` §4 already publishes, unchanged by the completed implementation.

**Does execution require the preserved original operation, or a canonical digest?** The evidence supports neither answer being free of a real design cost, and per the reframing above, the more precise question is not whether an executor can *derive* a dispatchable operation from the gateway's canonical representation — the evidence does not support that design at all (§5) — but whether the executor dispatches from a preserved original `ProtocolOperation` it (or an upstream component) already holds, checked against a digest, or instead receives the preserved operation itself as part of the authorization handoff. Requiring the preserved original operation means an executor needs a channel to receive or already hold it that is at least as trustworthy as the one that carried the normalized request to the gateway — which, in a same-process topology (Option A), is plausibly free (it is already in memory, provided the process retains it from normalization onward), but in a separated topology (Option B) reopens the whole authenticated-handoff problem §5 already flags. Requiring only a canonical digest, without the preserved original operation, is not sufficient by itself — a digest can verify that a candidate operation matches what was authorized, but it cannot substitute for retaining the operation to be dispatched somewhere in the chain.

**Could adapter evidence participate in the binding?** Plausibly, but not without a decision this assessment does not make: the adapter evidence digest is already computed under a fixed, accepted canonicalization profile (RFC 8785, per ADR-0007), and reusing that same digest as one input to an execution-binding check would avoid inventing a second canonicalization mechanism. But the digest as currently defined covers *normalized* fields plus a *governed projection* of protocol evidence — not necessarily every field an executor would need to fully verify the preserved original operation against what was authorized, and `adapter-evidence-construction-semantics.md`'s own governed-projection design (approved metadata keys only, closed allow-list) was deliberately built to be *narrower* than the full protocol evidence, for evidence-hygiene reasons unrelated to execution binding. Widening that projection to serve a binding purpose it was not designed for is exactly the kind of scope creep §2's non-goals warn against.

**Is a separate authorization grant/artifact needed?** This is the central open question, and the evidence in this assessment does not make it unavoidable. The gateway's own `GatewayAuditEvent`/`AuditEvidence` pair already constitutes a recordable, correlatable account of what was authorized — whether it is durably persisted in a given deployment depends on `basis-gateway`'s own runtime configuration rather than on any persistence guarantee `basis-core` itself provides (§4); whether that pair is *sufficient* as a binding artifact, or whether a distinct, purpose-built "execution grant" is required, depends on decisions this assessment explicitly declines to make (§7's freshness question in particular). What the evidence does rule out, per the task's own instruction and consistent with every accepted document's restraint on inventing cryptographic mechanisms: nothing here shows that a new signed execution token is *unavoidable*. The existing `AuditEvidence`/`GatewayAuditEvent` pair, referenced by the correlation identifiers already in the chain (§13), is a plausible sufficient binding mechanism for a same-process (Option A) topology specifically, because in that topology "the executor trusts the artifact" and "the executor trusts its own process's prior state" collapse into the same fact.

**Must such a grant be cryptographically protected?** Only if the channel carrying it is not already trusted by some other means. In Option A, the channel is process memory — no additional cryptographic protection is implied beyond what already protects the process itself. In Option B, the channel is a network hop, and per §5's analysis, that hop needs authentication of *some* kind regardless of whether the artifact it carries is a bespoke signed token, a bearer reference to the gateway's own `AuditEvidence`, or an mTLS-authenticated direct call. This assessment does not find evidence that the specific mechanism must be a new signed token as opposed to, for example, an mTLS-authenticated call the executor makes back to the gateway (or to `basis-producer`) to fetch and verify the disposition it is about to act on.

**Is the gateway response sufficient?** Structurally, the response the producer already receives (`GatewayEvaluationResult`, per `basis-producer`'s own `gateway_client_response.py`) carries the disposition, the outcome, and the failure-reason vocabulary — everything an executor would need to know *whether* to dispatch. It does not carry anything that would let an executor detect that the operation it is about to dispatch has been silently substituted for a different one between receipt and dispatch, because nothing in the chain computes a binding digest over the *composed, canonical* operation (as opposed to the pre-composition, adapter-normalized one) at all.

**Should an executor trust producer memory/state rather than a portable grant?** In a same-process topology, this is not a meaningful distinction — "producer memory" and "the grant" are the same fact. In a separated topology, trusting an executor's own local record of "what I was told to do" without any check against a portable, gateway-issued artifact reintroduces exactly the confused-deputy risk §5 already names. The evidence favors: same-process topologies can safely rely on in-memory state; separated topologies cannot, and need a genuine portable artifact.

**Does the answer change across same-process vs. separate-process deployment?** Yes, materially — this is the single clearest finding in this section. The binding problem is close to free in Option A and is the dominant new engineering cost in Option B. This is not a novel observation particular to execution; it is the same shape of finding ADR-0009 already reached for the producer-to-gateway boundary specifically because direct in-process certificate handling proved unsafe and a trusted-ingress topology was required instead (Phase 1A's "Outcome B"). The execution boundary has not yet had its own equivalent spike; this assessment does not substitute for one.

**Which identifiers are security-relevant versus merely diagnostic?** Restated from §13's correlation analysis: the gateway-generated correlation ID and the kernel's `trace_id`/`evidence_id` are diagnostic and integrity-adjacent (they let a human or a monitoring system link records after the fact) but none of them today functions as a security control — nothing checks them at a trust boundary, they are simply carried and compared for correlation. A binding mechanism, if one is built, would need to promote at least one identifier (or a new one) from diagnostic to security-relevant status, which is itself a decision with consequences for every existing consumer of that identifier's current, weaker guarantee.

**This assessment does not design a new signed execution token.** Per the task's explicit instruction and consistent with the evidence above: nothing inspected shows such a mechanism is unavoidable, and every accepted document this assessment cites treats "avoid inventing crypto for elegance" as a governing discipline (most directly, ADR-0007's rejection of using `reference_id` as anything more than an opaque identifier, and ADR-0008's restraint from adding a request-body producer-identity field "merely to duplicate transport-authenticated identity").

## 7. Replay and Freshness

**Is an `ALLOW` reusable today?** As a fact about the software: yes, trivially, because nothing in `basis-core`, `basis-gateway`, or `basis-producer` tracks whether a given `AuditEvidence`/`GatewayAuditEvent` pair has already been "consumed." Nothing prevents a caller (a producer, or, in a hypothetical separated topology, an executor) from acting on the same disposition twice. This is not a defect introduced by the authorization-only scope — it is a direct consequence of the kernel's own deliberate statelessness (`basis-core` "performs no external I/O, persistence... during evaluation," per the glossary's **Evaluation Layer** entry), and the threat model already names the general shape of this gap for the *existing* authentication boundary (§7.6, "the architecture provides expiry bounds and audit correlation but has not settled comprehensive replay defense").

**What would replay mean for a read?** Materially low-consequence in the general case — dispatching the same authorized read operation twice produces (at most) a duplicate, non-destructive query. Some protocol families complicate even this: MQTT's adapter explicitly preserves wildcard subscription topics verbatim without expanding them, so a "read" in the form of a subscribe could, depending on QoS and broker retention semantics, have effects (delivery-count accounting, duplicate message processing downstream) that are not perfectly free of consequence — but this is a second-order concern relative to writes.

**What would replay mean for a write/control operation?** Potentially serious, and protocol-dependent in a way that makes a single ecosystem-wide answer risky to assert. DNP3's adapter module docstring states explicitly that the adapter is "stateless: SELECT and OPERATE normalize independently... does not correlate select/operate pairs, track sequence numbers, enforce select timeouts, or protect against replay," and assigns that responsibility explicitly to "a runtime enforcement boundary or a future DNP3-aware runtime layer." IEC 61850's adapter makes the near-identical statement for its own SBO (select-before-operate) model. Both of these statements are direct evidence, from the components closest to the protocol semantics, that **replay protection for control operations cannot be assumed solved by normalization and must be solved somewhere else in the chain** — and today, nowhere in the chain solves it.

**Does a same-process producer/executor need explicit anti-replay state?** Only if it is expected to reject a second, distinct submission of the same logical operation — which is a policy question (is duplicate submission itself suspicious?) as much as a security one. A same-process topology at least has the option of tracking "have I already dispatched the operation this specific `AuditEvidence` authorized" as simple in-memory state, without needing a distributed mechanism.

**Does a network handoff to a separate executor require stronger replay controls?** Yes — this follows directly from §6's finding that separated topologies reopen the confused-deputy risk. A captured handoff artifact, replayable from a different network position than the one that legitimately produced it, is a strictly worse replay surface than same-process reuse of a disposition the process already holds honestly.

**Is wall-clock expiry necessary?** Not established as necessary by this assessment's evidence, but plausible as one component of a solution. `basis-schemas`' published contracts carry no expiry-shaped field on any evidence-reference or decision-response contract today (confirmed by direct schema inspection, §3), so there is no existing precedent in the ecosystem's own contracts to extend. ADR-0008's own security-consequences analysis for the *existing* mTLS boundary already grapples with a closely related question (certificate validity, not disposition validity) and explicitly declines to require continuous connectivity to an external validation service — "unacceptable for isolated and air-gapped OT deployments" — a constraint that would apply with equal force to any wall-clock-expiry mechanism for a disposition.

**Would monotonic/process-local validity sometimes suffice?** For the same-process (Option A) topology specifically, yes, plausibly: a process-local sequence counter or a simple "not yet consumed" flag requires no clock synchronization and no external dependency, and would be sufficient to prevent the process's own accidental double-dispatch (crash-and-retry, for example — see §14). It would not, by itself, prevent a deliberately malicious replay by a compromised version of that same process, which is a different threat this assessment analyzes separately in §12.

**How do disconnected or air-gapped deployments affect time assumptions?** Directly and negatively for any mechanism depending on wall-clock freshness relative to an external time source. BASIS's own operational profile — "long-lived, intermittently maintained deployments, constrained maintenance windows, and frequently air-gapped or low-connectivity networks," per ADR-0008's own "Operational consequences" section, written about the producer-authentication boundary but applicable without modification to an execution boundary — means any freshness mechanism this ecosystem eventually adopts for execution should be evaluated first against whether it degrades gracefully with no reachable time authority, the same discipline ADR-0008 already applied to certificate validation.

**How does policy change after authorization affect a pending execution?** Genuinely unresolved, and not analyzed by any document this assessment inspected. If a policy bundle is reloaded (`basis-gateway`'s `policy/operation_aware_loader.py` already supports bundle selection at runtime, per the capability matrix in the prior producer-discovery assessment) between the moment a disposition is issued and the moment an execution attempt would occur, nothing in the current architecture defines whether the disposition remains valid, becomes stale, or must be re-evaluated. This is squarely a freshness question this assessment surfaces rather than resolves.

**What happens if the authorization subject credential expires after evaluation but before actuation?** Also unresolved. The bearer authorization-subject credential is verified once, at request time, by `basis-gateway`'s existing `authenticate()` dispatch; nothing in the chain re-checks it later, and in a same-process topology there is no "later" to re-check against unless the process deliberately introduces a delay between disposition and dispatch. In a separated topology, if the executor is expected to independently re-verify the authorization subject's continued standing before acting, that is a new responsibility with its own credential-verification cost, not free of the same operational burden ADR-0008 already documents for the producer's own mTLS credential.

## 8. Execution Lifecycle and Failure Semantics

The interoperability roadmap's five-state sketch — `authorized-but-not-attempted`, `attempted-and-completed`, `attempted-and-failed`, `partially-applied`, `execution-status-unavailable` — is, per every accepted document that cites it, explicitly non-normative roadmap language, not a governed contract (`operation-producer-and-execution-boundary.md` §2 states this directly: "that sketch is roadmap language, not a governed contract, and this document does not promote it to one"). This assessment inherits that caution and evaluates the sketch's sufficiency against the protocol-level evidence gathered in §9, rather than treating it as settled.

**Sufficiency assessment.** The five states are a reasonable *coarse* partition but the protocol evidence in §9 suggests at least two refinements a bounded reference implementation would likely surface: first, "attempted-and-failed" conflates *rejected before transmission* (a local, deterministic failure — malformed operation, no route to the endpoint) with *rejected by the remote endpoint* (a protocol-level negative acknowledgement, which several protocols represent very differently — compare a BACnet `Error-PDU` to a Modbus exception response to an MQTT broker connection refusal) — collapsing these loses information the existing authorization-side design would never accept losing (compare `operation-producer-and-execution-boundary.md` §8's own five preserved distinctions, none of which permit collapsing "not executed" causes together). Second, "execution-status-unavailable" needs to distinguish *no acknowledgement primitive exists for this protocol* (DNP3's stateless SBO model, or an MQTT fire-and-forget publish at QoS 0) from *an acknowledgement primitive exists but did not arrive in time* (a timeout on a protocol that does support confirmation) — these are different facts with different operational implications, and merging them the way the five-state sketch currently does would obscure exactly the kind of protocol-specific reality §9 documents.

**Candidate states, evaluated against explicit scenarios:**

| Scenario | Best-fit state (of the candidates) | Why the fit is imperfect, if it is |
| - | - | - |
| Authorization succeeded, endpoint unavailable | not attempted | Distinguishable from a local pre-dispatch failure only if the executor can tell "endpoint unreachable" from "operation malformed" before it tries to connect — not all protocols make this distinction cheap |
| Failure before dispatch (local validation) | not attempted | Same fit as above; the five-state sketch does not separate this from endpoint-unavailable, though the two have different remediation paths |
| Timeout before bytes are sent | not attempted, arguably | A timeout establishing a connection (TCP handshake, TLS negotiation) is closer to "not attempted" than "attempted," but this is a judgment call the sketch does not make explicit |
| Timeout after dispatch | status unknown | The clean case for this state — bytes left the executor, no confirmation returned |
| Transport connection failure (mid-operation) | status unknown, most protocols | The device may have received a partial operation; whether that constitutes "attempted" depends on the protocol's framing (a single-datagram Modbus write is atomic at the transport level; a multi-frame IEC 61850 MMS exchange may not be) |
| Protocol rejection (explicit negative response) | attempted-and-failed | The clean case for this state, but see the refinement above — this needs to be distinguishable from a local pre-dispatch rejection |
| Acknowledgement received (positive) | attempted-and-completed | Clean fit, but "completed" should not be conflated with "state change verified" (see the next two rows) |
| Acknowledgement absent (protocol has none, or none arrived) | status unknown | Needs the refinement above: "protocol structurally has no ack" and "ack didn't arrive" are different facts |
| Operation accepted but state change unverified | attempted-and-completed, with a caveat the five-state sketch has no field for | This is the KNX DPT-shape-check case: the adapter's own docstring notes it validates "a write's format" without confirming "the physical actuator actually moved" — a distinction the five states do not currently carry a field for |
| Operation accepted and state change verified (independent readback) | attempted-and-completed, with the same missing caveat field | Genuinely stronger evidence than the row above, and the current vocabulary cannot distinguish the two |
| Multi-step operation partially completed (protocol/session level) | protocol transaction partially progressed, not automatically `partially-applied` | The five-state sketch's `partially-applied` label implies a physical side effect partly occurred; DNP3 and IEC 61850's stateless select/operate model (§9) makes multi-stage protocol transactions that stop partway through a structurally real, frequent outcome for those two families specifically, but a SELECT-succeeds/OPERATE-fails sequence is direct evidence only that the protocol exchange stopped there — it is not, by itself, evidence of what fraction of the physical operation the device actually performed. Whether `partially-applied` should be reserved for confirmed physical partial application, redefined to mean protocol-transaction progression, or split into two distinct states is left to the execution-lifecycle specification |
| Process crash before dispatch | not attempted, if durably recorded before the crash | Requires the "create an execution-attempt record before dispatch" ordering discussed in §14 to be provable rather than assumed |
| Process crash after dispatch | status unknown | The device may have acted; the executor's own crash prevents it from ever knowing |
| Response lost after device may have acted | status unknown | Structurally identical to the row above from the executor's perspective |
| Evidence persistence failure after device action | attempted-(unknown outcome), evidence gap flagged separately | This is a *distinct* failure from any execution-status value — the operation's real-world outcome and the durability of the *record* of that outcome are separate facts, exactly as §10 argues below |
| Retry after known failure | a new attempt, correlated to the prior one | Not itself a new state, but raises the idempotency question §7 already flags as protocol-dependent and unresolved |
| Retry after unknown outcome | a new attempt, correlated to the prior one, carrying materially higher risk for non-idempotent operations | The riskiest row in this table for write/control operations on protocols with no read-back confirmation (DNP3, IEC 61850's control paths) |

**The two governing distinctions this section preserves, restated because they are the load-bearing finding of this whole section:**

> `failed` and `not executed` are not necessarily equivalent — a local pre-dispatch rejection and a remote protocol-level rejection are different facts with different remediation paths, and collapsing them loses exactly the kind of information the authorization side of this architecture has never permitted itself to lose.

> `timeout` does not necessarily mean the endpoint did nothing — a timeout after dispatch is evidence of *uncertainty*, not evidence of *non-occurrence*, and any execution-evidence contract that reports a timeout as equivalent to "not executed" would be lying by omission.

**What the generic BASIS execution model must leave open, so protocol-specific executors can report reality without lying, stated directly from this table's evidence:**

- It must not assume every protocol has a single-step, atomically confirmable control operation — DNP3 and IEC 61850's stateless select/operate model makes multi-stage protocol transactions that stop partway through a real, frequent, structural outcome for those two families specifically, not an edge case. Whether a specific partly-progressed protocol transaction should be reported as a physical `partially-applied` side effect, as a `status unknown` result, or as some other state distinguishing protocol-level progression from device-level effect is a decision this assessment leaves to the execution-lifecycle specification (§8) — the adapters' own stateless design gives no basis for inferring physical actuation from protocol-transaction progress alone.
- It must not assume acknowledgement implies state-change confirmation — KNX's own adapter docstring states this distinction explicitly for its own protocol, and it generalizes: a positive protocol-level acknowledgement (a Modbus normal response, a BACnet `SimpleACK`) proves the device *accepted* the operation, not that the device's physical state actually changed as a result.
- It must not treat a REST 2xx response, or any other protocol-level positive acknowledgement, as generic proof that an intended real-world side effect completed. What a 2xx response can support is that the remote HTTP application accepted the request and returned a result; whether the request caused any downstream physical action, whether an asynchronously scheduled operation later completed, and whether device state actually changed are each a distinct fact a 2xx response does not, by itself, establish. This applies the same protocol/application-acknowledgement-versus-execution-completion distinction the KNX row already draws explicitly for its own protocol, extended here because REST is the protocol family in this ecosystem whose "success" response is easiest to mistake for a general execution-completion signal.
- It must not assume every protocol offers a meaningful "acknowledgement absent" signal distinct from "protocol doesn't have one" — MQTT at QoS 0 and KNX group communication are both structurally closer to fire-and-forget than to request/response, and forcing them through a request/response-shaped execution-status vocabulary would misrepresent what the protocol actually offers.
- It must leave room for protocol-specific extension fields on whatever execution-evidence shape it eventually adopts, because the *kind* of evidence available (a Modbus exception code, a BACnet error class/code pair, a DNP3 internal-indications bitfield, a KNX bus-level NAK, an OPC UA `StatusCode`) is genuinely different in shape across families, in the same way `adapter-evidence-construction-semantics.md` already accepts a per-protocol governed metadata projection rather than one universal evidence shape for *authorization* evidence.

**The goal is not nine protocol specifications**, and this assessment does not attempt to write them — the table above answers the narrower question the task poses (what must the generic model leave open) using only what the nine adapters' own accepted design invariants already state about themselves.

## 10. Execution Evidence

**Invariant preserved, restated because it governs everything else in this section:**

> Authorization evidence records what BASIS decided. Execution evidence, if it comes to exist, would record what happened after that decision. Execution evidence must never mutate, reinterpret, or replace the original authorization decision.

This restates, without weakening, `operation-producer-and-execution-boundary.md` §5's own invariant ("an execution result must not alter or rewrite the prior kernel outcome") and the structural reason `GatewayAuditEvent` deliberately has no `enforcement_status` field today.

**Who observes execution, who constructs execution evidence, who retains it.** Genuinely open. §5's role decomposition (execution-result observation, separate from execution-evidence construction/retention) suggests these need not be the same component, by direct analogy to the authorization side's own split between `basis-adapters` (constructs evidence material) and `basis-producer` (retains it and assembles the reference) — a split ADR-0007 justified specifically to avoid "normalization drift" between what was observed and what was recorded. The same drift risk applies to execution: a dispatcher that both dispatches and self-reports what happened has a structural incentive (or at minimum, a structural opportunity) to misreport a failure as a success, which a separated observer-and-recorder pair would at least partially check.

**Should construction and retention be separate responsibilities?** The authorization-side precedent (ADR-0007) argues yes, for the same reason: `basis-adapters` constructs evidence material deterministically and `basis-producer` retains it only after independently confirming the retention succeeded (the "retain-before-mint" invariant). A directly analogous "retain-before-anything-else" discipline for execution evidence would prevent an executor from ever claiming a durable evidence record exists when persistence actually failed — precisely the "execution evidence write failure" failure mode §8's table already names as structurally distinct from every execution-status value.

**Separation of dispatch, evidence construction, and evidence retention is a responsibility-clarity, durability, tamper-boundary, and blast-radius property — not, by itself, a truthfulness property.** These are different things, and this assessment states the distinction directly because the findings above could otherwise be read as implying more than they support. Durably retaining an execution-evidence record in a component separate from the one that dispatched can prove *what was reported* — that a specific, tamper-resistant record exists and has not been altered since it was written. Neither separation nor durability can, by itself, prove that what was reported is *true* — that the device actually did what the record claims. A compromised executor that fabricates a false observation and hands it to an honest, separate evidence-recording component produces a durable, tamper-resistant record of a false observation; the record's integrity says nothing about the observation's truthfulness. Establishing stronger confidence in what actually occurred, as distinct from what was reported, would require an independently trustworthy observation source — a protocol-level acknowledgement from a component the executor does not control, an independent state readback, or some other mechanism this assessment does not design. This distinction — the integrity of the evidence record, versus the truthfulness or authority of the observation recorded inside it — governs every claim about execution evidence's trustworthiness elsewhere in this document, including §12's compromise analysis.

**Is evidence produced before, during, or after execution?** The DNP3/IEC 61850 stateless-control evidence in §9 argues for at least a two-part answer: an *attempt* record should exist before dispatch (so a crash between authorization and dispatch is distinguishable from a crash after — see §14), and a *result* record is necessarily produced after, whenever the protocol yields enough information to produce one at all.

**What happens if execution succeeds but evidence retention fails?** This is not a hypothetical this assessment invents — it is the direct execution-side analogue of the `required`/`optional` evidence-mode distinction ADR-0007 already made for adapter evidence, and the same discipline plausibly transfers: under a "required" execution-evidence mode, an executor that cannot durably retain a result record has failed at something the deployment considers non-negotiable, even though the physical operation itself may have succeeded. What this means operationally (does the executor retry the write? alert an operator? simply log locally and continue?) is not decided by the evidence gathered here, and this assessment does not decide it.

**What is authoritative, self-reported, inferred, or confirmed by independent readback?** These four categories are useful working distinctions for characterizing an execution-observed fact's trustworthiness, but this assessment does not conclude that they map cleanly onto the existing, closed `ProvenanceClassification` enum (`verified`, `gateway_derived`, `trusted_producer_asserted`, `untrusted_caller_asserted`, `configuration_derived`, `unavailable`). `trusted_producer_asserted` currently carries a specific, narrower meaning: a field asserted by an admitted *operation producer* and accepted by the gateway as a trusted-producer assertion, in the authorization-submission context that classification was built for. A future execution role is architecturally distinct from the operation-producer role (§5), and this assessment does not assume executor-observed facts inherit producer-specific provenance semantics merely because both are, in some general sense, self-reported by a trusted component — that would be reusing producer-specific provenance semantics for executor-produced facts prematurely, before architecture has decided whether the two contexts are actually equivalent. Whether the existing six-value vocabulary is sufficient to describe execution-observed facts, whether an existing classification can accurately describe executor-produced observations without conflating two different trust contexts, or whether execution requires its own additive governed provenance concept is exactly the kind of question `operation-producer-and-execution-boundary.md` §7 already flags as a finding for the architecture process. This assessment restates that restraint without narrowing it by informally pre-assigning execution facts to any specific existing value, including `trusted_producer_asserted`; it does not propose a new provenance value, and `basis-schemas` is not modified.

**Likely linkage to existing identifiers.** Restated and extended from §13 below: a future execution-attempt or execution-evidence record would need, at minimum, a reference back to the `AuditEvidence.evidence_id` and/or `GatewayAuditEvent.request_id` it is executing under, exactly as `AdapterEvidenceReference` today references (never embeds) the material `basis-adapters` constructed. Whether it also needs a reference to the specific `AdapterEvidenceReference.reference_id` (to bind execution to the *evidence* the authorization decision was based on, not merely to the decision itself) is an unresolved, genuinely useful question this assessment surfaces without answering, because it bears directly on §6's binding-mechanism question.

**Likely invariant fields, unresolved fields, protocol-specific extension needs, and questions that must be answered before schema publication:**

- Likely invariant, by direct analogy with every existing evidence-reference contract's shape: a `reference_id`-shaped identifier for the execution-evidence artifact itself; a digest of whatever material constitutes "what was observed"; a reference back to the authorization chain (at minimum the audit-evidence ID); a provenance classification.
- Unresolved: the execution-status vocabulary itself (§8); whether validity/freshness metadata belongs on this contract or on a separate binding artifact (§6, §7); whether the contract needs to distinguish dispatch-observation from state-observation as two separate sub-records or one combined one (the KNX "format valid, state unconfirmed" case in §9 argues for keeping them separable).
- Protocol-specific extension needs: per §9, a Modbus exception code, a BACnet error class/code, a DNP3 internal-indications bitfield, an OPC UA `StatusCode`, and similar per-protocol detail cannot be squeezed into one universal field without losing information a deployment might need — the governed-per-protocol-metadata-projection pattern ADR-0007 already established for authorization evidence is the most direct available precedent for how to admit this variation without an unbounded, ungoverned metadata bag.
- Before schema publication: per `ecosystem-contract-inventory.md`'s own governing principle, restated throughout every accepted document this assessment cites, "implementation proves a stable shape" — no execution-evidence contract should be published until a bounded reference implementation (for one protocol, one topology, the same discipline ADR-0008 applied to the producer slice) exists to prove the shape is actually sufficient.

## 11. Credentials and Trust

Five credential categories this assessment inventories, restated from the task's own framing and grounded in what the completed producer slice actually built:

1. **Authorization subject credentials.** Bearer token (OIDC or `basis_local_token`), verified once by `basis-gateway`'s existing `authenticate()` dispatch, independently of the producer's own credential per ADR-0008's "Producer vs. authorization subject" distinction — implemented and proven.
2. **Producer workload credentials.** mTLS client certificate and private key, held by `basis-producer`, per Phase 3 — implemented and proven.
3. **Executor workload credentials, if separate.** Do not exist. No component in the inspected repositories holds, or is designed to hold, a distinct executor identity.
4. **OT endpoint/protocol credentials.** Do not exist anywhere in the inspected repositories, confirmed by direct search — no adapter, and no component in `basis-producer` or `basis-gateway`, holds a Modbus unit-ID authentication secret, a BACnet device password, an OPC UA client certificate for endpoint authentication, an MQTT broker credential, a DNP3 secure-authentication key, or the equivalent for any of the other protocol families.
5. **Trust material required by a protocol.** Varies enormously by family and is, per §9, largely outside what the normalization layer models at all — OPC UA's own protocol includes certificate-based endpoint trust as a first-class concept the adapter explicitly excludes ("No certificate handling. No secure channel"); several of the other eight protocol families (classic Modbus TCP, classic BACnet/IP, KNX bus communication) have no native authentication at all, a fact this assessment states plainly rather than euphemizing, per the task's own instruction not to assume every OT protocol has native authentication.

**Should protocol/device credentials belong to the producer, or only to the execution role?** The evidence in §5's Option A/B analysis argues this is precisely the fork in the road: Option A concentrates them with the producer's existing credentials (incremental widening of an already-accepted custody boundary, per ADR-0010's own reasoning); Option B separates them (stronger credential isolation, at the cost of a new trust boundary). Neither is established as necessary by the evidence gathered here.

**If producer and executor share a process, can credential ownership still be logically isolated?** Partially. Even within one process, nothing prevents structuring the code so that the device-credential-holding component is a distinct, narrowly-scoped module the dispatch logic calls through — the same "logical role, not necessarily a separate deployment unit" principle §2 states as this assessment's own governing constraint. What a single process cannot provide is *failure-domain* isolation: a memory-safety bug or a supply-chain compromise in one logical component within the process compromises every credential that process holds, regardless of how cleanly the code is modularized.

**Does a separate executor need its own workload identity?** If Option B is chosen, yes, by direct analogy: the same reasoning ADR-0008 applied to establishing a distinct producer workload identity (rather than reusing the authorization subject's bearer credential) applies to establishing a distinct executor identity rather than reusing the producer's mTLS certificate for a second purpose it was not scoped for.

**Can producer mTLS identity safely authorize execution handoff?** Not without a deliberate decision to scope it that way, which this assessment does not make. Reusing one credential for two purposes (authenticating to the gateway, and authenticating a handoff to an executor) would need its own admission-scoping analysis at least as careful as ADR-0008's own "exact admission matching... no wildcard, prefix, or case-insensitive matching" discipline, and no accepted document has performed that analysis for a second purpose.

**Would an execution service require an independent admission model?** Plausibly yes, on the same grounds ADR-0008 required a producer-specific admission model rather than reusing the gateway's existing bearer-subject admission for producer identity: a distinct trust class (execution authority, as opposed to submission authority) argues for a distinct, explicit, deployment-owned admission decision, not implicit inheritance from producer trust.

**How are credentials rotated? How are air-gapped credentials handled?** Every operational cost ADR-0008's own "Operational consequences" section documents for the producer's mTLS credential (rotation burden, air-gapped PKI, exact-match naming discipline) applies without modification, and compounds, for any additional credential class this boundary introduces — this assessment does not find evidence that execution credentials would be materially easier to operate than the producer credential already proven costly but tractable.

**How does least privilege apply?** Most directly in the device-credential dimension: whatever holds a device credential should hold only the credential(s) needed for the specific endpoints it dispatches to, not a broad or shared credential covering an entire protocol family or site — though this assessment found no existing mechanism in any inspected repository that would enforce or even express such a scoping constraint today, because no component holds a device credential at all yet.

**How could credential compromise permit bypass of BASIS?** This is the sharpest finding in this section, and the evidence supports stating it plainly rather than softening it:

> If an executor can directly reach an endpoint and possesses sufficient protocol credentials, a compromised executor may be capable of bypassing BASIS policy entirely.

Nothing in the current architecture — and nothing this assessment's evidence suggests a future architecture could fully close — prevents this in software alone. A protocol executor's entire *purpose* is to hold enough capability to reach a device and act on it; that is definitionally also enough capability to reach the device and act on it *without* going through authorization first, if the executor's own dispatch logic is compromised or bypassed. What is an application guarantee and what is a deployment/network guarantee, stated directly:

- **Application guarantee (BASIS can enforce this in software):** the executor does not construct or accept a dispatch instruction except one that carries a valid, gateway-issued disposition binding (§6), and refuses to dispatch anything else.
- **Deployment/network guarantee (BASIS cannot enforce this in software alone; the threat model already draws this exact line for the analogous OS-compromise and network-segmentation exclusions in its §10):** that the executor process itself has not been compromised at a level below its own application logic; that network segmentation prevents an attacker from reaching the OT endpoint by any path other than through the executor; that the device credential is scoped narrowly enough that its compromise does not grant broader capability than the executor legitimately needs.

## 12. Compromise and Bypass Analysis

**Compromised producer.** Could it alter a normalized operation after authorization? No — per §4, the authorization decision is already made and recorded before the producer could alter anything post-hoc; a compromised producer could alter what it submits for evaluation *before* the decision, which is the existing, already-analyzed "rogue integrator" / "compromised adapter" threat the threat model's §4.2 and §6.3 already cover, not a new execution-specific risk. Could it submit repeated requests? Yes, unconstrained today (§7). Could it misuse an `ALLOW`? Only in Option A, where the producer *is* the executor — see the combined-process analysis below. Could it access device credentials? Only if Option A is chosen and the implementation does not logically isolate them (§11). Could it bypass the executor? Not meaningfully distinct from "is the executor" in Option A; in Option B, a compromised producer that cannot forge a valid handoff artifact (per §6) cannot bypass a correctly-implemented executor.

**Compromised executor.** Could it execute without authorization? Only if the binding mechanism (§6) is absent, weak, or bypassable — this is precisely why §6 identifies binding as one of the most important open questions rather than a formality. Could it alter authorized parameters? Only if the binding mechanism does not cover the parameters it would alter — an argument for the binding to cover the *complete* dispatchable operation, not merely an opaque "yes/no" flag. Could it replay operations? Yes, absent the freshness controls §7 discusses, and more easily in a separated (Option B) topology per that section's analysis. Could it fabricate execution evidence? Yes, absent the observer/recorder separation §10 discusses as a partial mitigation — "partial" because a sufficiently compromised executor could still fabricate what it reports having observed, the same residual-risk structure ADR-0007 already accepts for adapter evidence ("hashing does not make a compromised producer trustworthy"). Could it suppress failures? Yes, for the same reason — nothing this assessment found would force an executor to report failures honestly beyond software discipline and the observer-separation mitigation. Could it directly reach endpoints outside expected scope? Yes, unless device-credential scoping (§11) and network segmentation (a deployment guarantee, per §11's closing distinction) both hold.

**Compromised adapter/plugin.** Could it misrepresent protocol semantics? This is the existing, already-analyzed threat model §6.3 threat ("normalization altered so an operation is misrepresented to the kernel"), unchanged by execution's existence — a misnormalized operation produces a wrong authorization decision regardless of whether execution exists downstream of it. Could it construct misleading evidence? Same existing threat, same existing mitigation (containment, not detection, per the threat model's own honest framing). Could it normalize one operation and later execute another? This is new, and specific to execution's existence: if original-operation preservation and authorized-operation binding (§5) do not tightly bind the preserved operation to the *same* normalized request the authorization decision was made against, a compromised or buggy adapter-invocation path could in principle normalize operation X for authorization while a substituted operation Y is later dispatched under that authorization. This is exactly the failure mode §6's binding analysis exists to prevent, restated here as an adapter-specific instance of it.

**Compromised gateway.** Per the task's own instruction, this assessment acknowledges the gateway's existing trust significance without redesigning that boundary. The threat model's own §6.2 analysis (not reproduced here) already establishes that gateway compromise is "the most consequential component compromise, because the gateway is the trust boundary" for the *authorization* side; nothing this assessment found changes that ranking, and if execution is ever bound to gateway-issued artifacts (per §6), gateway compromise would extend to potentially fabricating the execution-binding artifact as well as the authorization decision itself — a direct, mechanical extension of an already-acknowledged risk, not a new category.

**Risks mitigable in BASIS software versus requiring deployment controls, per this assessment's evidence:**

| Risk | Mitigable in BASIS software | Requires deployment control |
| - | - | - |
| Forged authorization-to-execution binding | Yes, if a binding mechanism (§6) is built and enforced | — |
| Replayed disposition | Partially (§7) — process-local state helps same-process topologies; full protection is a harder, still-open problem | Network segmentation reduces the attack surface for replay from outside the intended topology |
| Compromised executor bypassing BASIS entirely via direct device reach | No, not fully | Network segmentation; endpoint ACLs; credential scoping |
| Fabricated execution evidence from a compromised executor | Partially, via observer/recorder separation (§10) | Independent monitoring, out-of-band device-state verification |
| Device credential compromise | Partially, via least-privilege scoping (§11) | Hardware-backed credentials; process isolation; OS-level permissions |
| Compromised gateway fabricating dispositions or bindings | No — this is the existing, unresolved residual risk the threat model already accepts for the authorization boundary | Independent monitoring; the deployment-level integrity controls the threat model's own §9/§10 already name as assumptions BASIS depends on but cannot itself guarantee |

## 13. Correlation Model

Identifiers that exist today, their owning component, and what a future execution-attempt or execution-evidence record would plausibly need to add:

```text
AdapterEvidenceReference.reference_id   (basis-producer, minted, ADR-0007)
    → producer request_id / correlation_id   (basis-producer / caller)
        → gateway CorrelationMiddleware correlation ID   (basis-gateway, always generated)
            → basis-core trace_id   (basis-gateway-generated via injectable factory, embedded by basis-core)
                → basis-core AuditEvidence.evidence_id   (basis-gateway-generated via injectable factory, embedded by basis-core)
                    → GatewayAuditEvent.audit_evidence_id   (basis-gateway, references, never embeds)
                        → authorization disposition
                            ⇢ future execution-attempt identifier   (does not exist)
                                ⇢ future execution-evidence identifier   (does not exist)
```

**Which ID owns which scope.** `reference_id` scopes exactly one adapter-evidence artifact, deployment-locally unique by default (ADR-0007). The gateway's correlation ID scopes exactly one HTTP request to the gateway, unconditionally generated, never caller-influenced. `trace_id` and `evidence_id` scope exactly one kernel evaluation each, generated by the gateway's injectable factory (default `uuid.uuid4()`) and embedded, never generated, inside `basis-core`'s own artifact types. None of these five identifiers today scopes anything beyond the authorization chain — this is the direct, mechanical restatement of §4's central finding, expressed as an identifier-ownership fact rather than a narrative one.

**Whether IDs are generated before or after side effects.** Every identifier in the existing chain is generated before or during the authorization side effect it describes (the gateway generates its correlation ID at request-receipt time, before composition or kernel invocation; `trace_id`/`evidence_id` are generated before the kernel call and passed in). This "generate identifiers ahead of the fact they will describe" pattern is directly reusable for a future execution-attempt identifier, per the "create an execution-attempt record before dispatch" ordering §14 discusses — generating the identifier ahead of the attempt, rather than only upon completion, is what makes a crash between generation and completion detectable rather than silent.

**Which links must be integrity-protected versus which are diagnostic, restated from §6's finding because it belongs equally here.** Today, none of the five existing identifiers is integrity-protected in the sense of being checked at a trust boundary — they are generated, carried, and compared for correlation, but nothing rejects a request or a record because an identifier fails a cryptographic check. `GatewayAuditEvent.audit_evidence_id == audit_evidence.evidence_id` is enforced as a structural invariant at construction time (per the existing gateway module's own docstring, restated in `operation-producer-and-execution-boundary.md` §6), which is a correctness check, not a security control against forgery. Whether a future execution-binding identifier needs to cross the line from diagnostic to security-relevant is exactly the decision §6 already identifies as open and does not resolve here.

**This assessment does not conclude that all future identifiers must collapse into one ID.** Consistent with `operation-producer-and-execution-boundary.md` §6's own restraint on this exact question, applied one layer further down the chain: a future execution-attempt identifier and a future execution-evidence identifier are plausibly distinct facts (an attempt can exist without a completed evidence record, per the crash-consistency scenarios in §14), and forcing them into one identifier would lose that distinction the same way forcing `trace_id` and `evidence_id` into one value would lose the distinction between "this evaluation happened" and "this evidence artifact exists" that the current architecture deliberately preserves.

## 14. Side-Effect Ordering

The producer slice already established, and proved in a working implementation, the principle: **evidence before side effects** — `basis-producer`'s own retain-before-mint invariant (Phase 2A/2B) is exactly this principle applied to evidence retention preceding reference minting, which itself precedes gateway submission.

**How that principle plausibly evolves once execution exists**, stated as candidate ordering rather than codified sequence, per the task's own instruction not to over-specify:

```text
retain authorization-input evidence before requesting authorization   (existing, proven)
    → receive authoritative disposition                                (existing, proven)
        → [candidate] create an execution-attempt record before dispatch
            → perform the side effect (protocol dispatch)
                → [candidate] persist the execution result afterward
```

The two "[candidate]" steps are new, unproven, and exactly the kind of ordering decision this assessment surfaces without codifying, consistent with the task's explicit instruction not to fix this sequence without support. What the existing, proven half of the sequence does establish, by direct precedent, is that **this ecosystem already has a working discipline for "record before act, then confirm the record landed"** — the retain-before-mint pattern — and that discipline is the strongest available anchor for reasoning about the unproven half, without this assessment claiming the unproven half is settled.

**Crash-consistency analysis for each boundary, using the same four states this section's ordering above implies:**

| Boundary | State if a crash happens exactly here | Distinguishable from adjacent states? |
| - | - | - |
| Between disposition and attempt-record creation | Authorized, no execution attempted, no record that one was ever going to be | Yes, if the attempt record's absence is itself checked — an executor restarting after a crash here should find nothing to resume, and correctly conclude "not attempted" per §8's vocabulary |
| Between attempt-record creation and dispatch | Attempt is durably recorded; dispatch never happened | Distinguishable from "not attempted" only if the attempt record itself carries a distinct "dispatch not yet confirmed" sub-state — otherwise a restarting executor cannot tell this case apart from the one below without additional information |
| Between dispatch and result persistence | Device may have acted; the executor's own crash prevents it from ever recording what happened | **Not** distinguishable from "attempt recorded, dispatch never happened" without protocol-level evidence the crash itself destroyed the executor's chance to observe — this is the single worst case in this table, and it is structurally unavoidable for any protocol without independent, executor-external state confirmation (readback) |
| Between result determination and evidence-record persistence | The real-world outcome is known to the (about-to-crash) process but never durably recorded | Distinguishable from the row above only if partial progress (a result was computed) is itself durably marked before the final record write completes — a finer-grained durability discipline than the three-state model above assumes, and not established as necessary by this assessment's evidence |

**The model must make these distinguishable rather than pretending all failures are atomic** — restated as this section's governing conclusion because the table above demonstrates, concretely, that at least one of the four boundaries (dispatch-to-result-persistence) is *not* cleanly distinguishable from its neighbor using only the ordering primitives available today, for any protocol lacking independent state readback. This is not a defect in the ordering principle; it is a structural limit that a candidate execution-evidence design must acknowledge honestly (per §10's provenance-classification discussion) rather than paper over with false atomicity.

## 15. Read vs. Write / Control Semantics

The existing, governed action vocabulary — `read`, `write`, `execute`, `browse`, `subscribe`, per `docs/glossary.md`'s **Action** entry and `docs/architecture/action-vocabulary.md` — is not modified, extended, or reinterpreted by this assessment, consistent with the task's own instruction to use existing governed action semantics rather than invent a new taxonomy.

**Does execution architecture need to distinguish these categories?** The evidence in §7 and §9 argues yes, functionally, even without a new taxonomy: a replayed `read` and a replayed `write`/`execute` carry structurally different risk (§7), and the protocol table in §9 shows that `subscribe`-shaped operations (MQTT topic subscriptions, IEC 61850's `ENABLE_REPORTING`/`ENABLE_GOOSE`) have execution semantics (ongoing delivery, not a single dispatch-and-confirm event) that differ materially from a single `write`/`execute` dispatch. This assessment does not conclude that the existing five-verb vocabulary needs a new member — the existing verbs already carry enough distinction (a `read` and a `write` are already different actions in every policy and audit record today) — but it does conclude that a future execution-lifecycle design should not assume every authorized action shares one execution shape merely because they share one authorization pipeline.

**Multi-step operations, discovery/browse, and publishing**, per the protocol evidence already gathered: `browse` (an OPC UA concept the current adapter explicitly excludes — "No endpoint discovery") and `subscribe` (MQTT, IEC 61850's reporting/GOOSE enable operations) both have execution semantics that look more like "establish an ongoing state" than "perform a discrete action" — a distinction §9's protocol table already surfaces without this section needing to restate it in full.

**This assessment does not invent a new canonical action vocabulary** and explicitly declines to propose one, per the task's instruction; it records the finding that execution risk varies by action category as a fact for a later architecture decision to weigh, not as a proposal to act on now.

## 16. Deployment Topologies

**Same-process producer + executor (Option A, expanded operationally).** Trust: highest concentration, lowest boundary count. Credentials: producer mTLS certificate, authorization-subject credential, and (if adopted) device credentials, all in one process — an incremental widening of the credential custody boundary ADR-0010 already accepted for `basis-producer`. Latency: lowest, no network hop between authorization and dispatch. Failure isolation: lowest — a crash anywhere in the process affects the whole pipeline, per §14's crash-consistency analysis. Air-gap suitability: highest — no second authenticated network boundary to provision for isolated deployments, directly consistent with ADR-0008's own stated preference for mechanisms that do not require external connectivity. Protocol library constraints: the process must link whatever protocol stack each adapter's real-world dispatch counterpart requires, which may impose dependency or licensing constraints `basis-adapters`' own normalization-only design has so far avoided entirely (every adapter's docstring lists what it deliberately does *not* link — pymodbus, asyncua, paho-mqtt, an MMS stack — and Option A would require linking exactly those, for real). Operational complexity: lowest, one deployable artifact. Observability: simplest, one process's logs and metrics cover the whole chain. Blast radius: highest for a single compromise, per §12's compromised-executor analysis.

**Separate producer and executor processes (Option B, expanded operationally).** Trust: a new, explicit boundary, requiring the same rigor ADR-0008/ADR-0009 already applied once. Credentials: cleanly separable, at the cost of a second credential-lifecycle burden (§11). Latency: higher, by whatever the handoff transport adds. Failure isolation: better — an executor crash does not necessarily take down the authorization-submission path, and vice versa. Air-gap suitability: worse than Option A by direct extension of ADR-0008's own operational-cost analysis (a second authenticated boundary to provision and maintain offline). Protocol library constraints: isolated to the executor process, which may be a genuine benefit if different protocol families have conflicting dependency requirements — this is the one dimension where Option B has a clear, evidence-grounded advantage over Option A. Replay/binding requirements: strictly harder, per §6 and §7. Observability: requires correlating two processes' records, a real but manageable cost given the correlation infrastructure §13 already inventories. Blast radius: lower per single compromise, higher aggregate trust-boundary count to secure.

**Embedded / constrained deployment.** `operation-producer-and-execution-boundary.md` §9 already analyzes this topology for the producer role alone ("normalization, an authorization client, and execution all run close to an isolated OT endpoint... for example, on a single-board controller with no separate gateway reachable"); extending it to include execution is a natural continuation of the same rationale (air-gapped deployments, strict resource constraints) rather than a new topology this assessment discovers. Its risk profile is Option A's, intensified: the constrained device concentrates every role and every credential this assessment discusses, which the existing document already flags directly ("cryptographic protection of the credential material at rest becomes proportionally more important the more roles a single constrained device combines").

**Centralized producer with distributed executors.** Included only because it is a credible future topology given the ecosystem's own stated ambitions (multi-site OT deployments, per the glossary's **Operational Resilience** and **Edge System** entries, and the threat model's own §11 open question on "multi-site trust relationships"). It is structurally Option B, replicated per site, and inherits every one of Option B's costs multiplicatively rather than additively — this assessment does not find evidence that centralization changes the trust-boundary analysis in kind, only in count.

**BASIS should prefer the smallest architecture that can preserve the required guarantees**, restated as this section's governing conclusion because it is the one normative-sounding sentence in the task's own framing this assessment can support directly from evidence: nothing gathered here shows that a distributed, multi-process execution topology is required by any deployment scenario this ecosystem's own documents already commit to (OT environments favor fewer moving parts and fewer trust boundaries, per the threat model's own repeated emphasis on boundary ownership as "the deepest security property in the architecture"), and Option A's costs are, on this evidence, both lower and better-precedented (by ADR-0010's own credential-concentration reasoning) than Option B's.

## 17. Historical PoC Lessons — Non-Normative

The separate `basis-poc` research repository was not mounted in the working environment and was not inspected directly; this section draws only on `basis-architecture`'s own white paper, Section 06 ("The BASIS Proof-of-Concept"), which documents the PoC's design and findings without being the PoC's source code. Findings below are labeled non-normative per the task's own instruction and inform this assessment without governing it.

**What was executed, where, with whose credentials.** The PoC's protocol adapter layer (an MQTT adapter for the HVAC simulator, CO2/occupancy sensors, and a data-center resource; a Modbus TCP adapter for a chiller and pump, simulated as in-memory registers) dispatched authorized commands directly from the same monolithic FastAPI process that also performed identity resolution, policy evaluation, and enforcement — Section 06's own "Key Architectural Observation" states this collapse directly: "identity resolution, policy evaluation, and enforcement" were co-located "in a single process," which by extension included the dispatch step as well. No distinct execution credential existed; the PoC used development-grade, static credentials throughout, explicitly disclaimed as inappropriate for anything beyond the research environment.

**How authorization and execution were coupled.** Tightly — the PoC's `require_action()` dependency, attached to every endpoint, gated dispatch directly; there was no separate disposition-to-dispatch handoff of the kind this assessment's §6 analyzes, because there was no process boundary for such a handoff to cross. This is directly relevant to Option A's evidence base: the PoC is existence proof that a same-process authorization-to-dispatch pipeline is buildable and was, in fact, built once already — though at a scale and fidelity (five simulated resources, no real protocol stacks) far short of what a production reference implementation would need to validate.

**What result semantics existed.** The PoC's `DualAuditStore` recorded two events per command on the allow path: one for the authorization decision, one for "the outcome of the command dispatch." Section 06's own "Key Architectural Observation" on this point states the separation was "architecturally intentional, not an implementation detail," reasoning explicitly that "an authorization event without a corresponding dispatch event identifies a command that was approved but did not complete" — this is, in substance, the same authorization/execution-evidence separation §10 of this assessment argues for, independently arrived at, on different evidence, roughly the same conclusion. This convergence is worth noting as a weak corroborating signal, not as proof — the PoC's dual-event design was never exercised under real failure conditions (Section 06 records no connection errors, timeouts, or malformed responses were ever encountered against the simulated resources).

**What assumptions were acceptable for the PoC but are not acceptable now.** Simulated resources with no real protocol-level failure modes; a single-container, non-distributed deployment with no operational-separation validation; static, non-rotating credentials; no replay protection of any kind; no distinction between a protocol-level rejection and a local pre-dispatch failure (Section 06 does not record the PoC's dispatch-event structure distinguishing these, and its own "What the PoC Did Not Demonstrate" section explicitly excludes "real protocol handling" — "connection errors, protocol-level timeouts, malformed responses... were not encountered and not handled"). None of these gaps should be read as criticism of the PoC, which the white paper itself frames throughout as a deliberately bounded, breadth-first research artifact — but they are direct evidence that the PoC's dispatch behavior, however architecturally suggestive, was never tested against the specific failure taxonomy §8 of this assessment develops, and should not be treated as validating that taxonomy's sufficiency.

**What should not be carried into production architecture, stated plainly.** The PoC's collapse of authorization and dispatch into one undifferentiated code path (no distinct disposition-to-dispatch handoff, no binding artifact, no freshness check) should not be read as evidence that Option A requires no binding mechanism at all — the PoC never needed one because it had no adversarial model requiring it, and it explicitly disclaims security hardening as out of scope for its own results ("the implementation has not been reviewed for production security requirements and should not be treated as a reference for secure configuration"). Citing the PoC's simplicity as justification for a production Option A implementation skipping §6's binding analysis would be exactly the "PoC behavior copied into architecture merely because it worked in a demonstration" pattern the task explicitly warns against.

## 18. Option Comparison

Evaluated only for the options that survived §5's analysis — same-process (Option A), separate-process (Option B), and the protocol-specific-executor question (Option C, a placement question orthogonal to A/B rather than a third row). Narrative tradeoffs, not numeric scores, per the task's own instruction against fake precision.

| Dimension | Same-process logical executor (Option A) | Separate executor boundary (Option B) | Protocol-specific execution model (Option C, layered on A or B) |
| - | - | - | - |
| Trust boundaries | Fewest — reuses the existing producer-to-gateway boundary only | One new boundary, requiring ADR-0008/ADR-0009-level rigor to build correctly | No new boundary of its own; inherits whichever of A/B it is layered on |
| Credential isolation | Weakest — device credentials join an already-concentrated process, mitigated only by code-level modularity (§11) | Strongest — device credentials never need to touch the producer's authorization-side credentials at all | Neutral — a per-protocol split does not by itself change credential isolation, though it could permit per-protocol credential scoping if combined with B |
| Authorization binding complexity | Lowest — in-process state can plausibly serve as the binding (§6) | Highest — requires a genuine portable, verifiable artifact | Neutral — orthogonal to binding complexity, which is governed by A/B, not by protocol count |
| Replay risk | Lower — no second network hop to replay across (§7) | Higher — a captured handoff artifact is replayable from an unintended position | Neutral |
| Failure isolation | Weakest — one process failure affects the whole authorization-to-dispatch chain | Strongest — an executor crash need not affect the producer's own authorization-submission path | Improves failure isolation specifically for protocol-library conflicts (a crash in one protocol's stack need not affect another's), regardless of A/B |
| Protocol flexibility | Weaker — the producer process must link every protocol stack it dispatches for, risking dependency conflicts across nine families | Stronger, if paired with per-protocol executor processes | This is Option C's core evidence-grounded advantage, and it is realizable under either A or B if "same-process" is read per-protocol rather than ecosystem-wide |
| Air-gap suitability | Strongest — fewest authenticated boundaries to provision offline, consistent with ADR-0008's own preference | Weaker — a second boundary's credential lifecycle must also work offline | Neutral, inherited from A/B |
| Deployment complexity | Lowest — one artifact | Higher — at least two artifacts, two release cadences | Higher still if realized as genuinely separate per-protocol deployables; comparable to A if realized as per-protocol dispatch branches within one process |
| Testing complexity | Lower — one process's test suite, extending `basis-producer`'s existing layered-error-propagation discipline | Higher — requires testing the handoff boundary itself, in addition to each side independently | Higher per protocol added, regardless of A/B, simply because each protocol family's failure taxonomy (§9) differs |
| Evidence clarity | Simpler chain of custody for evidence (§10), but weaker independent-observer property against a compromised process (§12) | Cleaner observer/actor separation, if the executor and the evidence-recorder are themselves kept distinct (§10) | Neutral to slightly positive — per-protocol evidence shapes (§9's closing point) are easier to keep honest when each protocol's executor is a bounded, independently reviewable unit |
| Current architecture fit | Strong — extends `basis-producer`'s existing "compose already-tested collaborators into one bounded pipeline" pattern with minimal structural change | Weaker fit today — no accepted document has yet defined the handoff contract this option requires, unlike the producer-to-gateway boundary, which took four ADRs to define properly | Fit depends entirely on which of A/B it is layered on; the multi-protocol-adapter precedent in `basis-adapters` itself (nine independent implementations under one shared `normalize()` contract) is the strongest existing architectural precedent for this pattern generally |

## 19. Decision Inventory

### Findings

The repository evidence gathered in this assessment makes the following clear now:

- Authorization and execution are distinct lifecycle stages, and every accepted document this assessment cites treats that distinction as load-bearing, not incidental — confirmed, not merely asserted, by the completed producer slice's own deliberate `STOP` before any execution code (§1, §4).
- Execution evidence cannot be merged into authorization evidence without destroying information the architecture already depends on preserving — confirmed by `GatewayAuditEvent`'s own deliberate omission of an `enforcement_status` field (§10).
- A logical execution role exists regardless of process placement, and decomposes into at least four sub-responsibilities (original-operation preservation and authorized-operation binding, dispatch, result observation, evidence construction/retention) that are not all equally separable (§5).
- Protocol-neutral execution status must tolerate genuine uncertainty as a first-class outcome, not an edge case — DNP3 and IEC 61850's own adapter docstrings state this about their own stateless select/operate model directly, in nearly identical language, independently of this assessment (§8, §9).
- Same-process execution is measurably better-precedented by existing accepted architecture (ADR-0010's credential-concentration reasoning, `basis-producer`'s existing pipeline-composition pattern) than separate-process execution, which has no equivalent existing precedent to build from (§5, §16, §18).
- A compromised executor with direct device reach and sufficient protocol credentials can bypass BASIS policy entirely, and this is not fully closable by software alone under any topology this assessment evaluated (§11, §12).
- Nothing in the current architecture requires inventing a new signed execution token; the existing correlation and audit infrastructure is a plausible sufficient foundation for a same-process binding mechanism specifically, though not demonstrated sufficient for a cross-process one (§6).

### Open Questions

Questions this assessment surfaces and does not resolve, because resolving them requires architectural judgment this document is not authorized to exercise:

1. Is authorization-to-execution binding required at all for a same-process (Option A) deployment, or does process-local trust make it unnecessary? (§6)
2. If a binding mechanism is required, what artifact carries it — the existing `AuditEvidence`/`GatewayAuditEvent` pair, referenced by ID, or a new, purpose-built artifact? (§6, §10)
3. What freshness model applies to a pending disposition — wall-clock expiry, process-local monotonic validity, both, or neither, and how does the answer change for air-gapped deployments? (§7)
4. Does policy change after authorization invalidate a pending execution, and if so, how is that detected? (§7)
5. Is the five-state execution-status sketch sufficient, or does it need the refinements §8 identifies (separating local-rejection from remote-rejection; separating "no ack primitive" from "ack didn't arrive")? (§8)
6. Should execution-status vocabulary vary by action category (read vs. write/control vs. subscribe), and if so, how much? (§8, §15)
7. Who owns device/protocol credentials — the producer (Option A), a distinct executor (Option B), or a topology-dependent answer? (§11)
8. Does an executor need its own workload identity distinct from the producer's, and under what admission model? (§11)
9. Should execution-evidence construction and retention be separate responsibilities, mirroring the authorization side's `basis-adapters`/`basis-producer` split, or can a bounded reference implementation combine them safely? (§10)
10. What is the minimum durable "attempt record before dispatch" mechanism needed to make the crash-consistency states in §14 distinguishable, and is that minimum achievable for every protocol family in §9, or only some?
11. Does the ecosystem's existing six-value `ProvenanceClassification` enum suffice for execution-observed facts, or is a new value required — and if new, what precisely does it mean? (§10)
12. Should a future execution-evidence contract reuse the existing per-protocol-metadata-projection pattern ADR-0007 established for authorization evidence, or does execution evidence's greater per-protocol variability (§9) argue for a different extension mechanism?

## 20. ADR Recommendation

**Is there enough evidence to write an execution-model ADR?** Partially. There is enough evidence to write an ADR selecting a *default deployment topology* (same-process, per §5, §16, §18's convergent findings) and stating the *governing invariants* execution must preserve (§4's stop-point facts, §6's binding requirement in principle, §8's honesty-about-uncertainty requirement). There is not yet enough evidence to select a specific binding *mechanism*, a specific freshness *model*, or a specific execution-evidence *contract shape* — each of those needs its own normative architecture specification following the ADR, and, only where a specific implementation question cannot responsibly be settled from architecture alone, a bounded technical spike.

**This is not a circular dependency, and an earlier draft of this assessment mischaracterized the producer boundary's own history in a way that made it read as one.** ADR-0008 selected mutual TLS and authorized a bounded producer reference slice *before* that slice was implemented — the reference implementation that later validated ADR-0008's choices was downstream of the decision, not a precondition for making it. ADR-0010 established `basis-producer` as the permanent operation-producer-runtime repository and authorized its next implementation phase before the complete five-phase producer slice existed; it drew on the gateway-side mTLS boundary Phase 1B had already proven as supporting evidence, but it did not wait for `basis-producer`'s own implementation to validate the repository-placement decision itself. The pattern this assessment recommends for the execution boundary is the one ADR-0009 demonstrates most directly: architecture selects a direction first (ADR-0008 chose mTLS); a narrow technical spike tests a specific, otherwise-unresolvable implementation question the architecture could not responsibly settle on its own (Phase 1A tested whether direct application-level certificate exposure was viable, and found it was not — Outcome B); and only then does a further architecture decision (ADR-0009) resolve what the spike's answer requires. Applied here: the execution-model ADR and its supporting specification(s) come first; a bounded technical spike, if one proves necessary, tests a specific implementation question those decisions could not responsibly settle from architecture alone; and the bounded execution reference slice — the analogue of the producer program's Phase 2A through Phase 5 — follows the architecture, rather than preceding or substituting for it.

**Does the topic require one ADR or several tightly related decisions?** Several, by direct analogy with how the producer boundary itself required four (ADR-0007 for evidence construction, ADR-0008 for authentication/admission, ADR-0009 for the transport topology gate ADR-0008's own bounded slice surfaced, ADR-0010 for permanent placement). This assessment recommends the execution boundary follow the same discipline rather than attempting one omnibus ADR: a first ADR should establish topology default and governing invariants (what this assessment could support today); a second, narrower ADR (or a normative specification, if the binding mechanism proves non-trivial the way mTLS-transport did) should resolve the binding mechanism — informed, where a specific implementation question cannot responsibly be settled architecturally, by a bounded technical spike for exactly one protocol, on the same "REST first, because it minimizes unrelated protocol complexity" reasoning ADR-0008 already used successfully, with the bounded reference implementation that puts the resolved mechanism into practice following afterward, not preceding it.

**Is a normative architecture specification also required?** Likely yes, for at least the execution-lifecycle vocabulary (§8) and the binding mechanism (§6), given the precision the protocol evidence in §9 shows is needed to avoid the vocabulary lying by omission — this mirrors how `adapter-evidence-construction-semantics.md` existed as a dedicated specification alongside, not instead of, ADR-0007.

**What should the ADR decide?** At minimum: that a logical execution role exists and is architecturally distinct from the operation-producer role regardless of process placement (already true today; the ADR would make it explicit and binding); a default topology recommendation (same-process, per this assessment's findings) with an explicit acknowledgment that other topologies remain architecturally possible for deployments whose protocol-library or credential-isolation needs argue otherwise; the governing invariants execution must never violate (no dispatch before disposition, no dispatch without a valid binding once one is defined, authorization evidence and execution evidence remain permanently distinct artifacts); and the decision gates that remain open pending the normative specification work, and any bounded technical spike, this ADR authorizes downstream of itself.

**What should deliberately remain implementation-defined?** The specific binding-artifact encoding; the specific freshness window or mechanism, if any; the exact execution-evidence field shape; and per-protocol dispatch mechanics for any protocol beyond whichever one a first reference implementation targets — each of these is exactly the kind of decision `ecosystem-contract-inventory.md`'s "implementation proves a stable shape" principle argues should follow evidence, not precede it.

**Recommended next sequence, refined during architect review to remove a circular reference-implementation-before-ADR dependency an earlier draft implied:**

```text
this discovery assessment
    → architect review
        → execution-model ADR (topology default, governing invariants)
            → normative architecture specification(s) sufficient to define
              the bounded execution slice (binding mechanism,
              execution-lifecycle vocabulary)
                → [only where needed] a bounded technical spike testing a
                  specific implementation question the specification(s)
                  could not responsibly settle from architecture alone
                    → architecture refinement or an additional ADR, if the
                      spike exposes a genuine architectural constraint
                        → repository-specific implementation planning
                            → bounded execution reference slice
                                → conformance, demonstration, and review
                                    → shared schema publication, only once
                                      a stable cross-repository contract
                                      shape is actually established
```

This assessment does not begin the implementation plan beyond identifying, in §19's decision table, its prerequisites.

**Recommendation discipline, applied to this assessment's own leading option.** The evidence currently favors a same-process default for the first bounded reference implementation specifically — lower binding complexity, stronger existing architectural precedent, better air-gap fit, and a materially simpler path to a working reference implementation the ecosystem could actually build and learn from, the same way REST-as-first-protocol served the producer slice. This appears to minimize both the number of new trust boundaries the ecosystem must design correctly on the first attempt and the distance between what already exists (`basis-producer`'s proven pipeline-composition pattern) and what a reference implementation would need to add. It does not follow that every future deployment must use this topology — Option B's protocol-flexibility and failure-isolation advantages (§18) are real and evidence-grounded, and a deployment with strong reasons to isolate device credentials from producer credentials, or to isolate one protocol's library dependencies from another's, has a legitimate case for it. The evidence does not make alternatives to same-process clearly untenable; it makes same-process the lower-risk starting point for the first reference implementation specifically, which is a narrower and more defensible claim.
