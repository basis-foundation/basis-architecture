# ADR-0014: Minimum Execution-Evidence Semantics

## Status

Accepted

## Context

[ADR-0012](0012-authorization-to-execution-binding.md) — Accepted — resolved Gate 1 for the same-process first-reference topology: a same-process authorization-to-execution binding record, created by the operation-producer role before gateway submission and verified by the protocol-executor role immediately before dispatch, establishes by content-based digest comparison that the operation about to be dispatched is unchanged from the operation whose normalized semantics received the authoritative permitting disposition. ## Problem

Once an operation has received the authoritative permitting disposition and entered the protocol-execution/pre-dispatch boundary, ADR-0013's pre-dispatch model (its Decision 2) resolves it one of two ways: toward successful binding verification followed by a committed dispatch — an execution attempt whose attempt-outcome and resulting-state-verification values the protocol-executor role has observed — or toward a pre-dispatch `NOT_ATTEMPTED` outcome, which is not itself evidence that binding verification succeeded, and which for a Case C outcome specifically may be exactly the fact that binding verification failed (no binding record found, digest mismatch, non-permitting correlated disposition, already-consumed binding, verification error). Once that model has resolved either way, what minimum evidence semantics are required so BASIS can truthfully record that attempt without confusing it with authorization evidence, kernel evidence, gateway audit facts, adapter evidence, or a future identity-evidence contract? The answer must state what counts as execution evidence at all; which logical role observes it, which constructs the durable record, and which retains it, and whether those are the same role; the minimum facts such a record must preserve to be honest rather than merely present; how it correlates to the authorization disposition, the ADR-0012 binding record, the ADR-0013 execution attempt, the gateway correlation ID, the kernel `trace_id`/`evidence_id`, the adapter evidence reference, and prior attempts in a retry sequence; how it relates to ADR-0013's three axes, including defining the evidence-durability axis ADR-0013 deliberately left open; what evidence durability means and how its failure is represented without rewriting what actually happened; which facts are authoritative observations and which are derived correlation facts only; whether any of `basis-core`, `basis-gateway`, `basis-adapters`, or `basis-schemas` gains new responsibility; whether schema publication is authorized now or remains deferred; and what remains open for implementation planning now that this ADR is accepted.

The answer must not, in the course of settling any of the above, silently resolve the broader replay/freshness question ADR-0012 and ADR-0013 both deliberately left open, must not treat `ALLOW` as proof of execution, must not let execution evidence nest inside or overwrite `AuditEvidence` or `GatewayAuditEvent`, and must not assign new implementation responsibility to a repository whose current non-responsibilities are load-bearing architecture rather than incidental scoping.

## Decision

**ADR-0014 defines the minimum execution-evidence semantics required before BASIS can plan a bounded protocol-execution implementation.** It defines what execution evidence is and is not; assigns observation to the protocol-executor role (restating ADR-0013 Decision 14, not reopening it), construction to a distinct logical execution-evidence-producer role, and retention to that same role for the first bounded reference slice while leaving durable-storage shape to implementation planning; fixes the minimum facts, both observational and correlational, an execution-evidence record must carry; defines the evidence-durability axis ADR-0013 left open, as a minimal three-value shape rather than a schema; states which facts are authoritative and which are diagnostic correlation only; states plainly that no existing repository gains implementation responsibility from this decision; declines to authorize schema publication now; narrows nothing further about replay/freshness beyond what ADR-0012 and ADR-0013 already narrowed; and states what remains open. It does not define a JSON Schema, protobuf, or OpenAPI contract, does not select field names or serialization, does not create an implementation plan, and does not authorize protocol execution.

## Execution Evidence Definition

**Execution evidence is the record of what the protocol-executor role truth-owns and actually observed about a single pre-dispatch record once that record exists (ADR-0013 Decision 2) — either the attempt-outcome and, where meaningful, resulting-state-verification values for an execution attempt that reached dispatch, or the attempt-outcome value and boundary-local failure cause for a pre-dispatch execution-boundary failure that record itself resolves to — together with the minimum correlation facts (below) tying that record to the authorization chain and to whatever ADR-0012 binding-record facts actually exist for it, plus an evidence-durability value describing the record's own retention outcome.** This generic definition deliberately does not assume that every execution-evidence record describes both an attempt outcome and a meaningful resulting-state-verification value, that a binding record necessarily existed or was found, or that an execution attempt necessarily came into existence — none of those are true across every case this ADR covers (the case list immediately below, and **Minimum Evidence Facts**, further below, state exactly what does and does not hold per case). This ADR distinguishes, and requires a future implementation to distinguish, two states of the same concept rather than treating "execution evidence" as synonymous with "durable record" throughout: an **execution-evidence candidate** is the record while it exists only in process memory, before a retention attempt for it has succeeded; **durable execution evidence** is that same record once a retention attempt has actually succeeded (**Evidence Durability and Persistence Failure**, below). A retention attempt that fails leaves an execution-evidence candidate that is not durable execution evidence — it does not retroactively stop being a candidate, and this ADR does not describe a failed retention attempt as having produced a durable record of its own failure. Where this ADR uses "execution evidence" without qualification, it means the concept generically, independent of which of the two states a specific record is currently in; where the distinction matters, this ADR says "candidate" or "durable" explicitly.

Execution evidence — as a candidate, and as durable evidence if retention succeeds — is produced for exactly two cases, stated separately because ADR-0013's pre-dispatch model (its Decision 2) makes them truthfully different facts about truthfully different objects, not the same fact recorded twice:

1. **For an execution attempt that reached dispatch** — that is, for which ADR-0013's pre-dispatch record resolved to a committed dispatch and an execution attempt began to exist (ADR-0013 Decision 2) — execution evidence records what the protocol-executor role observed about that attempt: its attempt-outcome and resulting-state-verification values.
2. **For a pre-dispatch execution-boundary failure** — any boundary-local condition, arising after the pre-dispatch record already existed, that prevents dispatch from ever being committed to (ADR-0013 Decision 2's Case C) — execution evidence records the fact that this failure was caught, before dispatch, against a pre-dispatch record that already existed when the failure occurred: ADR-0013 Decision 2 requires the protocol executor to create that record immediately upon entering the pre-dispatch boundary, strictly before binding verification begins, so any Case C failure always has an already-existing record to resolve rather than needing one invented after the fact (ADR-0013 Decision 2's Case C specifically — never Case B, where record creation itself failed and no record ever existed; see below). Case C is not limited to binding-verification failures: it also covers another protocol-executor-local pre-dispatch condition arising after the record was created and before dispatch is committed to — an endpoint unreachable before any bytes are sent, a transport/connection timeout before dispatch, or another executor-local pre-dispatch condition that prevents dispatch after the context exists. **A binding-verification failure under ADR-0012's Failure Semantics (no binding record found; digest mismatch; non-permitting correlated disposition; already-consumed binding; verification error) is an especially security-relevant subset of Case C, not the whole of it: it is exactly the substitution/mutation threat ADR-0012 exists to catch, and this ADR requires a binding-verification-failure record to retain its binding-specific failure facts (Minimum Evidence Facts, below) in addition to, not instead of, the facts every Case C record carries.** Durably recording that any Case C failure was caught is a fact this architecture should not discard merely because dispatch never occurred. **This record describes a pre-dispatch execution-boundary failure associated with that already-existing pre-dispatch record — it must never be labeled, serialized, or otherwise represented as describing an execution attempt that reached dispatch, because, per ADR-0013 Decision 2, no execution attempt exists until dispatch is committed to, and none existed in this case.**

It is not produced for a `NOT_ATTEMPTED` outcome caused by conditions upstream of the protocol-executor role entirely — `DENY`, evaluation failure, producer authentication or admission failure, producer-only context rejection, or gateway unavailability (ADR-0013 Decision 2's Case A: the protocol executor is never invoked for these, and no pre-dispatch record is ever created for the execution-evidence producer role to attach a record to) — because those facts already have an authoritative record (`GatewayAuditEvent`, `AuditEvidence`) produced by the roles that actually observed them, and this ADR does not require the execution-evidence producer role to duplicate, re-derive, or independently attest to a fact it did not itself observe.

**It is equally not produced for a Case B `NOT_ATTEMPTED`** — the protocol executor entered the pre-dispatch boundary, but creation of the required pre-dispatch record itself failed (ADR-0013 Decision 2). This ADR does not invent an execution-evidence record that references a pre-dispatch record for Case B: no record ever came into existence, so there is nothing for case 2's correlation facts (**Minimum Evidence Facts**, below) to describe or reference, and constructing one regardless would misrepresent a record that never existed as though it had. The fact that record creation failed is itself covered by ADR-0013's own fail-closed requirements (ADR-0013 Decision 16) as a lifecycle fact; this ADR does not additionally require the execution-evidence-producer role to construct a durable evidence record for it.

**The resulting architectural rule, stated plainly:**

```text
Case A            → no execution-evidence candidate
Case B            → no execution-evidence candidate
Case C            → execution-evidence candidate
dispatch reached  → execution-evidence candidate
```

This preserves execution-boundary lifecycle facts the protocol executor actually owns and observed, without duplicating upstream authorization facts (Case A) or inventing a record for a creation failure that left nothing to correlate against (Case B).

Execution evidence is, by definition and without exception:

- **not authorization evidence** — it does not exist until after `ALLOW` and after binding verification is attempted, restating ADR-0011 Decision 11 and ADR-0013 Decision 11 without weakening either;
- **not a kernel artifact** — `basis-core`'s `OperationAwareDecisionResponse`, `EvaluationTrace`, and `AuditEvidence` remain complete and immutable the moment the kernel produces them; execution evidence never mutates, reinterprets, replaces, or nests inside any of the three;
- **not a gateway audit fact** — `GatewayAuditEvent` records the gateway's own enforcement-boundary facts and deliberately has no `enforcement_status` field; execution evidence is never merged into it, and this ADR does not add one;
- **not adapter evidence** — `AdapterEvidenceReference` records what `basis-adapters` normalized and preserved before authorization; execution evidence may reference it by identifier (Correlation Model, below) but never absorbs, widens, or repurposes it;
- **not identity evidence** — the future `IdentityEvidenceReference` contract, not yet produced by `basis-identity` (`operation-producer-and-execution-boundary.md` §12), describes the initiating subject; execution evidence describes what happened at the protocol boundary, a structurally unrelated fact this ADR does not conflate with subject identity even where both might eventually correlate to the same operation.

```text
authorization evidence   →  what BASIS decided, before execution existed to describe
execution evidence       →  what the protocol-executor role observed, after dispatch was attempted
                             (or, narrowly, after a Case C pre-dispatch execution-boundary
                             failure against an already-existing record — above)

execution evidence is never a patch, an update, a completion, or a
reinterpretation applied to authorization evidence — it is a later,
separate, referencing fact appended to the same correlation chain.
```

## Observation, Construction, and Retention Ownership

**Observation.** Within the scope this ADR ever constructs evidence for — an execution attempt that reached dispatch (case 1), or a pre-dispatch execution-boundary failure once a pre-dispatch record already existed to fail against (case 2; ADR-0013 Decision 2's Case C — never Case B, where record creation itself failed and no record ever existed to construct evidence against; **Execution Evidence Definition**, above) — the protocol-executor role is the sole truth-owning observer of the attempt-outcome value, the specific boundary-local failure cause for case 2 (**Minimum Evidence Facts**, below), and, where meaningful (ADR-0013 Decision 5), the resulting-state-verification value an execution-evidence record describes, restating ADR-0013 Decision 14's boundary-entered scope without reopening it. This ADR never requires execution evidence for a pre-boundary `NOT_ATTEMPTED` (ADR-0013 Decision 2's Case A), exactly because the protocol executor never observes anything for that case (ADR-0013 Decision 14) — that fact already belongs to, and is already recorded by, whichever upstream role produced it, and this ADR does not require the execution-evidence-producer role to duplicate, re-derive, or independently attest to a fact the protocol executor never saw (**Execution Evidence Definition**, above). This ADR decides nothing new about observation ownership; it exists here only because construction and retention cannot be assigned without first restating whose observation they are permitted to act on.

**Construction.** **A distinct logical execution-evidence-producer role constructs the execution-evidence record from the protocol-executor role's observations and the minimum correlation facts named below.** This is the recommended default this ADR adopts, justified primarily by responsibility clarity rather than by any truthfulness or verification guarantee: it gives construction semantics — what facts get assembled into a record, and how — an explicit owner distinct from the protocol-executor role's dispatch and observation responsibilities; it gives retention outcome (**Evidence Durability and Persistence Failure**, below) an explicit owner as well, rather than leaving it implicit in whichever role happens to also dispatch; it prevents dispatch semantics and evidence-record semantics from collapsing into one undifferentiated responsibility, mirroring, one layer further down the chain, ADR-0011 Decision 2's "same-process does not mean same responsibility" principle; it preserves future separability — a later topology could relocate construction or retention without redesigning which facts each role owns, because the ownership boundary is already explicit; and it gives a future separated deployment a clear durability and blast-radius boundary to build from — restating, and adopting without weakening, the discovery assessment's own framing (§10) of this separation as "a responsibility-clarity, durability, tamper-boundary, and blast-radius property."

The discovery assessment's §10 finding also observes, as a secondary point this ADR does not treat as its primary justification, that "a dispatcher that both dispatches and self-reports what happened has a structural incentive (or at minimum, a structural opportunity) to misreport a failure as a success." This ADR does not lean on that observation as a security control: the same §10 finding states directly, in the same breath, that this separation "is... not, by itself, a truthfulness property," and this ADR adopts that restraint without weakening it — it does not claim that a logically distinct construction role makes execution evidence more truthful, verifies it, or catches a compromised executor's false observations, only that misreporting requires an additional, avoidable step rather than none. **Because the protocol-executor role remains the sole observer of protocol facts (Observation, above), a compromised executor can fabricate those observations regardless of how many logically distinct roles later handle them; logical separation does not make a false observation true, and it does not independently verify one.** This residual risk is stated, not closed, in **Security Consequences**, below.

The analogy to ADR-0007's `basis-adapters`/`basis-producer` split is not exact, and this ADR states the difference directly rather than eliding it: `basis-adapters` is a pure, network-free library with no access to what happens after normalization, whereas the execution-evidence-producer role necessarily receives the protocol-executor's raw, in-process observation directly — there is no equivalent of `basis-adapters`' complete architectural isolation available here, because the fact being recorded (what did the protocol channel report) only exists inside the process that dispatched. The separation this ADR requires is therefore a *logical-role* separation — a distinct responsibility with its own obligations — not a claim that construction is architecturally isolated from observation the way `basis-adapters` is isolated from `basis-producer`'s network calls.

**Retention.** **Retention may be colocated with observation and construction for the first bounded reference slice, hosted alongside the operation-producer and protocol-executor roles within `basis-producer`'s existing process boundary, consistent with ADR-0011 Decision 3's same-process default topology.** This ADR does not require a separate retention component, a database, or a durable store technology for the first slice — that is implementation planning. What this ADR does require, restating the authorization side's own "retain-before-mint" discipline (ADR-0007) as the closest available precedent, is that the execution-evidence-producer role never report a durable record as existing until retention has actually been attempted and its result is known (**Evidence Durability and Persistence Failure**, below) — an analogous "retain-before-anything-else" discipline for execution, not a new invention.

**Are all three the same component in the first bounded reference slice?** Plausibly yes, hosted together within `basis-producer`'s process boundary alongside the operation-producer role, exactly as ADR-0011 Decision 3 already permits multiple logically distinct roles to share one process. This ADR does not require three separate deployment units, three separate classes, or three separate modules — only that the three obligations (observe, construct, retain) remain logically distinct enough that a future implementation could separate them without redesigning what each one owns, restating ADR-0011's own restraint on implementation specifics.

## Minimum Evidence Facts

An execution-evidence record must carry, at minimum, the following facts. This is a semantic minimum, not a schema: this ADR does not fix field names, types, or serialization for any of them. Not every fact a record might carry necessarily exists for every case this ADR constructs evidence for (**Execution Evidence Definition**, above): case 1 (an execution attempt that reached dispatch) and case 2 (a pre-dispatch execution-boundary failure — always ADR-0013 Decision 2's Case C, since case 2 is never constructed unless a pre-dispatch record already existed) do not have identical source facts available, and this ADR requires the facts below to be split accordingly rather than stated as though every fact were always available. Ownership (whose observation each fact rests on) is as already established in **Observation, Construction, and Retention Ownership**, above.

**Always required for an execution-boundary evidence candidate** — because the underlying fact necessarily exists for both case 1 and case 2 as this ADR scopes them:

- an execution-evidence-record identifier of its own, minted by the execution-evidence-producer role;
- whether the record describes (a) an execution attempt that reached dispatch (case 1), or (b) a pre-dispatch execution-boundary failure (case 2) — the two are never conflated, and a record must state which one it is;
- **the lifecycle outcome** — the attempt-outcome value itself, kept as a fact distinct from, and never substituted by, the specific failure cause named in the next bullet: for case 1, the attempt-outcome value reached, using Accepted ADR-0013's vocabulary (`PROTOCOL_ACCEPTED`, `PROTOCOL_REJECTED`, or `OUTCOME_UNKNOWN`, including which of the two structurally different `OUTCOME_UNKNOWN` reasons applies where the protocol makes that distinction knowable — case 1 never resolves to `NOT_ATTEMPTED`, by definition); for case 2, the attempt-outcome value is `NOT_ATTEMPTED`, always and by definition (ADR-0013 Decision 2's Case C) — this fact is required on every case-2 record regardless of which specific boundary-local condition produced it;
- **the specific failure cause, for case 2 only** — the specific boundary-local condition, under ADR-0013 Decision 2's Case C, that produced the `NOT_ATTEMPTED` outcome above: the specific binding-verification failure reason under ADR-0012's Failure Semantics (no binding record found; digest mismatch; non-permitting correlated disposition; already-consumed binding; verification error) when the Case C condition is a binding-verification failure, or the specific other protocol-executor-local pre-dispatch condition (for example, an endpoint unreachable before any bytes are sent, or a transport/connection timeout before dispatch is committed to) when it is not. **This ADR requires the lifecycle outcome and the specific failure cause to be preserved as two separate facts, never collapsed into one another — `attempt outcome = NOT_ATTEMPTED` states only that dispatch did not occur; `failure cause = <specific cause>` states why. It does not define schema field names or enum identifiers for either;**
- for a multi-stage case-1 attempt (ADR-0013 Decision 7), the per-stage sequence of attempt-outcome values, not merely the collapsed overall value — otherwise a partially progressed select/operate attempt loses exactly the information ADR-0013 Decision 7 requires be preserved;
- the resulting-state-verification value: for case 1, whichever of ADR-0013's three values (`VERIFICATION_NOT_APPLICABLE`, `STATE_VERIFIED`, `STATE_NOT_VERIFIED`) the protocol executor actually reached. **For case 2, this ADR preserves ADR-0013 Decision 5's own semantics rather than redefining them: because attempt outcome is `NOT_ATTEMPTED`, resulting-state verification is meaningless by definition and the value is `VERIFICATION_NOT_APPLICABLE`, always and without exception — this is a semantic fact every case-2 record carries, not a fact this ADR declares absent or not required.** This ADR states a semantic minimum, not a serialization contract: whether a future schema must physically serialize a value that is fully derivable, for every case-2 record, from `attempt outcome = NOT_ATTEMPTED` alone is downstream serialization planning this ADR does not decide;
- the evidence-durability value reached for this specific record, using the minimal vocabulary this ADR defines in **Evidence Durability and Persistence Failure**, below;
- the pre-dispatch record's creation time and the observation-resolution time — a minimum timing pair, not a full timing model; both exist for every case this ADR constructs evidence for, because a pre-dispatch record's existence is a precondition of either case;
- the pre-dispatch record/context identifier (**Correlation Model**, below, treats this as the lifecycle correlation anchor for the cycle), since neither case 1 nor case 2, as this ADR scopes it, is ever constructed without one having been successfully created first (ADR-0013 Decision 2's Case C for case 2; a successfully created record followed by dispatch for case 1) — this ADR does not construct evidence, of either case, for a Case B record-creation failure, precisely because no record exists then for this identifier, or anything else in this list, to describe (see **Execution Evidence Definition**, above);
- the authoritative permitting disposition (`ALLOW`) that caused the protocol executor to enter the pre-dispatch boundary in the first place (ADR-0013 Decision 2) — always present and always permitting, because boundary entry is itself conditioned on having received it. **This is a distinct fact from, and must never be conflated with, the disposition/correlation value stored in or associated with the binding record that verification checks** (below), which is not guaranteed to exist, and is not guaranteed to be permitting when it does;
- the gateway-generated correlation ID and the kernel `trace_id` / `AuditEvidence.evidence_id` — both travel with the authoritative permitting disposition itself, before any binding-record lookup occurs, and are therefore available regardless of whether a binding record is later found.

**Conditionally required, only when the source fact actually exists** — a record must state the fact's absence, never fabricate or default it, when it does not:

- the ADR-0012 binding identifier the attempt was verified against, when a binding record was actually found — omitted, not fabricated or defaulted to a placeholder, when the case-2 failure reason is precisely that no binding record was found;
- the disposition/correlation value stored in or associated with the binding record, as checked by binding verification, when a binding record was found — recorded as whatever it actually was, including a non-permitting or mismatched value. A case-2 record whose failure reason is "non-permitting correlated disposition" must record that stored value as non-permitting; it must never omit it, and it must never restate the authoritative `ALLOW` disposition (above) in its place as though the two were the same fact — doing so would make a security failure look like a successful, permitting fact, which this ADR forbids;
- other binding-related values available from the binding record (for example, the recomputed and stored digests, when a mismatch is the failure reason), when a binding record was found;
- the `AdapterEvidenceReference.reference_id`, when the operation-producer role holds one for the operation this attempt or failure concerns;
- a reference to the prior execution-attempt's evidence record, only for a retry (ADR-0013 Decision 9) following a prior attempt that reached dispatch.

This ADR treats this list as a floor, not a ceiling: a future execution-evidence schema (Gate 3's own downstream work, now that this ADR is accepted) may add fields this list does not name — a protocol-specific result code, per discovery assessment §9's per-protocol evidence — but must not omit any always-required fact, must not state a conditionally required fact when its source fact does not exist, and must not conflate an observational fact with a correlation fact merely because both eventually live in the same serialized record. Above all: missing information must never be made to look like a successful or permitting fact.

## Correlation Model

Extending, by exactly one hop, the identifier chain `operation-producer-and-execution-boundary.md` §6 and discovery assessment §13 already inventory:

```text
AdapterEvidenceReference.reference_id      (basis-producer, minted, ADR-0007)
    → producer request_id / correlation_id  (basis-producer / caller)
```

The solid arrows (`→`) mark a link that necessarily exists once the chain has reached that point; the dashed arrow (`⇢`) marks a link that is conditional on a source fact this ADR does not guarantee — the ADR-0012 binding identifier only enters this chain when binding verification actually found a binding record to check, and a retry-lineage reference only exists when the record in question actually is a retry. Neither is fabricated or defaulted when the underlying fact is absent (**Minimum Evidence Facts**, above).

Two rules govern this extension, restated from the components that already implement correlation today and generalized forward without weakening either restatement:

**No component may overwrite an identifier owned by another component.** This is already `operation-producer-and-execution-boundary.md` §6's explicit policy, generalized there specifically to anticipate this ADR: "a future execution-evidence producer must not overwrite the `request_id`, `correlation_id`, or `trace_id` it receives from the authorization chain — it appends its own identifier and references the ones that came before it, exactly as `GatewayAuditEvent` references `AuditEvidence` rather than absorbing it." This ADR requires the execution-evidence-record identifier to follow the identical discipline: it is appended, never substituted for an upstream identifier — including the pre-dispatch record/context identifier — and never used to "correct" or "complete" an upstream record.

**Correlation creates deterministic linkage; it does not by itself prove authenticity or causation.** This is discovery assessment §13's finding, restated for execution evidence specifically because it is the single most important caution this Correlation Model carries: a shared correlation ID across an `AuditEvidence` record and an execution-evidence record proves that the two records claim to describe the same operation. It does not prove that the execution-evidence record is genuine, that the component which wrote it was the component authorized to, or that the execution it describes actually corresponds to the authorized operation rather than a coincidentally similar one. None of the identifiers in this chain is integrity-protected at a trust boundary today — restated from discovery assessment §6 and §13 without narrowing — and this ADR does not change that; the ADR-0012 binding digest, not a correlation identifier, is what already does the actual mutation/substitution-detection work upstream of dispatch. This ADR's correlation model is diagnostic and reconstructive, not a security control, and every fact under **Conditionally required** in **Minimum Evidence Facts**, above, must be understood, and eventually serialized, as diagnostic rather than authoritative for exactly this reason.

**Which identifier scopes what, and why this ADR does not introduce a separate execution-attempt identifier:** ADR-0013 Decision 2 states directly that it "does not mandate two separate stored objects, two identifiers, or two data structures for the pre-dispatch record and the eventual execution attempt" — a future implementation may represent them as one evolving in-process structure, and the pre-dispatch record/context identifier (Minimum Evidence Facts, above) is created once, before binding verification, and continues to identify that same object whether it ultimately resolves to Case C `NOT_ATTEMPTED` or is superseded, at dispatch, by an execution attempt (ADR-0013 Decision 2). This ADR treats that identifier — not a second, execution-attempt-specific identifier — as the lifecycle correlation anchor for the cycle: it is the one identifier both branches in the diagram above correlate against. A new authorization/execution cycle receives its own new pre-dispatch record/context identifier; this ADR does not permit reusing one across cycles. The execution-evidence-record identifier is a separate concern from the lifecycle correlation anchor: it scopes exactly one execution-evidence record — candidate or durable — describing that one attempt or pre-dispatch failure, and is minted independently by the execution-evidence-producer role, referencing the pre-dispatch record/context identifier rather than replacing it. This ADR does not collapse the two into one identifier, for the same reason discovery assessment §13 already declines to collapse `trace_id` and `evidence_id` into one value: an execution-evidence candidate can exist in process memory, mid-observation, before it is durably retained, and forcing one identifier to serve both the lifecycle-correlation role and the evidence-record-identity role would lose exactly the distinction **Evidence Durability and Persistence Failure**, below, depends on preserving. Retry lineage (ADR-0013 Decision 9) correlates through the reference to the prior execution-attempt's own execution-evidence record already required above (**Minimum Evidence Facts**), not through the pre-dispatch record/context identifier, which does not itself carry retry semantics and is minted fresh for every cycle.

**On whether a distinct execution-attempt identifier might still be genuinely necessary:** this ADR considered, and rejects for this bounded semantic minimum, introducing one. Nothing this ADR requires — correlating Case C evidence and dispatched-attempt evidence back to the same pre-dispatch record/context identifier, or correlating retry lineage through the execution-evidence-record identifier — depends on a second identifier existing, and ADR-0013 Decision 2 explicitly declines to require one at the lifecycle-semantics level this ADR builds on. If a future schema-design or implementation effort discovers a genuine need for one (for example, because a specific serialization cannot represent "the same identifier before and after dispatch" cleanly), that is itself an architectural question requiring its own review, not something to introduce silently through this document's correlation diagram — consistent with the general principle that this ADR states a semantic minimum, not a schema.

## Binding-Identifier Lifetime Is Compatible With ADR-0012

Accepted ADR-0012 states two separate things this ADR must not conflate. First, under its **The binding record** section: "The binding identifier and the binding record itself are same-process-local. They are not submitted to `basis-gateway`, do not appear on the operation-aware request or response, and require no `basis-schemas` change[,] because the first bounded topology is same-process (ADR-0011 Decision 3), the operation-producer role can correlate the disposition it receives back to its own binding record using only the identifiers the chain already generates on both sides of the round trip, without a new field crossing the wire." Read in context, this is a statement about how the binding identifier participates in the Gate 1 authorization-to-execution mechanism — it does not cross the wire to `basis-gateway` — not a statement that the identifier's value can never be recorded anywhere else, by any other mechanism, for any other purpose. Second, under its **Freshness and single use** section, ADR-0012 states that the **process-local single-consumption guarantee** — the enforcement property that a binding record may be consumed by at most one dispatch within the process's own running lifetime — "does not survive a process restart, and provides no protection against a deliberately compromised process replaying its own state." That sentence's subject is the *guarantee*, not "the binding record and its binding identifier" as a joint claim; it describes what the enforcement property does not provide, not a normative restriction on where the identifier's value may ever be copied. A prior version of this section attributed "does not survive a process restart" directly to the binding record and identifier as a pair, which is not the sentence ADR-0012 actually states; that has been corrected here.

Most directly, ADR-0012 itself names this exact question and declines to answer it, reserving it to Gate 3: under **Security Consequences → Still requiring follow-on architecture**, it lists "[m]inimum execution-evidence semantics, including whether the binding record or its identifier participates in a future execution-evidence record (Gate 3)." ADR-0012 does not resolve that question in either direction there; it defers it. This ADR is Gate 3, and this section is where that deferred question is answered — **Outcome A**, in the sense that ADR-0012's actual normative language constrains the live binding record and the guarantee it enforces, and explicitly leaves the identifier-value question open for this ADR to decide, rather than closing it in either direction itself.

**Correlation Model**, above, permits the binding identifier to be copied into an execution-evidence record, conditional on a binding record actually having been found (**Minimum Evidence Facts**, above) — never fabricated or defaulted when none was found. This ADR resolves ADR-0012's deferred question by permitting exactly that, under strict limits: ADR-0012's same-process-local constraint and its process-local single-consumption guarantee govern the *binding record* — the live artifact that establishes, and that dispatch consumes to authorize, one execution attempt — not every downstream copy of the *value* of its identifier. Durably copying the binding identifier into an execution-evidence record, retained for the first bounded reference slice within the same `basis-producer` process boundary (ADR-0011 Decision 3; **Observation, Construction, and Retention Ownership**, above): does not persist the binding record itself; does not recreate it; does not make it consumable again after it has already been consumed or has failed verification; and does not transmit it to `basis-gateway`, onto the operation-aware request or response, or across any trust boundary ADR-0012 did not already accept for the binding record itself. The binding identifier, once copied into execution evidence, is diagnostic correlation only — restating, for this specific identifier, the same rule **Correlation Model**, above, already states for every identifier in this chain: it proves that two records claim to describe the same operation, not that either is genuine, and it is never a reusable authorization artifact or an independent security control. This ADR does not require, and does not create, any mechanism by which a durably recorded binding identifier could later be presented to re-authorize or re-consume the binding record it names.

## Evidence Durability and Persistence Failure

ADR-0013 named the evidence-durability axis and required that it "must never be conflated with the other two" (its Decision 3), but explicitly left its values, ownership, and persistence mechanism to Gate 3. **This ADR defines the evidence-durability axis's minimum values as a three-value shape, mirroring the transient/terminal pattern ADR-0013 already used for its own attempt-outcome axis, as a non-normative illustration of the concept — restating ADR-0013's own disclaimer that "any class, module, function, or API name that appears anywhere in this document is a non-normative illustration of a concept, never a specification of an interface":**

**Naming the object each value describes, to avoid a recursive definition.** Every value below describes the retention outcome of the **execution-evidence candidate** defined in **Execution Evidence Definition**, above — the in-process record — not of an already-durable artifact describing itself. In particular, `PERSISTENCE_FAILED` describes a retention attempt against the candidate that did not succeed; it is not itself durably persisted "as the record of its own failure" — a failed retention attempt cannot rely on the successfully durable existence of the very record whose durability failed. The fact that a specific retention attempt failed exists, for as long as the process holding it stays up, as the in-process evidence-durability value on the candidate itself; whether and how that fact is made durable in turn (an operator alert, a fallback log, a separate durability record) is implementation planning this ADR does not decide (below). Only `PERSISTED` describes a case where the underlying observational facts have actually reached durable storage; `NOT_YET_PERSISTED` and `PERSISTENCE_FAILED` both describe a candidate that has not.

**`NOT_YET_PERSISTED` is non-terminal only relative to a process that survives long enough to complete and observe the retention attempt — it is not a guarantee that a terminal value is eventually reached.** The candidate, and the `NOT_YET_PERSISTED` value describing it, exist only in process memory unless and until a retention attempt actually succeeds; this ADR does not provide, and does not assume, any mechanism by which the candidate or its in-process durability value survives a process crash on its own. If the process crashes before the retention attempt reaches an observed terminal result, this ADR does not pretend a terminal durability value necessarily exists afterward: durable execution evidence for that record is not guaranteed to exist, and whether it does depends entirely on whether retention had already reached `PERSISTED` before the crash — a fact this ADR's in-process model alone cannot establish after the fact. Recovery, reconstruction, or how a later process diagnoses an incomplete retention attempt remains implementation planning and future architecture, exactly as already scoped below.

| Value (illustrative) | Meaning | Terminal? |
| - | - | - |
| `NOT_YET_PERSISTED` | The observational facts (attempt outcome, resulting-state verification) are known in-process, but the execution-evidence-producer role has not yet completed a durable-retention attempt for this record. | No, while the process holding the candidate remains running and able to complete and observe the retention attempt — but not guaranteed to resolve at all: this value is not itself durable, and if the process crashes before the retention attempt reaches an observed terminal result, `NOT_YET_PERSISTED` does not "become" `PERSISTED` or `PERSISTENCE_FAILED` on anyone's behalf; see the crash scenario below. |
| `PERSISTED` | A durable-retention attempt for this record completed successfully, using whatever retention mechanism the deployment provides. This ADR does not define "durable" for a given deployment — disk fsync, database commit, an append-only log, or another mechanism are all implementation planning. | Yes. |
| `PERSISTENCE_FAILED` | A durable-retention attempt for this record was made and did not succeed. | Yes, for the retention attempt whose result was actually observed — this ADR does not decide whether a further retention attempt follows, and if one does, does not decide how it would be represented or correlated to the one this value describes; see the note immediately below the table. |

**This ADR governs the minimum retention outcome for one observed retention attempt; it does not decide what happens if evidence retention is retried.** `NOT_YET_PERSISTED`, `PERSISTED`, and `PERSISTENCE_FAILED` are minimum values for the retention outcome this ADR governs, and `PERSISTENCE_FAILED` is terminal only for the specific retention attempt whose result was observed — it is not, by itself, a statement about whether that was the only retention attempt that will ever be made. This ADR does not decide: whether failed execution-evidence retention is retried at all; if it is, how multiple retention attempts for the same underlying observational facts would be correlated to one another; whether a future durability model would represent current/latest durability only, a full retention-attempt history, or both; a retention-retry count, trigger, or backoff policy; a retention-attempt identifier; or a retry-history schema. A prior version of this section stated that a retry, if one occurs, is necessarily "a new retention attempt against the same execution-evidence record" — that is exactly the kind of retention-retry architecture this ADR does not decide, and that statement has been removed rather than corrected in place, because no replacement claim is warranted here either. The first bounded reference slice this ADR scopes must not depend on any undefined retention-retry semantics: it may attempt retention exactly once and report whichever of the three values above actually results, without needing any of the open questions above resolved. This is a separate question from execution retry (ADR-0013 Decision 9, above) — a retry of the *dispatch* is a new execution attempt with its own new execution-evidence candidate; retrying *retention* of one already-observed candidate, if a future architecture ever does so, is a different question this ADR leaves entirely to that future architecture to reconcile with the durability semantics governed here, not to invent silently downstream of it.

**Normative requirement, restating and narrowly extending ADR-0013 Decision 3 and Decision 6 without weakening either:** an evidence-durability value of `PERSISTENCE_FAILED` must never revise, retract, or cast doubt on an already-reached attempt-outcome or resulting-state-verification value. The observational facts are fixed the moment the protocol-executor role reaches them (ADR-0013 Decision 15's ordering, restated); evidence-durability is evaluated afterward, independently, and describes only whether the *record* of those facts was successfully retained — never the facts themselves. A record that fails to persist is not deleted, discarded, silently dropped, or replaced by a "safer" reconstructed value; the in-process, already-observed facts remain exactly what they were, for as long as the process holding them remains up, and the failure to durably retain them is itself the fact `PERSISTENCE_FAILED` exists to preserve.

**How persistence failure is communicated onward is implementation planning, not decided here.** This ADR does not decide whether a `PERSISTENCE_FAILED` record triggers an operator alert, a local retry, a fallback log, or another mechanism — restating, without narrowing, discovery assessment §10's own "what this means operationally... is not decided by the evidence gathered here." What this ADR does require is that whichever mechanism a future implementation chooses, it must not be permitted to change what the attempt-outcome or resulting-state-verification value *was* — only what the deployment does in response to not yet having a durable record of it.

## Schema Publication Boundary

**This ADR defines minimum execution-evidence semantics. It does not publish a schema, and it does not authorize immediate `basis-schemas` work.** This is the recommended default this ADR adopts without departing from it: `ecosystem-contract-inventory.md`'s own governing principle — restated throughout every accepted document in this repository that touches schema readiness — is that a contract becomes schema-ready only "when implementation proves a stable shape," and discovery assessment §20 states the same conclusion specifically for execution evidence: "no execution-evidence contract should be published until a bounded reference implementation... exists to prove the shape is actually sufficient." Nothing gathered for this ADR is that implementation evidence; this ADR's minimum-facts list (**Minimum Evidence Facts**, above) is a semantic floor an eventual schema must satisfy, not a candidate schema itself, and this ADR does not select field names, types, enum value identifiers, a serialization format, or a canonicalization profile for any fact it names.

A future schema publication should follow only after a bounded execution reference implementation — the analogue of the completed producer program's Phase 2A through Phase 5 — provides enough evidence to stabilize field names, serialization, and compatibility shape, consistent with `ecosystem-contract-inventory.md`'s discipline and with discovery assessment §20's own recommended sequence (this discovery assessment → execution-model ADR → normative specifications → a bounded technical spike, only where architecture cannot responsibly settle a question alone → repository-specific implementation planning → a bounded execution reference slice → conformance, demonstration, and review → shared schema publication, only once a stable cross-repository contract shape is established). This ADR is one of the "normative specifications" that sequence names; it is not the schema-publication step, and it does not shorten the sequence by skipping ahead to one.

## Replay/Freshness Boundary

**This ADR does not resolve, narrow, or reinterpret the broader replay/freshness question ADR-0012 and ADR-0013 both deliberately left open.** Restating both without weakening either: execution evidence must preserve the attempt correlation and retry lineage ADR-0013 already requires — the prior-execution-attempt reference named in **Minimum Evidence Facts**, above, is exactly that requirement, carried into evidence semantics rather than newly invented here. Execution evidence may record freshness-related facts only if a later, dedicated architecture decision defines them; this ADR does not add a TTL, an expiry timestamp, a freshness window, or any other freshness-relevant field to the minimum-facts list, and a future implementation must not treat this ADR's silence on freshness as permission to invent one unilaterally. Wall-clock expiry, policy-reload invalidation of a pending or already-consumed disposition, restart-surviving replay prevention, retry/idempotency rules beyond ADR-0013's narrow attempt-correlation resolution, and any replay database all remain deferred, exactly as ADR-0012 and ADR-0013 both state, and this ADR does not narrow any of them further.

**Evidence semantics must not be mistaken for replay prevention.** This is the governing distinction this section exists to state plainly: an execution-evidence record that correlates a retry to its prior attempt (**Correlation Model**, above) makes a retry *reconstructible after the fact* — an auditor or operator can trace a sequence of attempts for one logical operation. It does not *prevent* a replay, does not detect one in real time, and does not substitute for whatever mechanism a future architecture decision eventually assigns that responsibility to. Restating discovery assessment §13's identical caution about correlation identifiers generally, applied here without exception: correlation "support[s] detection of duplicates in audit," it does not itself prevent duplication or forgery. This ADR's evidence-only resolution of attempt correlation is not, and does not present itself as, the "dedicated future architecture decision" ADR-0012 and ADR-0013 both anticipate for the broader replay/freshness properties they leave open.

## Failure and Uncertainty Semantics

Extending, without weakening, ADR-0013's own scenario table with the evidence-durability axis this ADR adds:

```text
persistence not yet attempted   ≠  persistence failed           (transient is not negative)
persistence failed              ≠  execution failed              (the record's durability is not the event's outcome)
execution-evidence record exists ≠  execution-evidence record is genuine   (correlation is not authenticity)
NOT_ATTEMPTED (Case C — pre-dispatch boundary failure) ≠  NOT_ATTEMPTED (Case A upstream cause, or Case B record-creation failure)  (all are NOT_ATTEMPTED; only Case C gets an execution-evidence record under this ADR)
```

| Scenario | Attempt outcome | Evidence durability |
| - | - | - |
| Binding verification fails (no record, digest mismatch, non-permitting correlation, already consumed, verification error) — Case C | `NOT_ATTEMPTED` | An execution-evidence record is created and its durability tracked, per **Execution Evidence Definition**; binding-specific failure facts are retained in addition to the facts every Case C record carries |
| Another protocol-executor-local pre-dispatch failure after record creation (for example, endpoint unreachable, transport/connection timeout) — Case C | `NOT_ATTEMPTED` | An execution-evidence record is created and its durability tracked, per **Execution Evidence Definition**, carrying the applicable failure cause instead of binding-specific facts |
| `DENY`, evaluation failure, producer auth/admission failure, gateway unavailable — Case A | `NOT_ATTEMPTED` | No execution-evidence record — the fact is already authoritatively recorded upstream (`GatewayAuditEvent` / `AuditEvidence`) |
| Protocol executor enters the boundary but cannot create the required pre-dispatch record — Case B | `NOT_ATTEMPTED` | No execution-evidence record — no pre-dispatch record ever existed to correlate one against; the failed creation attempt is covered by ADR-0013's own fail-closed requirements (ADR-0013 Decision 16) |
| Dispatch succeeds, protocol acknowledges, evidence write succeeds | `PROTOCOL_ACCEPTED` | `PERSISTED` |
| Dispatch succeeds, protocol acknowledges, evidence write fails | `PROTOCOL_ACCEPTED` (unchanged) | `PERSISTENCE_FAILED` — the acceptance fact is not revised or withdrawn |
| Dispatch occurs, outcome unknown (timeout or no-ack primitive), evidence write succeeds | `OUTCOME_UNKNOWN` | `PERSISTED` — the record durably preserves the uncertainty itself, not a guessed resolution of it |
| Process crashes before the retention attempt reaches an observed terminal result | Whatever attempt-outcome value was last reached in process memory before the crash — this fact is unaffected by the durability question | Not guaranteed to be any value at all: the in-process candidate and its `NOT_YET_PERSISTED` state do not survive the crash, and this ADR does not provide persistence for the candidate itself. Whether durable execution evidence exists for this record afterward depends entirely on whether a retention attempt had already reached `PERSISTED` before the crash — a fact not established by the crash alone. This ADR does not decide how, or whether, a recovering process detects or reconstructs an incomplete retention attempt — implementation planning and future architecture |
| Retry after `OUTCOME_UNKNOWN` | A new, correlated execution attempt (ADR-0013 Decision 9), with its own fresh ADR-0012 binding | A new, independent execution-evidence record, referencing the prior one — never a mutation of it |

## Alternatives Considered

**A — Collapse the execution-evidence-producer role into the protocol-executor role entirely, with no logical construction/retention distinction.** Rejected. This repeats, for execution, exactly the drift risk ADR-0007 designed the `basis-adapters`/`basis-producer` split to avoid for authorization evidence (discovery assessment §10), and does so without the mitigating benefit that split provides — a dispatcher with no distinct construction responsibility has both the opportunity and, absent any check, the least friction to misreport a failure as a success.

**B — Assign construction and retention to the operation-producer role rather than a new logical execution-evidence-producer role.** Considered, not selected as the primary model. The operation-producer role already constructs `AdapterEvidenceReference` and creates the ADR-0012 binding record, and could plausibly also construct execution evidence. Not selected because the operation-producer role, per ADR-0011 Decision 2, is architecturally distinct from the protocol-executor and does not have direct access to post-dispatch protocol observations — only the executor does; routing observations back through the producer would add a return hop for no protective benefit in a same-process topology, where a dedicated execution-evidence-producer role can sit adjacent to the executor and ingest observations directly. This ADR does not prohibit a future implementation from having the same concrete component play both the operation-producer and execution-evidence-producer logical roles — three logically distinct roles hosted by one process, exactly as ADR-0011 Decision 3 already permits — only from collapsing the roles conceptually.

**C — Abandon axis-based observation and record one combined "execution result" fact for evidence purposes, independent of ADR-0013's vocabulary.** Rejected. This would reopen ADR-0013's Decision 3 rejection of a single flat status field, for the specific reason ADR-0013 already gives: a combined value reproduces the "partially-applied"-shaped conflation risk the discovery assessment found in the retired five-state sketch. Evidence must serialize the vocabulary ADR-0013 defines, not a different one invented for convenience at the evidence layer.

**D — Publish an execution-evidence schema now, alongside this ADR.** Rejected, per **Schema Publication Boundary**, above — no bounded reference implementation exists yet to prove the shape is sufficient, and publishing now would repeat exactly the premature-formalization risk `ecosystem-contract-inventory.md`'s governing principle exists to prevent.

**E — Resolve the broader replay/freshness question here, as part of evidence semantics, since evidence and freshness are related concerns.** Rejected. ADR-0012 and ADR-0013 both deliberately reserved this question for a dedicated future architecture decision; this ADR gathers no new evidence about wall-clock expiry, restart survival, or a replay database, and resolving it here would preempt that dedicated decision without the evidentiary basis it requires — the same reasoning ADR-0013's own Alternative D already applied to itself.

**F — Assign a new, seventh `ProvenanceClassification` value to execution-observed facts now.** Rejected. No reference implementation exists yet to demonstrate that any of the six existing values genuinely fails to describe an execution-observed fact, or, if one does fail, what a new value should precisely mean — discovery assessment §10 states this restraint directly, and this ADR preserves it rather than resolving it by informal extension. See **What This ADR Deliberately Leaves Open**, below.

## Consequences

### Positive

- BASIS now has a normative minimum-evidence specification satisfying Gate 3 as ADR-0011 named it — the last of the three unconditional prerequisite gates.
- Construction and retention now have an explicit, if same-process-colocated, logical home, closing discovery assessment §19's Open Question 9.
- The evidence-durability axis ADR-0013 deliberately left open now has a minimal, non-normative shape a future schema can serialize without inventing one ad hoc.
- The correlation model extends the existing, already-implemented identifier chain by exactly one hop, rather than introducing a parallel or competing correlation mechanism.
- A future execution-evidence schema (downstream of a bounded reference implementation) has a stable semantic floor to build from, rather than needing to invent minimum-facts requirements as a side effect of schema design — restating, for Gate 3, the same benefit ADR-0013 claims for Gate 2's relationship to this ADR.

### Negative / Tradeoff

- This ADR's own acceptance resolved Gate 3 in ADR-0011's sense only because ADR-0013 was accepted together with it, in the same coupled review — a dependency this ADR stated rather than resolved on its own.
- The evidence-durability axis's illustrative three-value shape is deliberately coarse; a real bounded implementation may surface retention-failure modes (partial writes, delayed durability, eventual consistency) this ADR's minimal shape does not distinguish, and a future schema may need to refine it.
- The exception carved out in **Execution Evidence Definition** — that a `NOT_ATTEMPTED` outcome caused by a Case C pre-dispatch execution-boundary failure (binding-verification failure or another protocol-executor-local pre-dispatch condition) gets an execution-evidence record, while a Case A or Case B `NOT_ATTEMPTED` does not — introduces an asymmetry a future implementer must apply carefully rather than treating all `NOT_ATTEMPTED` outcomes identically.
- Whether the existing six-value `ProvenanceClassification` enum suffices remains genuinely unresolved by this ADR, which a future schema-design step must still settle before publication.

## Security Consequences

### Prevented by this architecture

- Execution evidence being treated as, mutated into, or confused with authorization evidence, kernel evidence, gateway audit facts, adapter evidence, or identity evidence.
- A `PERSISTENCE_FAILED` evidence-durability outcome silently revising, retracting, or casting doubt on an already-observed attempt-outcome or resulting-state-verification value.
- Treating any Case C pre-dispatch execution-boundary failure — including, but not limited to, a binding-verification failure, the exact substitution/mutation event ADR-0012 exists to catch — as a fact with no durable execution-side record, merely because dispatch never occurred.
- Treating a correlation identifier, on its own, as proof that an execution-evidence record is genuine or that the execution it describes actually corresponds to the authorized operation.
- Silent, ungoverned proliferation of freshness-relevant fields into execution evidence ahead of the dedicated replay/freshness decision ADR-0012 and ADR-0013 both reserve.

### Still requiring follow-on architecture

- The broader replay/freshness properties this ADR explicitly declines to narrow further (**Replay/Freshness Boundary**).
- Whether the existing six-value `ProvenanceClassification` enum suffices for execution-observed facts, or a new value is required (**What This ADR Deliberately Leaves Open**).
- The exact reasons distinguishable within `OUTCOME_UNKNOWN` for a given protocol, as governed fields — left to future, protocol-specific schema design.
- Protocol/device credential custody, if the eventually selected bounded target requires one (Gate 4) — unaffected by, and not made conditional on, this ADR.
- The eventual execution-evidence schema itself, deferred per **Schema Publication Boundary**.

### Residual risks

- A compromised protocol-executor role can fabricate any observation an execution-evidence record would faithfully preserve, because it remains the sole authoritative observer (ADR-0013 Decision 14) — the same residual-risk structure ADR-0011 Decision 19, ADR-0012, and ADR-0013 all already accept for a compromised same-process component, restated here rather than newly introduced. Separating construction from observation (**Observation, Construction, and Retention Ownership**) is, as discovery assessment §10 states directly, "partial" mitigation at best: a sufficiently compromised executor can still fabricate what it hands to an honest construction role.
- This ADR's minimum-facts list constrains what a conforming implementation may honestly report; it does not, by itself, verify that an implementation is conforming.

## What This ADR Deliberately Leaves Open

This ADR does not decide: the exact execution-evidence field list, serialization, or a named/versioned profile identifier; whether the existing six-value `ProvenanceClassification` enum suffices for execution-observed facts, or what a seventh value would mean if one is eventually required; the exact reasons distinguishable within `OUTCOME_UNKNOWN` as governed, protocol-specific fields; whether a future execution-evidence contract should reuse ADR-0007's per-protocol-metadata-projection pattern or use a different extension mechanism (discovery assessment §19 Open Question 12); what "durable" means for a given deployment's retention mechanism; how a `PERSISTENCE_FAILED` record is communicated onward operationally; how a recovering process resolves an execution-evidence record stuck in `NOT_YET_PERSISTED` after a crash; **whether failed execution-evidence retention is retried at all, and if so, how a retention retry would be represented, correlated to the retention attempt(s) that preceded it, counted, triggered, backed off, or given a retention-attempt identifier of its own, and whether a future durability model represents current/latest durability, full retention-attempt history, or both (Evidence Durability and Persistence Failure, above)** — automatic evidence-retention retries, retention retry counts, backoff, fallback storage, retention-attempt identifiers, and retry-history schemas are all explicitly not designed here, and a future implementation needing retention retries must reconcile that behavior with this ADR's governed durability semantics rather than inventing it silently; any broader replay/freshness property beyond ADR-0013's narrow attempt-correlation resolution; device/protocol credential custody (Gate 4, not triggered by this decision); an implementation plan; a bounded reference-implementation target or protocol; or any Python interface, class, module, or package shape for the execution-evidence-producer role, consistent with ADR-0011's, ADR-0012's, and ADR-0013's own restraint on implementation specifics.

## Non-Goals

This ADR does not: implement execution; add protocol dispatch code for REST, BACnet, Modbus, OPC UA, MQTT, DNP3, IEC 61850, KNX, or Niagara; modify `basis-producer`, `basis-gateway`, `basis-adapters`, `basis-core`, `basis-identity`, or `basis-schemas`; create `basis-executor` or any other new repository; define a JSON Schema, protobuf definition, OpenAPI contract, or compatibility fixture for execution evidence; select field names, enum value identifiers, or a serialization format for any fact or axis defined here; add a seventh `ProvenanceClassification` value; design automatic evidence-retention retries, retention retry counts, backoff, fallback storage, retention-attempt identifiers, or retry-history schemas (**Evidence Durability and Persistence Failure**, above); resolve broader replay/freshness beyond restating, without narrowing, what ADR-0012 and ADR-0013 already narrowed; define device/protocol credential custody (Gate 4); change ADR-0011's, ADR-0012's, or ADR-0013's status; mark itself `Accepted`; imply that Gate 3 is resolved before this ADR's own separate, dedicated acceptance review, or that Gate 2 is resolved merely because this ADR depends on ADR-0013's vocabulary; create an implementation plan, a PR sequence, or a milestone count; imply a `basis-producer` "Phase 6"; or authorize protocol execution. Any class, module, function, or API name that appears anywhere in this document — including the illustrative evidence-durability values in **Evidence Durability and Persistence Failure** — is a non-normative illustration of a concept, never a specification of an interface.

## Validation / Implementation Gate

This ADR's merging did not itself constitute acceptance, consistent with this repository's established convention (see ADR-0011's, ADR-0012's, and ADR-0013's own Validation / Implementation Gate sections and [`docs/adr/README.md`](README.md#lifecycle-states)) that merging an ADR does not by itself change its status to `Accepted`. After this ADR merged, a separate, dedicated formal architecture and governance review accepted it together with ADR-0013, ADR-0015, and ADR-0016, as one coupled execution-readiness milestone; this ADR's status now records `Accepted`. Acceptance establishes the minimum execution-evidence semantics defined here as the governed floor a future execution-evidence schema and a future bounded execution implementation must satisfy — it does not, by itself, authorize that implementation. Per ADR-0011's own Follow-On Decision Gates and Validation / Implementation Gate sections, Gates 1 through 3 are unconditional prerequisites and Gate 4 is conditional; the coupled, simultaneous acceptance of this ADR and ADR-0013 resolves Gates 2 and 3. Gate 4 (protocol/device credential custody) is not triggered by the credential-free target Accepted ADR-0015 establishes; it remains conditionally outstanding only for a future target that requires a protocol/device credential. No implementation plan, bounded reference implementation, or schema publication is authorized by this ADR's acceptance. Protocol execution remains entirely unimplemented and unauthorized.
