# ADR-0014: Minimum Execution-Evidence Semantics

## Status

Proposed

## Context

## Problem

Once an execution attempt exists in ADR-0013's proposed vocabulary — an authorized, binding-verified, dispatched (or fail-closed `NOT_ATTEMPTED`) operation whose attempt-outcome and resulting-state-verification values the protocol-executor role has observed — what minimum evidence semantics are required so BASIS can truthfully record that attempt without confusing it with authorization evidence, kernel evidence, gateway audit facts, adapter evidence, or a future identity-evidence contract? The answer must state what counts as execution evidence at all; which logical role observes it, which constructs the durable record, and which retains it, and whether those are the same role; the minimum facts such a record must preserve to be honest rather than merely present; how it correlates to the authorization disposition, the ADR-0012 binding record, the ADR-0013 execution attempt, the gateway correlation ID, the kernel `trace_id`/`evidence_id`, the adapter evidence reference, and prior attempts in a retry sequence; how it relates to ADR-0013's three axes, including defining the evidence-durability axis ADR-0013 deliberately left open; what evidence durability means and how its failure is represented without rewriting what actually happened; which facts are authoritative observations and which are derived correlation facts only; whether any of `basis-core`, `basis-gateway`, `basis-adapters`, or `basis-schemas` gains new responsibility; whether schema publication is authorized now or remains deferred; and what remains open for implementation planning once this ADR is accepted.

The answer must not, in the course of settling any of the above, silently resolve the broader replay/freshness question ADR-0012 and ADR-0013 both deliberately left open, must not treat `ALLOW` as proof of execution, must not let execution evidence nest inside or overwrite `AuditEvidence` or `GatewayAuditEvent`, and must not assign new implementation responsibility to a repository whose current non-responsibilities are load-bearing architecture rather than incidental scoping.

## Decision

**ADR-0014 defines the minimum execution-evidence semantics required before BASIS can plan a bounded protocol-execution implementation.** It defines what execution evidence is and is not; assigns observation to the protocol-executor role (restating ADR-0013 Decision 14, not reopening it), construction to a distinct logical execution-evidence-producer role, and retention to that same role for the first bounded reference slice while leaving durable-storage shape to implementation planning; fixes the minimum facts, both observational and correlational, an execution-evidence record must carry; defines the evidence-durability axis ADR-0013 left open, as a minimal three-value shape rather than a schema; states which facts are authoritative and which are diagnostic correlation only; states plainly that no existing repository gains implementation responsibility from this decision; declines to authorize schema publication now; narrows nothing further about replay/freshness beyond what ADR-0012 and ADR-0013 already narrowed; and states what remains open. It does not define a JSON Schema, protobuf, or OpenAPI contract, does not select field names or serialization, does not create an implementation plan, and does not authorize protocol execution.

## Execution Evidence Definition

**Execution evidence is the durable record of the attempt-outcome and resulting-state-verification values the protocol-executor role observed for exactly one ADR-0013 execution attempt, together with the minimum correlation facts (below) tying that record to the authorization chain and to the ADR-0012 binding record it was verified against, plus an evidence-durability value describing the record's own persistence.** It is produced only for an execution attempt that reached ADR-0012 binding verification — that is, from binding verification onward, including a `NOT_ATTEMPTED` outcome caused by a binding-verification failure (a no-record, digest-mismatch, non-permitting-correlated-disposition, already-consumed, or verification-error condition, per ADR-0012's Failure Semantics), because that specific family of `NOT_ATTEMPTED` causes is exactly the substitution/mutation threat ADR-0012 exists to catch, and durably recording that it was caught is a security-relevant fact this architecture should not discard merely because dispatch never occurred. It is not produced for a `NOT_ATTEMPTED` outcome caused by conditions upstream of the protocol-executor role entirely — `DENY`, evaluation failure, producer authentication or admission failure, producer-only context rejection, or gateway unavailability — because those facts already have an authoritative record (`GatewayAuditEvent`, `AuditEvidence`) produced by the roles that actually observed them, and this ADR does not require the execution-evidence producer role to duplicate, re-derive, or independently attest to a fact it did not itself observe.

Execution evidence is, by definition and without exception:

- **not authorization evidence** — it does not exist until after `ALLOW` and after binding verification is attempted, restating ADR-0011 Decision 11 and ADR-0013 Decision 11 without weakening either;
- **not a kernel artifact** — `basis-core`'s `OperationAwareDecisionResponse`, `EvaluationTrace`, and `AuditEvidence` remain complete and immutable the moment the kernel produces them; execution evidence never mutates, reinterprets, replaces, or nests inside any of the three;
- **not a gateway audit fact** — `GatewayAuditEvent` records the gateway's own enforcement-boundary facts and deliberately has no `enforcement_status` field; execution evidence is never merged into it, and this ADR does not add one;
- **not adapter evidence** — `AdapterEvidenceReference` records what `basis-adapters` normalized and preserved before authorization; execution evidence may reference it by identifier (Correlation Model, below) but never absorbs, widens, or repurposes it;
- **not identity evidence** — the future `IdentityEvidenceReference` contract, not yet produced by `basis-identity` (`operation-producer-and-execution-boundary.md` §12), describes the initiating subject; execution evidence describes what happened at the protocol boundary, a structurally unrelated fact this ADR does not conflate with subject identity even where both might eventually correlate to the same operation.

```text
authorization evidence   →  what BASIS decided, before execution existed to describe
execution evidence       →  what the protocol-executor role observed, after dispatch was attempted
                             (or, narrowly, after binding verification failed — above)

execution evidence is never a patch, an update, a completion, or a
reinterpretation applied to authorization evidence — it is a later,
separate, referencing fact appended to the same correlation chain.
```

## Observation, Construction, and Retention Ownership

**Observation.** The protocol-executor role is the sole truth-owning observer of the attempt-outcome and resulting-state-verification values an execution-evidence record describes — restating ADR-0013 Decision 14 without reopening it. This ADR decides nothing new about observation ownership; it exists here only because construction and retention cannot be assigned without first restating whose observation they are permitted to act on.

**Construction.** **A distinct logical execution-evidence-producer role constructs the execution-evidence record from the protocol-executor role's observations and the minimum correlation facts named below.** This is the recommended default this ADR adopts: the discovery assessment's own §10 finding argues for it directly, by analogy with ADR-0007's `basis-adapters`/`basis-producer` split — "a dispatcher that both dispatches and self-reports what happened has a structural incentive (or at minimum, a structural opportunity) to misreport a failure as a success, which a separated observer-and-recorder pair would at least partially check." The analogy is not exact, and this ADR states the difference directly rather than eliding it: `basis-adapters` is a pure, network-free library with no access to what happens after normalization, whereas the execution-evidence-producer role necessarily receives the protocol-executor's raw, in-process observation directly — there is no equivalent of `basis-adapters`' complete architectural isolation available here, because the fact being recorded (what did the protocol channel report) only exists inside the process that dispatched. The separation this ADR requires is therefore a *logical-role* separation — a distinct responsibility with its own obligations, restating ADR-0011 Decision 2's "same-process does not mean same responsibility" principle one layer further down the chain — not a claim that construction is architecturally isolated from observation the way `basis-adapters` is isolated from `basis-producer`'s network calls. The discovery assessment's own restraint on this exact point (§10: separation "is a responsibility-clarity, durability, tamper-boundary, and blast-radius property — not, by itself, a truthfulness property") is adopted here without weakening: this ADR does not claim that a logically distinct construction role makes execution evidence more truthful, only that it makes misreporting require an additional, avoidable step rather than none.

**Retention.** **Retention may be colocated with observation and construction for the first bounded reference slice, hosted alongside the operation-producer and protocol-executor roles within `basis-producer`'s existing process boundary, consistent with ADR-0011 Decision 3's same-process default topology.** This ADR does not require a separate retention component, a database, or a durable store technology for the first slice — that is implementation planning. What this ADR does require, restating the authorization side's own "retain-before-mint" discipline (ADR-0007) as the closest available precedent, is that the execution-evidence-producer role never report a durable record as existing until retention has actually been attempted and its result is known (**Evidence Durability and Persistence Failure**, below) — an analogous "retain-before-anything-else" discipline for execution, not a new invention.

**Are all three the same component in the first bounded reference slice?** Plausibly yes, hosted together within `basis-producer`'s process boundary alongside the operation-producer role, exactly as ADR-0011 Decision 3 already permits multiple logically distinct roles to share one process. This ADR does not require three separate deployment units, three separate classes, or three separate modules — only that the three obligations (observe, construct, retain) remain logically distinct enough that a future implementation could separate them without redesigning what each one owns, restating ADR-0011's own restraint on implementation specifics.

## Minimum Evidence Facts

An execution-evidence record must carry, at minimum, the following facts. This is a semantic minimum, not a schema: this ADR does not fix field names, types, or serialization for any of them.

**Observational facts (protocol-executor-owned, per Observation above):**

- the attempt-outcome value reached, using ADR-0013's proposed vocabulary (`NOT_ATTEMPTED` and, where the specific member of that family is known, which one; `PROTOCOL_ACCEPTED`; `PROTOCOL_REJECTED`; or `OUTCOME_UNKNOWN`, including which of the two structurally different `OUTCOME_UNKNOWN` reasons applies where the protocol makes that distinction knowable);
- for a multi-stage attempt (ADR-0013 Decision 7), the per-stage sequence of attempt-outcome values, not merely the collapsed overall value — otherwise a partially progressed select/operate attempt loses exactly the information ADR-0013 Decision 7 requires be preserved;
- the resulting-state-verification value reached, using ADR-0013's proposed vocabulary (`VERIFICATION_NOT_APPLICABLE`, `STATE_VERIFIED`, or `STATE_NOT_VERIFIED`);
- the pre-dispatch attempt-record creation time (ADR-0013 Decision 2) and the observation-resolution time — a minimum timing pair, not a full timing model; this ADR does not define a broader event-timeline contract.

**Durability fact (retention-owned, per Observation, Construction, and Retention Ownership above):**

- the evidence-durability value reached for this specific record, using the minimal vocabulary this ADR defines in **Evidence Durability and Persistence Failure**, below.

**Correlation facts (execution-evidence-producer-owned; diagnostic linkage only, never authoritative in themselves — see Correlation Model, below, for the full model):**

- an execution-evidence-record identifier of its own, minted by the execution-evidence-producer role;
- an execution-attempt identifier, referencing the ADR-0013 pre-dispatch attempt record this evidence describes;
- the ADR-0012 binding identifier the attempt was verified against;
- that the correlated disposition was permitting (`ALLOW`), restated as a fact rather than re-embedded in full;
- the gateway-generated correlation ID;
- the kernel `trace_id` and `AuditEvidence.evidence_id`;
- the `AdapterEvidenceReference.reference_id`, when the operation-producer role holds one for the operation this attempt executes;
- a reference to the prior execution-attempt's evidence record, when this attempt is a retry (ADR-0013 Decision 9).

This ADR treats this list as a floor, not a ceiling: a future execution-evidence schema (Gate 3's own downstream work, once this ADR is accepted) may add fields this list does not name — a protocol-specific result code, per discovery assessment §9's per-protocol evidence — but must not omit any fact this list requires, and must not conflate an observational fact with a correlation fact merely because both eventually live in the same serialized record.

## Correlation Model

Extending, by exactly one hop, the identifier chain `operation-producer-and-execution-boundary.md` §6 and discovery assessment §13 already inventory:

```text
AdapterEvidenceReference.reference_id      (basis-producer, minted, ADR-0007)
    → producer request_id / correlation_id  (basis-producer / caller)
        → gateway correlation ID            (basis-gateway, always generated)
            → kernel trace_id               (basis-gateway-generated, embedded by basis-core)
                → AuditEvidence.evidence_id  (basis-gateway-generated, embedded by basis-core)
                    → GatewayAuditEvent.audit_evidence_id  (basis-gateway, references, never embeds)
                        → authorization disposition (ALLOW)
                            → ADR-0012 binding identifier          (operation-producer role, minted)
                                → ADR-0013 execution-attempt identifier  (protocol-executor role, created pre-dispatch)
                                    → execution-evidence-record identifier  (execution-evidence-producer role, minted)
                                        ⇢ prior execution-attempt's evidence record, if this attempt is a retry
```

Two rules govern this extension, restated from the components that already implement correlation today and generalized forward without weakening either restatement:

**No component may overwrite an identifier owned by another component.** This is already `operation-producer-and-execution-boundary.md` §6's explicit policy, generalized there specifically to anticipate this ADR: "a future execution-evidence producer must not overwrite the `request_id`, `correlation_id`, or `trace_id` it receives from the authorization chain — it appends its own identifier and references the ones that came before it, exactly as `GatewayAuditEvent` references `AuditEvidence` rather than absorbing it." This ADR requires the execution-evidence-record identifier and the execution-attempt identifier to follow the identical discipline: each is appended, never substituted for an upstream identifier, and never used to "correct" or "complete" an upstream record.

**Correlation creates deterministic linkage; it does not by itself prove authenticity or causation.** This is discovery assessment §13's finding, restated for execution evidence specifically because it is the single most important caution this Correlation Model carries: a shared correlation ID across an `AuditEvidence` record and an execution-evidence record proves that the two records claim to describe the same operation. It does not prove that the execution-evidence record is genuine, that the component which wrote it was the component authorized to, or that the execution it describes actually corresponds to the authorized operation rather than a coincidentally similar one. None of the identifiers in this chain is integrity-protected at a trust boundary today — restated from discovery assessment §6 and §13 without narrowing — and this ADR does not change that; the ADR-0012 binding digest, not a correlation identifier, is what already does the actual mutation/substitution-detection work upstream of dispatch. This ADR's correlation model is diagnostic and reconstructive, not a security control, and every fact under **Correlation facts** in **Minimum Evidence Facts**, above, must be understood, and eventually serialized, as diagnostic rather than authoritative for exactly this reason.

**Which identifier scopes what remains unchanged from the existing chain, extended consistently:** the execution-attempt identifier scopes exactly one ADR-0013 execution attempt, correlated to exactly one consumed ADR-0012 binding record (ADR-0013 Decision 1's single-binding scoping, restated); the execution-evidence-record identifier scopes exactly one durable record describing that one attempt. This ADR does not collapse the two into one identifier, for the same reason discovery assessment §13 already declines to collapse `trace_id` and `evidence_id` into one value: an attempt can exist (in process memory, mid-observation) before its evidence record is durably retained, and forcing one identifier to serve both purposes would lose exactly the distinction **Evidence Durability and Persistence Failure**, below, depends on preserving.

## Relationship to ADR-0012

## Relationship to AuditEvidence and GatewayAuditEvent

Restated, without weakening, from `operation-producer-and-execution-boundary.md` §5 and ADR-0011 Decision 11: `basis-core`'s `AuditEvidence` is complete and immutable the moment the kernel produces it, and `basis-gateway`'s `GatewayAuditEvent` records the gateway's own enforcement-boundary facts beside — never inside — that kernel evidence. `GatewayAuditEvent`'s own schema deliberately has no `enforcement_status` / `enforcement_result` field today; this is not an oversight this ADR corrects, it is the structural reason execution evidence must be its own artifact rather than an extension of either existing one. Execution evidence never nests inside, mutates, reinterprets, or "completes" `AuditEvidence` or `GatewayAuditEvent`; it correlates to both by reference only — `AuditEvidence.evidence_id` and `GatewayAuditEvent`'s own correlation fields, per **Correlation Model**, above — exactly as `GatewayAuditEvent` itself already references, never embeds, `AuditEvidence`. This ADR does not add an `enforcement_status` field to `GatewayAuditEvent`, does not modify `basis-gateway`'s audit-event schema, and does not modify `basis-core`'s audit-evidence schema.

## Evidence Durability and Persistence Failure

ADR-0013 named the evidence-durability axis and required that it "must never be conflated with the other two" (its Decision 3), but explicitly left its values, ownership, and persistence mechanism to Gate 3. **This ADR defines the evidence-durability axis's minimum values as a three-value shape, mirroring the transient/terminal pattern ADR-0013 already used for its own attempt-outcome axis, as a non-normative illustration of the concept — restating ADR-0013's own disclaimer that "any class, module, function, or API name that appears anywhere in this document is a non-normative illustration of a concept, never a specification of an interface":**

| Value (illustrative) | Meaning | Terminal? |
| - | - | - |
| `NOT_YET_PERSISTED` | The observational facts (attempt outcome, resulting-state verification) are known in-process, but the execution-evidence-producer role has not yet completed a durable-retention attempt for this record. | No — always resolves to one of the two terminal values below. |
| `PERSISTED` | A durable-retention attempt for this record completed successfully, using whatever retention mechanism the deployment provides. This ADR does not define "durable" for a given deployment — disk fsync, database commit, an append-only log, or another mechanism are all implementation planning. | Yes. |
| `PERSISTENCE_FAILED` | A durable-retention attempt for this record was made and did not succeed. | Yes, for this retention attempt; this ADR does not decide whether or how a retry is represented, only that a retry, if one occurs, is a new retention attempt against the same execution-evidence record, not a new execution attempt. |

**Normative requirement, restating and narrowly extending ADR-0013 Decision 3 and Decision 6 without weakening either:** an evidence-durability value of `PERSISTENCE_FAILED` must never revise, retract, or cast doubt on an already-reached attempt-outcome or resulting-state-verification value. The observational facts are fixed the moment the protocol-executor role reaches them (ADR-0013 Decision 15's ordering, restated); evidence-durability is evaluated afterward, independently, and describes only whether the *record* of those facts was successfully retained — never the facts themselves. A record that fails to persist is not deleted, discarded, silently dropped, or replaced by a "safer" reconstructed value; the in-process, already-observed facts remain exactly what they were, for as long as the process holding them remains up, and the failure to durably retain them is itself the fact `PERSISTENCE_FAILED` exists to preserve.

**How persistence failure is communicated onward is implementation planning, not decided here.** This ADR does not decide whether a `PERSISTENCE_FAILED` record triggers an operator alert, a local retry, a fallback log, or another mechanism — restating, without narrowing, discovery assessment §10's own "what this means operationally... is not decided by the evidence gathered here." What this ADR does require is that whichever mechanism a future implementation chooses, it must not be permitted to change what the attempt-outcome or resulting-state-verification value *was* — only what the deployment does in response to not yet having a durable record of it.

## Schema Publication Boundary

**This ADR defines minimum execution-evidence semantics. It does not publish a schema, and it does not authorize immediate `basis-schemas` work.** This is the recommended default this ADR adopts without departing from it: `ecosystem-contract-inventory.md`'s own governing principle — restated throughout every accepted document in this repository that touches schema readiness — is that a contract becomes schema-ready only "when implementation proves a stable shape," and discovery assessment §20 states the same conclusion specifically for execution evidence: "no execution-evidence contract should be published until a bounded reference implementation... exists to prove the shape is actually sufficient." Nothing gathered for this ADR is that implementation evidence; this ADR's minimum-facts list (**Minimum Evidence Facts**, above) is a semantic floor an eventual schema must satisfy, not a candidate schema itself, and this ADR does not select field names, types, enum value identifiers, a serialization format, or a canonicalization profile for any fact it names.

A future schema publication should follow only after a bounded execution reference implementation — the analogue of the completed producer program's Phase 2A through Phase 5 — provides enough evidence to stabilize field names, serialization, and compatibility shape, consistent with `ecosystem-contract-inventory.md`'s discipline and with discovery assessment §20's own recommended sequence (this discovery assessment → execution-model ADR → normative specifications → a bounded technical spike, only where architecture cannot responsibly settle a question alone → repository-specific implementation planning → a bounded execution reference slice → conformance, demonstration, and review → shared schema publication, only once a stable cross-repository contract shape is established). This ADR is one of the "normative specifications" that sequence names; it is not the schema-publication step, and it does not shorten the sequence by skipping ahead to one.

## Replay/Freshness Boundary

**This ADR does not resolve, narrow, or reinterpret the broader replay/freshness question ADR-0012 and ADR-0013 both deliberately left open.** Restating both without weakening either: execution evidence must preserve the attempt correlation and retry lineage ADR-0013 already requires — the prior-execution-attempt reference named in **Minimum Evidence Facts**, above, is exactly that requirement, carried into evidence semantics rather than newly invented here. Execution evidence may record freshness-related facts only if a later, dedicated architecture decision defines them; this ADR does not add a TTL, an expiry timestamp, a freshness window, or any other freshness-relevant field to the minimum-facts list, and a future implementation must not treat this ADR's silence on freshness as permission to invent one unilaterally. Wall-clock expiry, policy-reload invalidation of a pending or already-consumed disposition, restart-surviving replay prevention, retry/idempotency rules beyond ADR-0013's narrow attempt-correlation resolution, and any replay database all remain deferred, exactly as ADR-0012 and ADR-0013 both state, and this ADR does not narrow any of them further.

**Evidence semantics must not be mistaken for replay prevention.** This is the governing distinction this section exists to state plainly: an execution-evidence record that correlates a retry to its prior attempt (**Correlation Model**, above) makes a retry *reconstructible after the fact* — an auditor or operator can trace a sequence of attempts for one logical operation. It does not *prevent* a replay, does not detect one in real time, and does not substitute for whatever mechanism a future architecture decision eventually assigns that responsibility to. Restating discovery assessment §13's identical caution about correlation identifiers generally, applied here without exception: correlation "support[s] detection of duplicates in audit," it does not itself prevent duplication or forgery. This ADR's evidence-only resolution of attempt correlation is not, and does not present itself as, the "dedicated future architecture decision" ADR-0012 and ADR-0013 both anticipate for the broader replay/freshness properties they leave open.

## Failure and Uncertainty Semantics

Extending, without weakening, ADR-0013's own scenario table with the evidence-durability axis this ADR adds:

```text
persistence not yet attempted   ≠  persistence failed           (transient is not negative)
persistence failed              ≠  execution failed              (the record's durability is not the event's outcome)
execution-evidence record exists ≠  execution-evidence record is genuine   (correlation is not authenticity)
NOT_ATTEMPTED (binding failure) ≠  NOT_ATTEMPTED (upstream cause)  (both are NOT_ATTEMPTED; only the former gets an execution-evidence record under this ADR)
```

| Scenario | Attempt outcome | Evidence durability |
| - | - | - |
| Binding verification fails (no record, digest mismatch, non-permitting correlation, already consumed, verification error) | `NOT_ATTEMPTED` | An execution-evidence record is created and its durability tracked, per **Execution Evidence Definition** |
| `DENY`, evaluation failure, producer auth/admission failure, gateway unavailable | `NOT_ATTEMPTED` | No execution-evidence record — the fact is already authoritatively recorded upstream (`GatewayAuditEvent` / `AuditEvidence`) |
| Dispatch succeeds, protocol acknowledges, evidence write succeeds | `PROTOCOL_ACCEPTED` | `PERSISTED` |
| Dispatch succeeds, protocol acknowledges, evidence write fails | `PROTOCOL_ACCEPTED` (unchanged) | `PERSISTENCE_FAILED` — the acceptance fact is not revised or withdrawn |
| Dispatch occurs, outcome unknown (timeout or no-ack primitive), evidence write succeeds | `OUTCOME_UNKNOWN` | `PERSISTED` — the record durably preserves the uncertainty itself, not a guessed resolution of it |
| Process crashes before evidence-durability resolves | Whatever value was last reached in process memory before the crash | Remains `NOT_YET_PERSISTED` from the perspective of any observer that never sees a later value; this ADR does not decide how, or whether, a recovering process resolves a stuck `NOT_YET_PERSISTED` record — implementation planning |
| Retry after `OUTCOME_UNKNOWN` | A new, correlated execution attempt (ADR-0013 Decision 9), with its own fresh ADR-0012 binding | A new, independent execution-evidence record, referencing the prior one — never a mutation of it |

## Alternatives Considered

**A — Collapse the execution-evidence-producer role into the protocol-executor role entirely, with no logical construction/retention distinction.** Rejected. This repeats, for execution, exactly the drift risk ADR-0007 designed the `basis-adapters`/`basis-producer` split to avoid for authorization evidence (discovery assessment §10), and does so without the mitigating benefit that split provides — a dispatcher with no distinct construction responsibility has both the opportunity and, absent any check, the least friction to misreport a failure as a success.

**B — Assign construction and retention to the operation-producer role rather than a new logical execution-evidence-producer role.** Considered, not selected as the primary model. The operation-producer role already constructs `AdapterEvidenceReference` and creates the ADR-0012 binding record, and could plausibly also construct execution evidence. Not selected because the operation-producer role, per ADR-0011 Decision 2, is architecturally distinct from the protocol-executor and does not have direct access to post-dispatch protocol observations — only the executor does; routing observations back through the producer would add a return hop for no protective benefit in a same-process topology, where a dedicated execution-evidence-producer role can sit adjacent to the executor and ingest observations directly. This ADR does not prohibit a future implementation from having the same concrete component play both the operation-producer and execution-evidence-producer logical roles — three logically distinct roles hosted by one process, exactly as ADR-0011 Decision 3 already permits — only from collapsing the roles conceptually.

**C — Abandon axis-based observation and record one combined "execution result" fact for evidence purposes, independent of ADR-0013's vocabulary.** Rejected. This would reopen ADR-0013's Decision 3 rejection of a single flat status field, for the specific reason ADR-0013 already gives: a combined value reproduces the "partially-applied"-shaped conflation risk the discovery assessment found in the retired five-state sketch. Evidence must serialize the vocabulary ADR-0013 defines, not a different one invented for convenience at the evidence layer.

**D — Publish an execution-evidence schema now, alongside this ADR.** Rejected, per **Schema Publication Boundary**, above — no bounded reference implementation exists yet to prove the shape is sufficient, and publishing now would repeat exactly the premature-formalization risk `ecosystem-contract-inventory.md`'s governing principle exists to prevent.

**E — Resolve the broader replay/freshness question here, as part of evidence semantics, since evidence and freshness are related concerns.** Rejected. ADR-0012 and ADR-0013 both deliberately reserved this question for a dedicated future architecture decision; this ADR gathers no new evidence about wall-clock expiry, restart survival, or a replay database, and resolving it here would preempt that dedicated decision without the evidentiary basis it requires — the same reasoning ADR-0013's own Alternative D already applied to itself.

**F — Assign a new, seventh `ProvenanceClassification` value to execution-observed facts now.** Rejected. No reference implementation exists yet to demonstrate that any of the six existing values genuinely fails to describe an execution-observed fact, or, if one does fail, what a new value should precisely mean — discovery assessment §10 states this restraint directly, and this ADR preserves it rather than resolving it by informal extension. See **What This ADR Deliberately Leaves Open**, below.

## Consequences

### Positive

- Upon acceptance, and once ADR-0013 is separately accepted, BASIS will have a normative minimum-evidence specification satisfying Gate 3 as ADR-0011 named it — the last of the three unconditional prerequisite gates.
- Upon acceptance, construction and retention would gain an explicit, if same-process-colocated, logical home, closing discovery assessment §19's Open Question 9.
- Upon acceptance, and once ADR-0013 is separately accepted, the evidence-durability axis ADR-0013 deliberately left open would have a minimal, non-normative shape a future schema can serialize without inventing one ad hoc; this proposal defines that shape now, but it is not authoritative before formal acceptance.
- The correlation model extends the existing, already-implemented identifier chain by exactly one hop, rather than introducing a parallel or competing correlation mechanism.
- A future execution-evidence schema (downstream of a bounded reference implementation) has a stable semantic floor to build from, rather than needing to invent minimum-facts requirements as a side effect of schema design — restating, for Gate 3, the same benefit ADR-0013 claims for Gate 2's relationship to this ADR.

### Negative / Tradeoff

- This ADR's own acceptance does not, by itself, resolve Gate 3 in ADR-0011's sense unless ADR-0013 is also separately accepted by then — a dependency this ADR states rather than resolves, and one a future implementer must track independently.
- The evidence-durability axis's illustrative three-value shape is deliberately coarse; a real bounded implementation may surface retention-failure modes (partial writes, delayed durability, eventual consistency) this ADR's minimal shape does not distinguish, and a future schema may need to refine it.
- The exception carved out in **Execution Evidence Definition** — that a `NOT_ATTEMPTED` outcome caused by binding-verification failure gets an execution-evidence record while other `NOT_ATTEMPTED` causes do not — introduces an asymmetry a future implementer must apply carefully rather than treating all `NOT_ATTEMPTED` outcomes identically.
- Whether the existing six-value `ProvenanceClassification` enum suffices remains genuinely unresolved by this ADR, which a future schema-design step must still settle before publication.

## Security Consequences

### Prevented by this architecture

- Execution evidence being treated as, mutated into, or confused with authorization evidence, kernel evidence, gateway audit facts, adapter evidence, or identity evidence.
- A `PERSISTENCE_FAILED` evidence-durability outcome silently revising, retracting, or casting doubt on an already-observed attempt-outcome or resulting-state-verification value.
- Treating a binding-verification failure — the exact substitution/mutation event ADR-0012 exists to catch — as a fact with no durable execution-side record, merely because dispatch never occurred.
- Treating a correlation identifier, on its own, as proof that an execution-evidence record is genuine or that the execution it describes actually corresponds to the authorized operation.
- Silent, ungoverned proliferation of freshness-relevant fields into execution evidence ahead of the dedicated replay/freshness decision ADR-0012 and ADR-0013 both reserve.

### Still requiring follow-on architecture

- The broader replay/freshness properties this ADR explicitly declines to narrow further (**Replay/Freshness Boundary**).
- Whether the existing six-value `ProvenanceClassification` enum suffices for execution-observed facts, or a new value is required (**What This ADR Deliberately Leaves Open**).
- The exact reasons distinguishable within `OUTCOME_UNKNOWN` for a given protocol, as governed fields — left to future, protocol-specific schema design.
- Protocol/device credential custody, if the eventually selected bounded target requires one (Gate 4) — unaffected by, and not made conditional on, this ADR.
- The eventual execution-evidence schema itself, deferred per **Schema Publication Boundary**.

### Residual risks

- A compromised protocol-executor role can fabricate any observation an execution-evidence record would faithfully preserve, because it remains the sole authoritative observer (ADR-0013 Decision 14) — the same residual-risk structure ADR-0011 Decision 19, ADR-0012, and ADR-0013 all already accept for a compromised same-process component, restated here rather than newly introduced. Separating construction from observation (**Observation, Construction, and Retention Ownership**) is, as discovery assessment §10 states directly, "partial" mitigation at best: a sufficiently compromised executor can still fabricate what it hands to an honest construction role.
- This ADR's minimum-facts list constrains what a conforming implementation may honestly report; it does not, by itself, verify that an implementation is conforming.

## What This ADR Deliberately Leaves Open

This ADR does not decide: the exact execution-evidence field list, serialization, or a named/versioned profile identifier; whether the existing six-value `ProvenanceClassification` enum suffices for execution-observed facts, or what a seventh value would mean if one is eventually required; the exact reasons distinguishable within `OUTCOME_UNKNOWN` as governed, protocol-specific fields; whether a future execution-evidence contract should reuse ADR-0007's per-protocol-metadata-projection pattern or use a different extension mechanism (discovery assessment §19 Open Question 12); what "durable" means for a given deployment's retention mechanism; how a `PERSISTENCE_FAILED` record is communicated onward operationally; how a recovering process resolves an execution-evidence record stuck in `NOT_YET_PERSISTED` after a crash; any broader replay/freshness property beyond ADR-0013's narrow attempt-correlation resolution; device/protocol credential custody (Gate 4, not triggered by this decision); an implementation plan; a bounded reference-implementation target or protocol; or any Python interface, class, module, or package shape for the execution-evidence-producer role, consistent with ADR-0011's, ADR-0012's, and ADR-0013's own restraint on implementation specifics.

## Non-Goals

This ADR does not: implement execution; add protocol dispatch code for REST, BACnet, Modbus, OPC UA, MQTT, DNP3, IEC 61850, KNX, or Niagara; modify `basis-producer`, `basis-gateway`, `basis-adapters`, `basis-core`, `basis-identity`, or `basis-schemas`; create `basis-executor` or any other new repository; define a JSON Schema, protobuf definition, OpenAPI contract, or compatibility fixture for execution evidence; select field names, enum value identifiers, or a serialization format for any fact or axis defined here; add a seventh `ProvenanceClassification` value; resolve broader replay/freshness beyond restating, without narrowing, what ADR-0012 and ADR-0013 already narrowed; define device/protocol credential custody (Gate 4); change ADR-0011's, ADR-0012's, or ADR-0013's status; mark itself `Accepted`; imply that Gate 3 is resolved before this ADR's own separate, dedicated acceptance review, or that Gate 2 is resolved merely because this ADR depends on ADR-0013's vocabulary; create an implementation plan, a PR sequence, or a milestone count; imply a `basis-producer` "Phase 6"; or authorize protocol execution. Any class, module, function, or API name that appears anywhere in this document — including the illustrative evidence-durability values in **Evidence Durability and Persistence Failure** — is a non-normative illustration of a concept, never a specification of an interface.

## Validation / Implementation Gate

This ADR's merging does not itself constitute acceptance, consistent with this repository's established convention (see ADR-0011's, ADR-0012's, and ADR-0013's own Validation / Implementation Gate sections and [`docs/adr/README.md`](README.md#lifecycle-states)) that merging an ADR does not by itself change its status to `Accepted`. Formal acceptance of this ADR, when and if it occurs through a separate, dedicated architecture and governance review, would establish the minimum execution-evidence semantics defined here as the governed floor a future execution-evidence schema and a future bounded execution implementation must satisfy — it would not, by itself, authorize that implementation, and, per **Context** and **Relationship to ADR-0013**, above, it would not by itself satisfy ADR-0011's "Gates 1 through 3" requirement unless ADR-0013 has also, by then, been separately accepted. Per ADR-0011's own Follow-On Decision Gates and Validation / Implementation Gate sections, Gates 1 through 3 are unconditional prerequisites and Gate 4 is conditional; even full, simultaneous acceptance of this ADR and ADR-0013 would resolve only Gates 2 and 3. Gate 4 (protocol/device credential custody) remains conditionally outstanding if the eventually selected bounded target requires a protocol/device credential, and no implementation plan, bounded reference implementation, or schema publication is authorized by this ADR's proposal, and none would be authorized by its acceptance alone. Protocol execution remains entirely unimplemented and unauthorized.
