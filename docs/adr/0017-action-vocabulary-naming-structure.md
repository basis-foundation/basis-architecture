# ADR-0017: Canonical Operational Action Verb Set

## Status

Accepted

## Context

[`docs/architecture/action-vocabulary.md`](../architecture/action-vocabulary.md) defines the governance model for action naming in the BASIS ecosystem: the `{verb}:{domain}[:{object}]` structure, naming conventions, stability expectations, and the deprecation process. [`docs/architecture/action-vocabulary-reconciliation.md`](../architecture/action-vocabulary-reconciliation.md) is an ecosystem-wide inventory that found the verb set actually in use disagreed across components — `basis-adapters`' shared `VALID_ACTIONS` set, per-protocol adapter extensions, `basis-core`'s documentary verb taxonomy, `basis-console`'s provisional vocabulary module, and the architecture governance document itself all named different verbs for the same operational concepts. That report's §5 concluded that a **five-verb canonical set** — `read`, `write`, `execute`, `browse`, `subscribe` — covers every operation emitted by all nine protocol adapters once two synonym pairs are unified (`control`/`command` → `execute`; `discover` → `browse`), and recommended that "a formal ADR ... should be opened to ratify" that conclusion (reconciliation report, Executive Summary and §5).

`action-vocabulary.md` was updated, prior to this ADR's acceptance, to describe this five-verb set and its deprecated aliases (reconciliation report §6). That governance document update was not, itself, a governing decision: per [`GOVERNANCE.md`](../../GOVERNANCE.md#architecture-decision-records) and [`docs/adr/README.md`](README.md#when-an-adr-is-required), a change of this kind — one that "changes the behavior of a compatibility surface (audit schema, action vocabulary, policy format, kernel evaluation semantics)" — requires an ADR. This ADR is that formal ratification step the reconciliation report called for; it does not perform new analysis and does not change the recommendation. Its acceptance completes that ratification.

This ADR addresses **only** the canonical verb set and its deprecated aliases. It does not address the separate, still-unresolved structural question the reconciliation report calls **I-1**: that protocol adapters emit a bare verb plus separate `resource_type`/`resource_id` fields, while `basis-core` requires the composite `{verb}:{domain}[:{object}]` form, and no component currently performs the composition between the two. The reconciliation report treats the verb-set question and the composition-structure question as "two independent disagreements... easy to conflate" (Executive Summary) and resolves only the first in its recommendation. This ADR preserves that separation and resolves only the verb set.

## Decision

BASIS adopts exactly **five** canonical operational action verbs:

- `read` — retrieve the current value, state, or configuration of a resource, without modification.
- `write` — modify the value, setpoint, configuration parameter, or state of a resource. This absorbs structural configuration changes; there is no separate `configure` verb.
- `execute` — cause the resource to perform an operation or command, as distinct from writing a value (method invocation, select-before-operate / operate, overrides, command points, acknowledgements).
- `browse` — enumerate or navigate the resource or address space without retrieving operational values.
- `subscribe` — establish a subscription to ongoing telemetry or event notifications from a resource.

This is the verb set already recorded in [`action-vocabulary.md`](../architecture/action-vocabulary.md#naming-conventions). This ADR's acceptance makes it a governed decision rather than an unratified documentation update.

The following normative points apply:

1. `control` is a deprecated compatibility alias for `execute`.
2. `discover` is a deprecated compatibility alias for `browse`.
3. Existing compatibility surfaces that accept `control` or `discover` — including the `basis-adapters` normalized-request schema's `action` enum — may continue to accept them for the governed deprecation period defined by the process in [`action-vocabulary.md`](../architecture/action-vocabulary.md#deprecation-expectations) and [`compatibility-philosophy.md`](../architecture/compatibility-philosophy.md#deprecation-philosophy). This ADR does not itself define or start that period; see [Compatibility Posture](#compatibility-posture), below.
4. Built-in/default protocol-adapter normalization mappings must emit the canonical verbs (`execute`, `browse`) rather than the deprecated aliases (`control`, `discover`). This is not limited to new mappings: the reconciliation report identifies two proven existing built-in/default drifts — BACnet's default `CommandValue → control` mapping and REST's default `OPTIONS → discover` mapping — and this ADR requires both to migrate to emit `execute` and `browse` respectively. This requirement does not extend beyond those two proven drifts; it is not a mandate to audit or rewrite any other adapter's default mapping table. See [Migration posture for existing defaults](#migration-posture-for-existing-defaults), below, for how that migration is governed.
5. Existing explicit legacy mappings that use a supported deprecated alias remain valid — they are not rendered non-compliant by this decision — for the duration of the deprecation window.
6. `command` is not a canonical operational verb. Command and invocation semantics are represented by `execute`.
7. `configure` is not a canonical operational verb. Configuration mutation is represented by `write`.
8. `audit` is a domain, not an operational verb. Audit access is represented as `read` with the `audit` domain (e.g., `read:audit:log`), consistent with the `basis-core` kernel constant.
9. Credential-management operations — enrolling and revoking devices, subjects, or credentials — are outside this operational action vocabulary. If a contract for them is needed, it belongs to a separate identity/administration vocabulary, not this one.
10. Introducing a new canonical operational verb, or removing one of the five, requires Foundation architecture review and an update to this ADR's governing lineage (a superseding ADR) — it is not an implementation-local decision available to any single component repository.

### Structural scope

This decision concerns the **verb set** only — the controlled vocabulary of single-segment operation names. It does not concern, and does not resolve, the separate canonical **composite authorization action structure** `{verb}:{domain}[:{object}]` that `action-vocabulary.md` describes in its "Verbs vs. Composite Action Names" section. In particular, this ADR does not resolve:

- the structural gap between adapter output (a bare verb plus separate `resource_type`/`resource_id` fields) and kernel/policy input (a single composite action string) — reconciliation report finding **I-1**;
- who owns the composition rule that turns an adapter's verb plus its resource mapping into a canonical composite action;
- whether that ownership belongs to `basis-adapters`, `basis-gateway`, a future `basis-schemas`, or another component.

That composition/ownership problem is explicitly **out of scope** for this decision and remains **unresolved**. This ADR does not silently assign it to any component. It is tracked as an open item in the reconciliation report (§5.2) and in `action-vocabulary.md`'s "Future Shared Contract Ownership" section, and is left exactly as open as those documents already describe it.

### Compatibility posture

Canonical emission and compatibility acceptance are different concerns:

- Canonical emission requires both new mappings and the two proven existing built-in/default drifts (BACnet `control`, REST `discover`) to move to `execute` and `browse` respectively (Decision point 4; [Migration posture for existing defaults](#migration-posture-for-existing-defaults), below).
- Compatibility acceptance is a separate, ongoing obligation: `control` and `discover` remain established in the `basis-adapters` normalized-request schema and are therefore subject to the stability expectations in `action-vocabulary.md`. This ADR does not require their removal from any schema or from any accepted explicit mapping. Migrating a *default* is not the same act as removing an accepted *alias*, and this ADR does the former, not the latter.
- Eventual removal of `control` or `discover` as accepted aliases requires the deprecation process already defined in [`action-vocabulary.md`](../architecture/action-vocabulary.md#deprecation-expectations) and [`compatibility-philosophy.md`](../architecture/compatibility-philosophy.md#deprecation-philosophy) — a defined replacement, a recorded deprecation notice, a deprecation period "long enough to be operationally meaningful," adapter migration, and policy-author notice — followed by removal only after that period ends. This ADR does not schedule or perform that removal.
- This ADR does not invent a deprecation duration. Neither `action-vocabulary.md` nor `compatibility-philosophy.md` defines a specific duration (in days, months, or a version count) for this or any other action-vocabulary deprecation; both instead state that the period "depends on the pace at which dependent deployments can realistically migrate" and must be "measured in months or quarters" in OT contexts generally. Setting a specific duration for the `control`/`discover` deprecation window, including for the BACnet/REST default migration below, is a separate decision this ADR does not make.

### Migration posture for existing defaults

Changing BACnet's default `CommandValue → control` mapping and REST's default `OPTIONS → discover` mapping to emit `execute` and `browse` is an intentional, governed normalization migration, not an incidental implementation cleanup. [`compatibility-philosophy.md`](../architecture/compatibility-philosophy.md#adapter-normalization-compatibility) treats "the normalization mapping for an established protocol operation" as a compatibility surface and lists "changing the normalization mapping for an established protocol operation" among changes that "are always breaking, regardless of how they are scoped or described." This ADR does not treat that classification as avoidable for this migration; it applies.

The following constraints govern how that migration must proceed:

- **The deprecated aliases continue to be accepted.** `control` and `discover` remain valid in the normalized-request schema and continue to be accepted wherever they are accepted today. A deployment that needs to preserve the prior emission for a specific operation can do so with an explicit legacy mapping that emits `control` or `discover` for that operation, rather than relying on the adapter's built-in default. That explicit-mapping path is the compatibility bridge this migration relies on.
- **Schema acceptance is not the same claim as transparent compatibility.** The normalized-request schema continuing to accept `control` and `discover` as valid enum values does not, by itself, mean that changing an adapter's *default* emission is invisible to policies or audit interpretation. A policy or audit query written to match the operation's prior label will not automatically match the new one, or vice versa, purely because both remain schema-valid; the label a given protocol operation is normalized to is what changes, and that has policy-matching and audit-interpretation consequences independent of schema validity. This ADR does not introduce a mechanism — in the policy engine or elsewhere — that rewrites or aliases one verb to the other at evaluation time; no such mechanism exists in the current architecture, and none is proposed here.
- **Deployments relying on the current default require migration notice.** A deployment that depends on BACnet's current default `control` emission or REST's current default `discover` emission for `CommandValue`/`OPTIONS` requires migration guidance and advance notice before that default changes, consistent with `action-vocabulary.md`'s [Deprecation Expectations](../architecture/action-vocabulary.md#deprecation-expectations) (a defined replacement, a recorded deprecation notice, and policy-author notice with sufficient lead time) and `compatibility-philosophy.md`'s [Deprecation Philosophy](../architecture/compatibility-philosophy.md#deprecation-philosophy).
- **The adapter release that changes these defaults is a breaking change, and this ADR is its governing architecture decision record.** A release of `basis-adapters` that changes BACnet's or REST's established default normalization mapping must be treated under the breaking-change and versioning governance in `compatibility-philosophy.md`'s [Breaking Change Expectations](../architecture/compatibility-philosophy.md#breaking-change-expectations), which requires "a major version increment, an ADR documenting the rationale and the migration path, and a deprecation period for the surface being changed." This ADR is that ADR for these two specifically governed migrations: it documents the rationale (Context, above) and the migration posture (this section) that the breaking-change requirement calls for. Implementing the BACnet and REST default changes does not require a second architecture ADR merely because the change is breaking. The eventual `basis-adapters` release must still independently satisfy the remaining, non-architectural parts of that governance — an appropriate major-version increment, a recorded deprecation notice, and migration guidance with sufficient lead time — none of which this ADR chooses on the release's behalf: it does not select a version number, a release date, or a deprecation duration. A further ADR would be required only if implementation or release planning surfaces a new architectural decision outside what this ADR already resolves — for example, a different composition or ownership question, or a change to the verb set itself — not because the release is breaking.
- **No new compatibility machinery is introduced.** This ADR relies only on mechanisms `action-vocabulary.md` and `compatibility-philosophy.md` already define — explicit legacy mappings, the existing deprecation process, and existing versioning governance. It does not design a new compatibility mechanism, a policy-engine rewriting layer, or an alias-translation feature to accompany this migration.

## Alternatives considered

**Retain the current union of adapter-emitted verbs (`read`, `write`, `execute`, `browse`, `subscribe`, `control`, `discover`) as co-equal canonical verbs, rather than collapsing synonyms.** Rejected. The reconciliation report found `control` emitted by exactly one of nine adapters (BACnet `CommandValue`) and `discover` by exactly one (REST `OPTIONS`), while every other adapter mapping for the same operational concepts uses `execute` or `browse` respectively (reconciliation report §1.1, §3 finding I-6). Treating both members of each synonym pair as independently canonical would carry two names for one operational concept indefinitely, which the reconciliation report's evaluation criteria (protocol neutrality, long-term stability, operator comprehension) weigh against.

**Preserve `control` as canonical, separate from `execute`.** Rejected. `execute` is the majority mapping across the adapters that represent "cause a device to act" (OPC UA, DNP3, IEC 61850, Niagara, and the `basis-core` docstring), while `control` is a single-adapter outlier (reconciliation report §1.1, §3 finding I-2). Retaining both as distinct canonical verbs would require policy authors to know which of two semantically identical verbs a given adapter happens to emit, degrading the "small, protocol-neutral vocabulary" objective without adding expressive power.

**Preserve `discover` as canonical, separate from `browse`.** Rejected on the same basis: `browse` is used by more components (OPC UA, Niagara, `basis-console`) than `discover` (REST `OPTIONS` only), and the two names the same operational concept — enumeration/navigation without retrieving operational values (reconciliation report §1.1, §3 finding I-3).

**Expand the canonical vocabulary to include governance-only terms that appeared in `action-vocabulary.md` prior to the reconciliation but that no adapter emits — `command`, `configure`, `audit` (as a verb), `enroll`, `revoke`.** Rejected. The reconciliation report found these terms appear only in the architecture governance document and are not emitted by any of the nine inventoried adapters (reconciliation report §2, §3 finding I-5). `command` and `configure` are synonyms already absorbed by `execute` and `write` respectively; `audit` is already modeled as a domain, not a verb, in the `basis-core` kernel (`read:audit:log`); `enroll` and `revoke` are credential-infrastructure operations, not protocol actions on operational resources, and are out of scope for this vocabulary by definition, not by omission. Carrying unused governance-only verbs in the operational vocabulary would violate the project's own stated preference for avoiding excessive granularity and large ontologies.

**Adopt the five-verb canonical set (`read`, `write`, `execute`, `browse`, `subscribe`), with `control` and `discover` retained as deprecated aliases.** Selected. This is the set the reconciliation report found already covers every operation emitted by all nine protocol adapters once the two synonym pairs are unified, and it is the set `action-vocabulary.md` has already been updated to describe. It maximizes adapter consistency while keeping the vocabulary small, and it preserves compatibility for the two established aliases through the existing deprecation process rather than requiring an immediate breaking change.

## Consequences

### Positive

- The action vocabulary now has a single, ratified canonical verb set, ending the four-way documentation disagreement the reconciliation report catalogued (reconciliation report §2).
- Policy authorship, audit interpretation, and adapter normalization now share one governed reference for what verbs exist, which is a precondition for the long-term (years-to-decades) stability `compatibility-philosophy.md` requires of the action vocabulary.
- `action-vocabulary.md`'s description of the five-verb set and its deprecated aliases is now backed by this governing decision, rather than standing as an unratified documentation update.
- Retaining `control` and `discover` as deprecated aliases preserves their representability and gives deployments an explicit legacy-compatibility path: existing explicit mappings that reference the aliases remain supported during the deprecation period, and a deployment that needs to preserve prior default behavior for a specific operation can do so by configuring an explicit legacy mapping. This does not extend to policies or audit interpretation that depended on the *default* emission itself — see the Negative/Tradeoff bullet below; those are not transparently preserved when a built-in default changes and require migration.

### Negative / Tradeoff

- BACnet continues to emit `control` and REST continues to emit `discover` today; this ADR's acceptance does not, by itself, change either adapter's behavior. What acceptance does is architecturally authorize and require — per Decision point 4 and [Migration posture for existing defaults](#migration-posture-for-existing-defaults), above — that BACnet's and REST's built-in/default mappings migrate to the canonical verbs (`execute`, `browse`) rather than remaining on `control`/`discover` indefinitely. That migration is intentionally compatibility-sensitive — an established normalization mapping is a compatibility surface — and must follow the governed posture above, including the breaking-change and versioning governance in `compatibility-philosophy.md`. This ADR does not itself perform, schedule, or version the adapter release that carries out that migration, and does not select a version number, release date, or deprecation duration; it establishes the governing decision a future release must satisfy. Explicit deprecated-alias mappings remain available throughout as the compatibility bridge for deployments that need to preserve the prior emission.
- The structural composition gap between adapter-emitted bare verbs and kernel-required composite actions (I-1) remains unresolved. A reader of this ADR must not infer that this ADR's ratification of the verb set also resolves that gap; it does not, and this ADR takes no position on who will resolve it.
- No deprecation duration is fixed by this ADR, including for the BACnet/REST default migration above. Until a specific duration is set through the existing deprecation process, `control` and `discover` remain acceptable indefinitely in practice, which some components may treat as ambiguity about when migration should occur.
- The numbering in `docs/adr/README.md`'s own naming-convention examples and the reconciliation report's original provisional reference both anticipated this decision landing at ADR-0003; that number had since been assigned to an unrelated ADR (`0003-operation-aware-trace-audit-evidence.md`), so this decision was accepted and numbered ADR-0017 instead.
