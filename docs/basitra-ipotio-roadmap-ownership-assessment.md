# Basitra–Ipotio Roadmap Ownership Assessment

> **Status: non-normative documentation assessment.** This assessment proposes documentation alignment. It does not itself transfer ownership of any capability, accept new architecture, change the status of any ADR or roadmap, or modify any roadmap's substantive plan. Every recommendation below takes effect, if at all, only through its own bounded PR, and recommendations marked *provisional* also depend on a decision that is not yet accepted.
>
> It does not modify `ipotio/architecture`. Ipotio documents are cited by path as read-only evidence, following this repository's cross-repository citation convention, and are not hyperlinked.

**Question.** Do the capabilities described in this repository's roadmaps still belong where those roadmaps place them, now that accepted architecture separates Basitra, the BASIS subsystem within it, and upstream supervisory platforms such as Ipotio? Where they do not, which ecosystem should describe them, and through which document?

**Answer in brief.** No whole-roadmap relocation is warranted. Most capabilities remain appropriately placed in Basitra, either inside BASIS or at the Basitra level. Supervisory responsibilities should be represented through platform-neutral boundary references. Unresolved capability classifications require further decisions before any reassignment is recommended. Those classifications include device identity enrollment and device-credential provisioning (I-5), some integration classes (P-3), operation-originating responses (I-7), and the sourcing of structural relationship facts (A-3).

Keeping a roadmap document in this repository is therefore not the same as confirming Basitra ownership of every capability it mentions. A small number of capability descriptions carry assumptions that predate accepted decisions: chiefly that protocol adapters execute operations, that an orchestrator or adapter is an operation producer, and that BASIS-side graphs or consoles might hold OT asset, topology, or device-management truth. These should be clarified in place, or replaced with platform-neutral cross-references to the governing decisions. Subject to the coverage gaps in [Section 6](#6-candidate-capabilities-for-ipotio-roadmap-coverage) and the baseline limitations in [Section 8.2](#82-evidence-gaps), Ipotio's existing roadmaps provide appropriate locations for the supervisory-platform side of each split capability, so a new Ipotio roadmap is not warranted. Five boundaries remain unresolved and are listed in [Section 8](#8-unresolved-questions-and-evidence-gaps).

**Scope of this pass.** Read-only inspection of `basis-architecture` and of a local checkout of `ipotio/architecture`. Implementation repositories were not inspected; every implementation status below is the status this repository records.

**Terminology in this document.**

- *Basitra* is the project, community, and ecosystem identity ([ADR-0019](adr/0019-basitra-ecosystem-identity-and-terminology-hierarchy.md) Decision 1).
- *BASIS* is the governed-path security subsystem of Basitra ([ADR-0024](adr/0024-long-term-scope-of-basis-within-basitra.md) Decision 1), not the component family. Where a roadmap uses "BASIS" as a family label, ADR-0024 Decision 12's reading rule applies.
- *Basitra level* means inside Basitra but outside BASIS: contract publication, administrative interfaces, deployment tooling, governance, and evidence consumers (ADR-0024 Decisions 4, 6, and **Placement Summary**).
- *Ipotio* is one example of an upstream supervisory platform. It is outside BASIS and outside Basitra (ADR-0024 Decision 11). From the Basitra side, every responsibility this assessment calls "Ipotio" is a responsibility of any platform in that category. Basitra documents must not name Ipotio-specific responsibilities ([ADR-0018](adr/0018-upstream-supervisory-producer-intake-boundary.md) Decision 9; [ADR-0023](adr/0023-supervisory-platform-and-administrative-interface-boundary.md) Decision 11).
- *Operator* follows ADR-0023's split: a *BASIS administrator* operates BASIS; an *OT operator* operates equipment through a supervisory platform.
- Boundary-Aware Security is written in full, because this document also refers to building automation systems.

## 1. Purpose, Scope, and Architectural Baseline

The project owner continues to support the capabilities these roadmaps describe, including the interface strategy and an open, extensible ecosystem modeled on Python's community. This assessment therefore does not ask whether those capabilities should exist. It asks which ecosystem, and within Basitra which layer, each capability belongs to under accepted architecture, so that the roadmaps can keep their ambition without implying ownership that accepted decisions assign elsewhere.

### 1.1 What this assessment does not do

- It does not relocate, rewrite, or re-status any roadmap, and it changes no ADR.
- It does not introduce an extension architecture, plugin API, or conformance program.
- It does not decide any open decision (OD-3, OD-6, OD-9, OD-10) or deferred mechanism (subject-credential conveyance, intake transport, Gate 4 device-credential custody).
- It does not rename any repository or component.
- It does not modify `ipotio/architecture`.

### 1.2 Status vocabulary

Every source this assessment relies on is labeled with one of these statuses. The labels follow the evidence rules in [`basitra-target-architecture-discovery-assessment.md`](architecture/basitra-target-architecture-discovery-assessment.md#2-status-vocabulary-and-evidence-rules) §2.

| Status | Meaning here |
| - | - |
| **Accepted** | An ADR recorded `Accepted`, or a document governed by one. Authoritative. |
| **Proposed** | An ADR recorded `Proposed`. Not authoritative, even where implemented. ADR-0001 through ADR-0006 are in this state. |
| **Implemented** | Recorded in this repository as realized in a released or merged implementation. Implementation does not confer acceptance. |
| **Strategy** | Recorded in the strategy document outside the portions ADR-0019 adopts. Not accepted architecture. |
| **Roadmap aspiration** | A roadmap direction with status `Planned` or equivalent. Not decided, not authorized. |
| **Ipotio record** | Stated in `ipotio/architecture`. Authoritative for Ipotio's own responsibilities only; it cannot decide anything on the Basitra side. |

Each capability in [Section 3](#3-capability-ownership-assessment) is classified with one of the following labels:

| Classification | Meaning |
| - | - |
| **Basitra · BASIS** | Inside the BASIS subsystem under ADR-0024 Decision 2's membership rule |
| **Basitra · Basitra level** | Inside Basitra, outside BASIS |
| **Ipotio** | A supervisory-platform responsibility, which Ipotio holds for itself |
| **Both, separated** | Each ecosystem holds a distinct, named responsibility, and the integration boundary between them is identified |
| **Unresolved** | Accepted architecture does not place the capability, or places only part of it |

A recommendation is **firm** when accepted architecture alone supports it. It is **provisional** when it depends on an open decision, a proposed ADR, or an unselected mechanism.

### 1.5 Console identity is not operational identity

The interface review in [Section 3.1](#31-interfaces-and-console-experiences) depends on keeping the following identities apart. Each row is accepted architecture or an Ipotio record. None is introduced here.

| Identity or context | Established by | What it authorizes | What it never implies |
| - | - | - | - |
| BASIS administrative identity (console login) | BASIS enforcement at `basis-gateway` (ADR-0023 Decision 5) | Administrative actions on BASIS-governed state, each evaluated by policy | OT operation-initiation, execution, or subject standing on any OT operation |
| Authorization subject of an OT operation | The BASIS identity chain (ADR-0008; ADR-0018 Decision 3; ADR-0023 Decision 3) | Whatever BASIS policy permits for that operation | A console session; it never needs one |
| Upstream workload identity (Ipotio's requesting workload) | Ipotio establishes it; BASIS admits it at intake (ADR-0018 Decision 2; ADR-0022) | Submission of intake requests | Producer admission, subject authentication, or authorization |
| Producer workload identity | BASIS operation-producer role (ADR-0008; ADR-0022) | Submission to the gateway | Subject authority |
| OT operator identity in Ipotio | Ipotio, consuming the external identity authority (Ipotio record) | Ipotio-side operator actions | A BASIS subject or a BASIS grant, even under shared SSO (ADR-0023 Decision 8) |
| Ipotio administrative identity | Ipotio (Ipotio record, Workstream 5C) | Ipotio topology, posture, integration, and deployment administration | Any BASIS administrative authority |
| Device or protocol credential | Device; custody by the protocol-executor role (ADR-0011 Decision 14) | Protocol access to a target | Any authorization |

The interface strategy can therefore support a single person who administers BASIS and also operates equipment, and it can support single sign-on across both ecosystems, without any interface conferring the other context's authority.

## 4. Conflicts and Outdated Assumptions

None of the items below contradicts an accepted decision in a way that changes ownership. Each is wording written before a later accepted decision. The parts that restate accepted decisions can be corrected as current-state clarification without an ADR. Where an item also touches an open question (X-4's relationship-fact sourcing, X-6's degraded-mode behavior), the clarification may only state the accepted boundary and record the question; answering it requires a decision.

### X-1. Adapters and integrations described as executing operations

ADR-0011 Decision 16 states that `basis-adapters` remains "free of protocol execution," and ADR-0024 Decision 5 states that the adapter role "performs no live protocol communication and no governed protocol execution." ADR-0013 Decision 14 makes the protocol executor the sole truth-owning observer of execution-boundary facts. The following roadmap text still assigns execution, execution telemetry, or execution results to adapters or adapter-like integrations:

- [`operator-and-training-experience.md` Relationship to Current and Future Repositories](roadmaps/operator-and-training-experience.md#relationship-to-current-and-future-repositories): "`basis-adapters` will continue to supply ... execution boundaries, and execution results where applicable."
- [`post-authentication-...md` Adapter boundary](roadmaps/post-authentication-identity-activity-correlation-and-detection.md#adapter-boundary), [Response boundary](roadmaps/post-authentication-identity-activity-correlation-and-detection.md#response-boundary) ("adapter execution"), [AI boundary](roadmaps/post-authentication-identity-activity-correlation-and-detection.md#ai-boundary) ("Adapters execute."), [Conceptual Components](roadmaps/post-authentication-identity-activity-correlation-and-detection.md#conceptual-components) ("execution telemetry"), and Phase 8's component list.
- [`identity-to-operation-...md` Adapter invariant](roadmaps/identity-to-operation-contract-and-interoperability.md#adapter-invariant) and Phase 6's integration profile ("translate an enforced decision back into native protocol behavior").
- [`identity-provider-integration-...md` Repository Responsibility Model](roadmaps/identity-provider-integration-and-learning-environment.md#repository-responsibility-model).

Adjacent non-roadmap drift, already recorded by the discovery assessment's [§4.3](architecture/basitra-target-architecture-discovery-assessment.md#43-findings-from-the-inventory) finding 5, has the same cause: `basis-console.md` Design Invariant 5 and `kernel-boundary-rules.md`. `basis-console.md`'s Future Possibilities "Adapter status visibility ... what devices they are connected to" is a further instance not recorded there.

### X-2. Producer and upstream roles predating ADR-0018

The identity-to-operation roadmap's Contract Responsibility Model lists "the adapter, gateway, plugin, proxy, orchestrator, or workload that submitted the operation" as the producer. Under ADR-0010 and ADR-0018, the operation-producer role produces and submits the governed operation; an adapter is a library it invokes; `basis-gateway` is the enforcement role; and an orchestrator or scheduling system is an upstream supervisory system that submits across intake without becoming a producer. Phase 6's note that a PAM or jump-host integration "primarily contributes producer and identity evidence" needs the same check.

### X-3. Roadmaps that describe Basitra-level work as extending BASIS

`ROADMAP.md` describes the post-authentication roadmap as "extending BASIS ... into durable identity activity, correlation, deterministic detection, investigation, behavioral analytics, and bounded response." The identity-to-operation roadmap's [Central Thesis](roadmaps/identity-to-operation-contract-and-interoperability.md#central-thesis) states that "BASIS aims to become the open identity-to-operation contract." Under ADR-0024, contract *semantics* are inside BASIS, while publication, consoles, and evidence analysis are Basitra-level. ADR-0024 Decision 12 means these sentences are not wrong as current family naming. They should nevertheless state which layer each capability belongs to, so that a reader does not infer BASIS membership, and with it governed-path standing, from the word. The naming itself waits for OD-9.

### X-4. BASIS-side asset and relationship models without a stated boundary

The post-authentication topology graph (Phase 3) and the FGA relationship model (Phase 7) both name facilities, buildings, controllers, devices, and points. Two matters need to be kept apart.

**Accepted boundary.** The asset model, supervisory state, and operator workflows stay with the supervisory platform (ADR-0023 Decision 1; ADR-0018 Decision 1). Resolving an upstream durable identity to a protocol-native target belongs to the upstream system: "BASIS holds no registry of upstream identifiers, performs no lookup from an upstream reference to a protocol target, and never substitutes, completes, or corrects the protocol-native target it received" (ADR-0020 Decision 3). The operation-producer role instantiates the upstream-authored operation losslessly (ADR-0020 Decision 4). It follows that neither the investigation graph nor the relationship model can be a source of OT target resolution on the governed path. Neither roadmap conflicts with this boundary today, but neither states it.

**Unresolved mechanism.** Accepted architecture does not decide how structural relationship facts, if any are needed, enter BASIS authorization data or the investigation graph. The alternatives recorded in [U-1](#81-unresolved-boundaries) remain open: proposals adopted by the BASIS configuration authority (the pattern ADR-0020 Decision 8 decides for mapping configuration only), category-scoped context (the pattern ADR-0021 decides for request-scoped context only), and independent authoring on the BASIS side. The supervisory platform's authority over its own asset model is not evidence that any export, ingestion, storage, or relationship-authoring mechanism has been selected, and this assessment selects none.

The firm correction is therefore limited to stating the accepted boundary in each roadmap and recording the open sourcing question. Choosing a sourcing mechanism remains provisional and requires an architecture decision.

### X-5. Residual ambiguity in console scope language

[`operator-and-training-experience.md`](roadmaps/operator-and-training-experience.md#purpose-and-scope) has already been reconciled with ADR-0023. Two phrases remain open to an OT reading: "a mature operational platform for BASIS" and "execution-capable operator actions" in **Safety and Confirmation Design**. The surrounding text bounds both, so this is a precision fix, not a conflict.

### X-6. Ipotio-side drift (recorded, read-only)

These are inconsistencies inside `ipotio/architecture` relative to Ipotio's own records and to accepted Basitra decisions. They are recorded for Ipotio's maintainers and are not changed here. The first two are execution-attribution errors that accepted decisions already settle (follow-up item 6). The third is ambiguous wording around a question that is partly open (follow-up items 7 and 10). The fourth waits for OD-9 (follow-up item 8).

- `docs/roadmaps/ai-infrastructure-and-learning-environment.md` §6 shows "BASIS authorization → Ipotio deterministic authorized execution path → protocol integration → OT device." Ipotio's own `docs/ipotio-basitra-execution-role-and-context-boundary.md` and initial-platform-evolution Phase 9 place dispatch in a Basitra-conformant protocol-executor role, "never an Ipotio protocol integration."
- `docs/roadmaps/ot-platform-engineering-learning-and-reference-environment.md` §4 describes "how Ipotio authenticates subjects and producers, requests authorization, enforces the result, and contributes execution evidence." Under ADR-0008, ADR-0014, and Ipotio's own Phase 9, Ipotio neither authenticates the Basitra producer nor owns execution evidence.
- initial-platform-evolution Phase 9 calls behavior when BASIS is unavailable "a deliberate, governed decision (fail-open versus fail-closed per operation class)." Read alone, this does not exclude dispatch without authoritative permission. Ipotio's own `docs/governed-ot-execution-topology.md` already states that "an unavailable Basitra does not become an implicit `ALLOW`" and that an Ipotio component "never dispatches a governed operation itself." ADR-0011 Decision 9 and ADR-0018 Decision 6 settle governed-path dispatch and intake. The remaining per-class and per-failure-domain policy is open in both repositories (Ipotio's **Degraded-operation policy** gate; U-3). A wording correction may cross-reference the settled constraints. It may not select bypass behavior, per-operation exceptions, or new availability semantics (see D-2).
- Ipotio documents do not yet cite ADR-0024 and continue to use "Basitra" for components and roles (strategy document [C-6](architecture/basitra-ecosystem-and-boundary-aware-security.md#c-6-ipotios-existing-use-of-basitra); OD-3).

### X-7. Status statements that are stale but do not affect ownership

The post-authentication roadmap's status paragraph still refers to the `basis-gateway` operation-aware rollout, "including ... PR 7," as current work. `ROADMAP.md` records that program as released. This is noted for completeness and is not part of any ownership recommendation.

## 5. Capabilities That Remain Correctly Placed in Basitra

No whole-roadmap relocation is warranted, and every roadmap document should stay in this repository. Keeping a roadmap document is not the same as confirming Basitra ownership of every capability it mentions. This section lists the capabilities whose Basitra placement accepted architecture supports. Several need the wording clarifications in [Section 4](#4-conflicts-and-outdated-assumptions), but none of these needs to move.

**Inside BASIS:** protocol normalization and community adapters (P-1, E-3); governed execution, binding, and execution evidence (P-2, V-1); executor implementations (E-4); identity-engine capabilities (A-1); authorization evaluators and relationship sub-decisions (E-2), though not the sourcing of the facts they evaluate (A-3); policy distribution and site-local enforcement behavior (A-4); contract semantics for the identity-to-operation contract.

**At the Basitra level:** the console and its Operator and Training doctrine, including investigation, simulation, policy administration, BASIS health dashboards, and the future CLI (I-1, I-3, I-6, I-8, I-9); activity, correlation, detection, analytics, and export over BASIS evidence (V-2, V-6, E-6); contract publication, conformance, and contribution governance (E-7, G-1, G-2); deployment tooling (D-1); the identity learning environment (D-6); and the open-source and commercial boundary (G-3).

The interface strategy is therefore intact. Every interface capability these roadmaps describe for BASIS administration, investigation, and training remains a Basitra capability. What accepted architecture removes from Basitra interfaces is the origination of OT operations and the management of OT devices, and the roadmaps already disclaim both. Whether any BASIS-native capability may ever originate a governed OT operation is not settled (U-2).

**Mentioned in Basitra roadmaps but not settled.** The following capabilities appear in this repository's roadmaps, but their classification is wholly or partly unresolved. They are not recommended for retention as Basitra-owned, or for reassignment to a supervisory platform, until the named decision is made:

- device identity enrollment and device-credential provisioning (I-5; Gate 4);
- operation-originating responses, such as a pre-approved bounded control (I-7, V-5; U-2);
- integration classes that may be upstream supervisory systems or implementations of BASIS roles (P-3, E-4; U-4);
- the sourcing of structural relationship facts (A-3, V-3; U-1);
- degraded-mode behavior beyond the accepted governed-path constraints (D-2; U-3);
- BASIS or Basitra-level placement of any detection that changes an enforcement outcome (E-6, V-2). This one stays within Basitra either way.

## 9. Recommended Follow-Up PR Sequence

Each item is a separate, bounded PR. Items 1 to 4 change only current-state wording in `basis-architecture`. Items 6 and 7 change only current-state wording in `ipotio/architecture`. All six preserve each roadmap's substance and status, depend only on accepted decisions, and select no unresolved mechanism. They are firm. Items 5 and 8 are provisional, and items 9 to 11 require architecture decisions.

1. **Align execution-role wording in roadmaps (X-1).** Replace adapter execution language in the operator-and-training, post-authentication, identity-to-operation, and identity-provider roadmaps with references to the protocol-executor and execution-evidence-producer roles (ADR-0011, ADR-0013, ADR-0014, ADR-0024 Decision 5). Keep every capability description; only the execution attribution changes. **Recommended next PR**: it corrects the most widespread outdated assumption, needs no decision, and every later item builds on it.
2. **Align `basis-console.md` and `kernel-boundary-rules.md` execution wording.** Design Invariant 5, the Future Possibilities adapter-status item, and the kernel rules' "field-level command delivery" sentence. This is the drift the discovery assessment's §4.3 finding 5 already recorded, and it fits ADR-0024 **Follow-On Work** item 4.
3. **Add upstream-supervisory boundary references to the identity-to-operation, post-authentication, and FGA roadmaps (X-2, X-4, P-4, P-6, V-3, V-5, A-3).** Correct the producer list. Add ADR-0018, ADR-0020, ADR-0021, and ADR-0023 references. State the accepted boundary: the supervisory platform owns the asset model and target resolution, and neither the investigation graph nor the relationship model is a source of OT target resolution (ADR-0023 Decision 1; ADR-0020 Decisions 3–4). Record the sourcing of structural relationship facts as open (U-1), without selecting any source, export, ingestion, storage, or authoring mechanism. Route equipment-acting responses to the supervisory-platform category. Keep every reference platform-neutral.
4. **Precision fixes to console scope language and roadmap layer placement (X-3, X-5, I-6, I-7, E-6, V-2).** State which capabilities are BASIS and which are Basitra-level, without changing names. Where a capability is unresolved (I-7's operation-originating responses), say so rather than placing it. Optionally add the identity-provider roadmap to the README index in the same PR.
5. **Clarify the identity-to-operation integration classes (U-4, P-3, E-4).** Provisional: classify each integration class with ADR-0024 Decision 5's test. If any class cannot be placed without deciding ADR-0011 Decision 6's executor taxonomy, record it as open rather than deciding it.
6. **Ipotio execution-attribution correction (X-6, first two items), in `ipotio/architecture`.** Correct the execution path in `docs/roadmaps/ai-infrastructure-and-learning-environment.md` §6 and the producer-authentication and execution-evidence attribution in `docs/roadmaps/ot-platform-engineering-learning-and-reference-environment.md` §4. Both should match Ipotio's own `docs/ipotio-basitra-execution-role-and-context-boundary.md` and initial-platform-evolution Phase 9, and ADR-0008, ADR-0011, ADR-0014, and ADR-0018. This does not wait for OD-9.
7. **Ipotio fail-behavior wording (X-6, third item; D-2), in `ipotio/architecture`.** Limited to stating constraints that are already accepted and identifying the ambiguity. Cross-reference initial-platform-evolution Phase 9's "fail-open versus fail-closed per operation class" to ADR-0011 Decision 9, ADR-0018 Decision 6, and Ipotio's own `docs/governed-ot-execution-topology.md` statement that an unavailable Basitra does not become an implicit `ALLOW`, and to the **Degraded-operation policy** gate. It must not select bypass behavior, per-operation exceptions, or new availability semantics. Anything beyond the accepted constraints stays with item 10.
8. **Ipotio terminology and ADR-0024 reconciliation (OD-3), in `ipotio/architecture`.** Provisional on OD-9, as the strategy document's C-6 recommends.
9. **Relationship-fact sourcing decision (U-1).** Requires an architecture decision. Raise in FGA Phase 7 discovery, and in post-authentication Phase 3's graph ownership gate, when those phases begin, and resolve by ADR. Any Ipotio coverage follows that decision.
10. **Degraded-mode and fail-behavior decision (U-3).** Requires an architecture decision on the Basitra side (`ROADMAP.md` Phase 4's open question), with Ipotio's **Degraded-operation policy** gate decided in Ipotio's repository against it. Accepted constraints (ADR-0011 Decision 9; ADR-0018 Decision 6) bind both and are not reopened by a wording PR.
11. **Decisions that only proceed if pursued:** an ADR under ADR-0023 Decision 7 for any BASIS-native operation-originating response (U-2), and OD-6 for community principles (U-5).

No whole-roadmap relocation is warranted, and no settled capability is recommended for transfer to Ipotio. The sections that should eventually be replaced with platform-neutral boundary references, rather than kept as embedded assumptions, are:

- the equipment-acting response classes in post-authentication Phase 8;
- the unstated asset-model and target-resolution boundary in post-authentication Phase 3 and FGA Phase 7, with sourcing left open;
- the decision-translating integration profile in identity-to-operation Phase 6.

Capabilities whose classification is unresolved (I-5, I-7, P-3, A-3) stay where they are described until items 5, 9, and 11 or Gate 4 decide them. The Ipotio documents to update are `docs/roadmaps/ai-infrastructure-and-learning-environment.md` §6 and `docs/roadmaps/ot-platform-engineering-learning-and-reference-environment.md` §4 (item 6), `docs/roadmaps/initial-platform-evolution.md` Phase 9 (item 7), and, after OD-9, the documents that use "Basitra" for components (item 8).
